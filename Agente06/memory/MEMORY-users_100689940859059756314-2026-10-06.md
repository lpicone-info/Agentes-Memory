## 1. Problema actual

En `ue_solicitar_cae()` ocurre lo siguiente:

1. Se agrupan comprobantes por ente, tipo y letra.
2. Se consulta `FECompTotXRequest` en las líneas **153-160**.
3. Se calcula el tamaño efectivo del lote.
4. Se envía cada lote con `FECAESolicitar`.
5. Se procesa la respuesta.
6. Se vuelve a consultar `FECompTotXRequest` en las líneas **258-265**.
7. Se utiliza ese nuevo valor para calcular el siguiente lote.

El punto 6 es el desperdicio principal. `FECompTotXRequest` realiza:

- 3 consultas SQL locales.
- 1 llamada HTTP sincrónica a ARCA.
- Parseo de XML.

La propuesta debe conservar el agrupamiento funcional actual. El código agrupa por:

```text
ente + compro_tipo + letra
```

El punto de venta se obtiene del comprobante máximo del grupo. No recomendaría cambiar ahora esa clave de agrupamiento porque podría alterar la selección de comprobantes y la correlatividad.

## 2. Primera implementación recomendada: cambio mínimo

La primera versión debería limitarse a consultar `RegXReq` una sola vez por cada grupo actual.

### Estado actual

En el inicio del grupo:

```powerscript
ll_nro_max_reg = LONG( &
    luo_nro_reg.EVENT ue_nro_de_registros_a_enviar( &
        li_entes[li_maximo_actual], &
        ls_tipos[li_maximo_actual], &
        ls_nros_maximos[li_maximo_actual]))
```

Luego se calcula:

```powerscript

    ll_compro_a_enviar = ii_nro_reg
ELSE
    ll_compro_a_enviar = ll_nro_max_reg

```

Pero después de cada lote se vuelve a ejecutar:

```powerscript
ll_nro_max_reg = LONG( &
    luo_nro_reg.EVENT ue_nro_de_registros_a_enviar(...))
```

### Cambio propuesto

Mantener `ll_nro_max_reg` constante durante todo el grupo y eliminar la segunda llamada remota:

```powerscript

// El valor se reutiliza durante todos los sublotes.
```

En lugar de volver a consultar ARCA después de cada respuesta, solamente se incrementaría el extremo del lote:

```powerscript
IF ii_nro_reg <> 0 AND ii_nro_reg < ll_nro_max_reg THEN
    ll_compro_a_enviar = ll_compro_a_enviar + ii_nro_reg
ELSE
    ll_compro_a_enviar = ll_compro_a_enviar + ll_nro_max_reg
END IF
```

El cambio sería acotado:

- No modifica `Nro. Reg. Envío`.
- No modifica la correlatividad.
- No saltea comprobantes rechazados.
- No modifica SP ni tablas.
- No cambia el XML enviado.
- Elimina una llamada WSFE por sublote.

Con 1.014 comprobantes y lote 10, el circuito pasaría conceptualmente de:

```text

```

a:

```text

```

La cifra exacta depende de la cantidad de grupos, pero el ahorro estructural es claro.

## 4. Separar este cambio de “persistir en bloque”

La frase “acumular resultados y persistir en bloque” corresponde a una segunda etapa, bastante más invasiva.

Actualmente `ue_analizar_respuesta()`:

- Recorre cada detalle XML.
- Llama `ue_grabar_cae()` por comprobante.
- `ue_grabar_cae()` ejecuta `afu_compro_cae_grabar`.
- Cada comprobante termina con su propio `COMMIT`.
- Luego se actualiza `afu_compro_cae_solicitud` nuevamente por comprobante.

Para persistir en bloque habría que modificar también:

- `uo_nv_afip_wsfe_autrequest.sru`
- `uo_nv_solicitud_cae.sru`
- `afu_compro_cae_grabar`
- `afu_compro_cae_solicitud`
- posiblemente `afu_compro_cae_respuestas`

Las alternativas técnicas serían:

1. **XML de resultados por lote** recibido por un nuevo SP.
2. **Tabla staging identificada por `id_solicitud`**.
3. **TVP de SQL Server**, si el mecanismo de conexión de PowerBuilder lo permite de forma estable.

La opción más compatible con el circuito actual probablemente sería una tabla staging o un SP que reciba el XML normalizado. Sin embargo, requiere resolver cuidadosamente:
