## Reversibilidad

### Mediante la aplicación normal

**No es viable como una sola transacción reversible.**

Razones:

- La importación de aportes ejecuta `COMMIT`.
- La facturación confirma el comprobante mediante otro `COMMIT`.
- La impresión realiza un tercer `COMMIT`.
- El PDF o salida de impresión es externo a SQL Server.
- Se consumen números de comprobante.
- Se actualizan cuenta corriente, prefacturas, aportes y registros auxiliares.
- Revertir solamente las tablas principales no reconstruye necesariamente todo el estado.

### Transacción SQL única

Técnicamente podría diseñarse una prueba de laboratorio llamando directamente a los mismos procedimientos desde una conexión SQL y manteniendo un `BEGIN TRAN` exterior. No la recomiendo como prueba funcional principal porque:

- No reproduce las validaciones y commits de la aplicación.
- Requiere parametrizar manualmente todo el circuito.
- Mantendría una transacción extensa con bloqueos.
- No incluiría de forma reversible la creación del PDF.
- Todavía habría que auditar todas las dependencias transitivas antes de certificar ausencia de efectos externos.

Sería útil como prueba técnica complementaria, no como sustituto del flujo funcional.

### A. Copia aislada — recomendada

Restaurar una copia reciente de `Desa_Britanico`, instalar allí exactamente el SP actual y apuntar el cliente PowerBuilder a esa base.

Ventajas:

### 1. El CUIT inicial se obtiene de la empresa, no del aporte real

→ ningún aporte coincide con DC.cuit

- El primer bloque de saldo inicial acepta únicamente aportes que **nunca tuvieron ajustes**.

- el remanente de un solo integrante;
- una combinación incorrecta;
- cero;
- un resultado distinto según el plan de ejecución.
