## Reversión

La reversión no aplica un importe negativo sobre cualquier lado. El proceso determina cuál comprobante debe actuar como débito y cuál como crédito:

```sql
IF @csr_debi_credi = 1
    débito  = comprobante original
    crédito = comprobante reverso
ELSE
    débito  = comprobante reverso
    crédito = comprobante original
```

Esto está explícito en [afs_revertir_comprobantes_main.sql](/home/desarrollo-ia-06/.openclaw/workspace/svn/ogomez-Prevencion-trunk/backend/procedures/afs_revertir_comprobantes_main.sql:479).

```text
  original: +100 → lado débito
```

```text
Reversión de un crédito:
  reverso:  +100 → lado débito
  original: -100 → lado crédito
```


## Aportes negativos

Un aporte negativo legítimo podría representarse de dos maneras:

1. **Como crédito:** saldo negativo y debe participar del lado `a`, con `a.saldo < 0`.  
   Este caso sigue permitido.

2. **Como débito:** debería materializarse mediante un comprobante o ajuste de débito cuyo saldo pendiente sea positivo.  
   También sigue permitido porque entra como `b.saldo > 0`.

Lo que queda bloqueado es utilizar un saldo negativo como lado débito:

```text
saldo inicial: -100
importe aplicado: 50
resultado: -100 - 50 = -150
```

Eso no compensa el aporte: aumenta el saldo contrario, que es precisamente el defecto del 30531.

## Punto importante sobre `apo`

`tipo_proceso = 'apo'` puede justificar omitir el control de **magnitud**, porque existen compensaciones especiales entre períodos y conceptos. Pero no justifica invertir la **dirección**:

- puede aplicar más allá de una magnitud bajo una regla especial;
- no debería restar un importe positivo sobre un saldo que ya es negativo.

Además, `@total_a_pagar` se genera positivo. Si existiera una regla funcional que permitiera pasar importes negativos a `afu_aplicar_compro_item`, entonces habría que diseñar otro tratamiento; no alcanza con volver de `> 0` a `<> 0`.
