```text

→ cambio de forma_farma o dosis_diaria
→ dw_prestac::ue_post_itemchanged
```

Y está condicionado a:

```powerscript
IF tipo_prod = 'D' THEN
    canti = DaysAfter(orden_fecha, vali_fecha) * dosis_diaria

```

El producto de la prueba quedó clasificado como producto normal:

```text
produ         = 22801
troquel       = 450247
droga_presen  = 000000000
tipo_prod     = P
```

Por lo tanto:

- cambiar Dosis Diaria dispara el evento, pero no recalcula porque no es tipo `D`;
- cambiar Validez no recalcula;
- cambiar Orden no recalcula;
- seleccionar el producto inicializa `canti`, pero no aplica la fórmula;
- modificar manualmente Cantidad conserva el valor ingresado.

## Validación al grabar

Al aceptar, el sistema:

- valida coherencia de las fechas;
- exige que `canti` no esté vacío;
- valida que el valor tenga formato numérico.

No comprueba nuevamente:

```text
canti = DaysAfter(orden_fecha, vali_fecha) × dosis_diaria
```

`pru_auto_produ_items` también guarda directamente los valores recibidos de `canti` y `dosis_diaria`, sin recalcularlos.

Esto explica por qué `1880689` pudo grabarse nuevamente en estado Aceptado con cantidad `30`.

## Impacto en generación múltiple

Con el circuito existente:

1. `RowsCopy` copiaría `canti` y `dosis_diaria` de la original.
2. Las nuevas fechas se asignarían directamente a la autorización hija.
3. Esa asignación no dispara `itemchanged`.
4. `ue_grabar` solo verificaría que `canti` tenga valor.

Consecuencia: **la hija conservaría la cantidad copiada aunque las nuevas fechas determinen otra cantidad teórica**. El comportamiento actual no recalcula automáticamente `canti` después de `RowsCopy`.
