## 1. Qué corrige actualmente `afs_valida_valor_recargo`

Existen tres conceptos que conviene separar:

- **Tope tarifario del titular:** se obtiene de `afi_tarifas.tope`.
- **Tope persistido del familiar:** se obtiene de `afi_edad_topes.tope`.
- **Tope efectivo de cálculo:** es el valor que finalmente se usa contra `tari_recargos`.

Para el contrato `529424`, por ejemplo, puede ocurrir que `afi_tarifas` tenga un tope alto o que el cónyuge tenga un tope alto en `afi_edad_topes`. Si `afs_puede_cambiar_tope` devuelve `0`, ese tope ya no debería utilizarse para seleccionar un recargo superior.

El fix actual hace conceptualmente esto:

```sql
EXECUTE afs_puede_cambiar_tope
    @prm_prepaga = @prepaga,
    @prm_contra  = @contra,
    @prm_inte    = @inte,
    @prm_perio   = @perio,
    @prm_ret     = @cambia OUTPUT

IF @cambia = 1
    SET @tope = @edad_busqueda
ELSE IF @tope > @max_edad_cambio_tope
    SET @tope = @max_edad_cambio_tope
```

Después, la consulta contra `tari_recargos` utiliza ese `@tope` ya limitado.

Por lo tanto, el fix resuelve el **cálculo del recargo**, aun cuando el dato histórico de `afi_edad_topes` continúe siendo, por ejemplo, `91`.

### Alternativa A: congelar el tope vigente

- No actualizar más `afi_edad_topes`.
- Conservar el último tope válido anterior al cumplimiento de la regla.

SET @tope_busqueda = @tope
