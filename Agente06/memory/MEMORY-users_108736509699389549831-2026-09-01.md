**Restricción de configuración**

El procedimiento de alta `pri_topes.sql` intenta impedir que una misma cobertura tenga más de un tope vigente con la misma `unidad`. Es decir, conceptualmente permitiría coexistir, por ejemplo:

- un tope anual `A`
- un tope mensual `M`

Pero no permitiría dos mensuales o dos anuales vigentes para la misma `cober`.

Referencia: [pri_topes.sql](/home/desarrollo-ia-06/.openclaw/workspace/svn/ogomez-Prevencion-trunk/backend/procedures/pri_topes.sql:50).

Importante: esa restricción no está garantizada por la tabla. `TOPES` tiene PK solo por `(grupo, cober)`, no por `cober + unidad`.

Referencia: [TOPES.sql](/home/desarrollo-ia-06/.openclaw/workspace/svn/ogomez-Prevencion-trunk/backend/tables/TOPES.sql:14).

En `prevencion_entrega` encontré datos vigentes donde una misma `cober` tiene más de un grupo de la misma unidad. Ejemplo detectado: `cober = 17478`, plan `A3`, prestación `660543`, con 2 topes anuales y 2 mensuales vigentes. Por eso no tomaría la restricción como absoluta: el ABM estándar la intenta controlar, pero la base permite que existan configuraciones duplicadas.

**Orden de control**

El cursor ordena por:

```sql
ORDER BY g.unidad
```

Con unidades `A` y `M`, se controlan primero los anuales y después los mensuales.

Pero dentro de la misma unidad no hay orden definido, porque no ordena por `grupo`, `tope`, `alta_fecha` ni otro campo. Si hay dos topes anuales o dos mensuales para la misma cobertura, el orden entre ellos no queda garantizado.
