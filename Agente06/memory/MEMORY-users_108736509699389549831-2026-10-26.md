## 1. Conclusión ejecutiva

El comportamiento esperado **no está implementado de forma completa en ninguna de las dos ramas**.

Ambas ramas tienen una lógica en `afi_genera_aportes_estimados.sql` que, durante una generación posterior de estimados:

1. Detecta un aporte real del mismo período y CUIT.
2. Traslada el importe del aporte real desde `impor_facturable` hacia `impor_consumible`.
3. Deja `impor_facturable = 0`.

La lógica no convierte el aporte estimado en consumible. Además:

- Se ejecuta dentro de la generación de estimados, no al importar el aporte real.
- La búsqueda se realiza por período y CUIT, sin restringir explícitamente por `contra` e `inte`.
- Si el aporte real ingresa después del estimado y no vuelve a ejecutarse la generación, no se produce el traslado.
- El estimado previamente creado no es neutralizado explícitamente.

Por lo tanto, la implementación existente es una compensación parcial y no garantiza la regla funcional solicitada.

- importación;
- generación de estimados;
- facturación;
- reversión/desaplicación;

- derivaciones;
- reprocesos;
- datos históricos.

3. Qué hacer con estimados ya facturados.
4. Cuál es la clave exacta de correspondencia: prepaga, contrato, integrante, CUIL, CUIT, obra social, sistema y período.
5. Cómo debe funcionar el reproceso de archivos.
6. Cómo se revierte y reconstruye el saldo ante una desaplicación.
7. Si se requiere adecuación de datos históricos.

# 1. Procedimientos SQL obligatorios

## 1.1. `afi_aportes_impor.sql` — Obligatorio

**Motivo:** es el punto común de importación de aportes reales.

## 1.2. `afi_genera_aportes_estimados.sql` — Obligatorio

**Motivo:** actualmente puede generar un estimado aun cuando ya existe un aporte real para el mismo período.

La lógica actual detecta un real mediante período + CUIT y luego hace:

```sql
impor_consumible = impor_facturable
impor_facturable = 0
```

Pero:

- no verifica contrato e integrante en esa condición;
- no neutraliza el estimado;
- la conciliación ocurre demasiado tarde;
- puede ejecutarse nuevamente y repetir la evaluación.

**Cambio requerido:**

- verificar existencia de aporte real antes de insertar el estimado;
- si existe real, no generar el estimado para ese período;
- si ya existe un estimado, marcarlo como no reutilizable según la definición funcional;
- evitar duplicación al regenerar;
- conservar trazabilidad entre el estimado y el real si el modelo lo requiere.

**Complejidad:** alta.
