Pato, hoy en **Subedatos – Importación de Derivación de aportes** existen dos tratamientos distintos:

### 1. Error de formato o lectura del archivo

Ejemplos: fecha inválida, campo numérico con texto o decimal incorrecto.

- La fila se marca como no importable.
- El error se muestra en **Detalle de errores**, indicando registro, campo y valor.
- Si existe al menos uno de estos errores, **se bloquea la importación completa del archivo**.
- El sistema informa: “Se encontraron errores. El archivo no podrá ser importado”.

Evidencia: [wp_clase_importacion.srw](</home/desarrollo-ia-07/.openclaw/workspace/svn/mpariso-Infomedical-trunk/exe/Source Infomedical/wp_clase_importacion.srw:612>).

### 2. Error funcional detectado al verificar

Una vez leído correctamente el archivo, se ejecutan validaciones como:

- afiliado inexistente;
- fila duplicada;
- CUIT vacío o no numérico;
- vigencia inválida;
- sueldo obligatorio;
- sistema de aportes inexistente;
- obra social inválida;
- superposición o incompatibilidad con derivaciones existentes.

En este caso:

- Las filas rechazadas aparecen en la pestaña **Rechazos**, con el motivo correspondiente.
- Las filas sin errores permanecen disponibles para importar.
- Si existe al menos una fila válida, se habilita **Importar**.
- Al importar, se procesan las filas válidas y se excluyen las rechazadas.
- Si todas las filas tienen errores, no se habilita la importación.

Evidencia: [wp_import_deriv_aportes.srw](</home/desarrollo-ia-07/.openclaw/workspace/svn/mpariso-Infomedical-trunk/exe/Source Infomedical/wp_import_deriv_aportes.srw:67>) y [afs_impor_deriv_apor_tmp.sql](</home/desarrollo-ia-07/.openclaw/workspace/svn/mpariso-Infomedical-trunk/backend/procedures/afs_impor_deriv_apor_tmp.sql:54>).

**Conclusión funcional:** Derivación de aportes aplica **rechazo total** ante errores de estructura/formato del TXT, pero permite **procesamiento parcial** ante errores funcionales: importa las filas válidas y deja las restantes como rechazadas.

Campos utilizados:

- `errorDescr`: contiene el mensaje mostrado en la pantalla.
- `spid`: separa los registros de cada sesión de importación.

La tabla temporal es solamente el soporte de ejecución; **no contiene la configuración de las validaciones**.

## Validaciones actuales

El procedimiento evalúa, en este orden:

1. **Contrato inexistente**
   - No encuentra un titular en `AFILIADOS` para la entidad y el contrato.
   - Condición adicional: `AFILIADOS.paren = 'T'`.

2. **Afiliado inexistente**
   - No encuentra la combinación de entidad, contrato e integrante en `AFILIADOS`.

3. **Regristro duplicado**
   - El texto contiene actualmente ese error de redacción.
   - Se detectan registros repetidos para entidad, contrato, integrante y vigencia.
   - Considera duplicados dentro del archivo y registros relacionados con `AFI_MAILS`.

4. **Indique la vigencia desde**
   - `AFI_IMPOR_MAILS_TMP.vigen_desde` es nulo o queda con `01/01/1900`.

5. **Afiliado no vigente a la fecha informada**
   - `AFILIADOS.ingre_fecha` es posterior a la vigencia informada.
   - La validación actual no evalúa `AFILIADOS.baja_fecha`.

6. **Formato de email incorrecto**
   - La función `afn_valida_mail` determina que el correo no tiene un formato válido.

Cada fila conserva **un solo error**. Como las validaciones se ejecutan secuencialmente y las siguientes únicamente procesan filas sin error, se muestra el primer incumplimiento encontrado.

- El correo debe tener formato válido.

- `AFILIADOS`: existencia del contrato, integrante y fecha de ingreso.

## Importación de derivación de aportes

También tiene campos obligatorios fijos:

- CUIT.
- Vigencia desde.
- Sueldo.
- Sistema de derivación.
- Obra social.

La vigencia hasta no es obligatoria, pero, si se informa, no puede ser anterior a la vigencia desde.

### Tablas evaluadas

- `AFILIADOS`
  - Verifica que el afiliado exista.

- `AFI_HISTO_INGRESOS`
  - Verifica que la vigencia de la derivación no sea anterior al ingreso del afiliado.

- `DERIV_APORTES_SISTEMA`
  - Verifica que el código de sistema informado exista y tenga `baja_fecha IS NULL`.

  - Verifica superposiciones, derivaciones posteriores y derivaciones vigentes para otras obras sociales.

- `RECHA_MOTIVOS`
  - Obtiene la descripción y clasificación del código de error.
  - No determina si el campo es obligatorio.

## Ejemplo de diferencia entre clientes

Si ambos clientes informan el sistema de derivación `XYZ`:

- En el cliente A, `XYZ` existe vigente en `DERIV_APORTES_SISTEMA`: el valor es aceptado.
- En el cliente B, `XYZ` no existe o tiene `baja_fecha` informada: se genera el rechazo correspondiente.

En ambos clientes el campo **Sistema sigue siendo obligatorio**. Lo que cambia es el catálogo de valores aceptados.

Para Mails y Derivación de Aportes:

- La **obligatoriedad** está programada en el SP.
- Las tablas maestras determinan si el valor informado es válido.
- `RECHA_MOTIVOS` determina principalmente el texto o clasificación del rechazo.
- `prepaga` limita la búsqueda a la entidad seleccionada, pero no activa ni desactiva campos obligatorios.
- Una obligatoriedad diferente entre clientes solo sería posible si tuvieran versiones o personalizaciones distintas del SP.
