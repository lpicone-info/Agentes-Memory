### [01/09/2026 12:22:03] Agente

Cristian, los saltos de línea se procesan como caracteres dentro del texto:

- `CHAR(13) + CHAR(10)` = salto Windows `CRLF`
- `CHAR(10)` = salto Unix `LF`
- Si el comentario viene con esos caracteres desde SQL, la DataWindow puede respetarlos visualmente.
- Si no hay salto real, la DW solo hace ajuste visual por ancho cuando tiene `edit.autohscroll=no` y `height.autosize=yes`.

En tu caso testigo, el comentario sí trae saltos reales desde base.

Sobre esto:

```powerscript
Send(Handle(THIS),256,9,LONG(0,0))
RETURN 1
```

Significa:

- `Send(...)`: envía un mensaje Windows al control actual.
- `Handle(THIS)`: obtiene el handle del objeto actual.
- `256`: es `WM_KEYDOWN`, o sea “tecla presionada”.
- `9`: es `VK_TAB`, la tecla Tab.
- `LONG(0,0)`: arma el `lParam` del mensaje en cero.
- `RETURN 1`: indica que el evento queda consumido/manejado y evita el procesamiento normal posterior.

En limpio: esa línea simula que el usuario presionó `Tab` sobre el control actual. Sirve para forzar navegación de foco. No convierte texto a mayúsculas por sí misma, pero sí puede provocar entrada/salida de edición o disparar lógica genérica asociada al foco.

### [01/09/2026 12:43:08] Agente

Cristian, la diferencia central es esta:

**Otros clientes que funcionaban bien**
En Celer, por ejemplo, el monto visible y la barra usan el mismo criterio:

```text
saldo_anterior1 = deuda1 - creditos
monto visible = impor1 + saldo_anterior1
barra = impor1 + deuda1 - creditos
```

Entonces si hay crédito, ese crédito se descuenta una sola vez y todo queda alineado: importe mostrado, condición de visibilidad y monto codificado en la barra.

**Montegrande antes del cambio**
Montegrande mostraba el vencimiento con otro criterio:

```text
monto visible = total - creditos
```

Pero la barra se generaba antes con la función Medimas:

```text
afn_get_medimas_codibarra(impor1, impor2, deuda1 - creditos, deuda2 - creditos)
```

En tu caso:

```text
impor1 = 43000
deuda1 = 0
creditos = 32000
deuda_neta = deuda1 - creditos = -32000
```

La función vieja hacía:

```text
barra = impor1 + deuda_neta
barra = 43000 - 32000
barra = 11000
```

Ahí estaba el problema: Montegrande ya tenía el importe neto en `impor1`, pero la función volvía a aplicar el crédito por `deuda_neta` negativa.

**Cambio que hice**
Solo cambié el tratamiento cuando la deuda neta llega negativa o cero:

```text
Antes:
importe_barra = importe + deuda_neta

Ahora:
si deuda_neta <= 0 -> importe_barra = importe
si deuda_neta > 0  -> importe_barra = importe + deuda_neta
```

Impacto sobre otros clientes:
- Si un cliente ya funcionaba con `deuda_neta > 0`, no cambia.
- Si un cliente no usa `contra_forma IN ('M','T','E')`, no pasa por `afn_get_medimas_codibarra`.
- Si un cliente usa esta función y manda `deuda_neta <= 0`, el cambio sí impacta, pero justamente evita que se reste crédito dos veces.

Con los profiles revisados, el único cliente detectado usando ese camino fue Montegrande/CMMG.
