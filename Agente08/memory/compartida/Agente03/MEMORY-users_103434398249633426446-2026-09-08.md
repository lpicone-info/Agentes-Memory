### [08/09/2026 15:36:16] Agente

Marcelo, la razón más probable es esta: **el índice no cubre las claves reales usadas en el JOIN**.

Vos decís que el índice cubre:

```sql
ente, compro_tipo, compro_nro
```

Pero el query une por:

```sql
CE.ente_rc = t.ente
AND CE.compro_tipo_rc = t.compro_tipo
AND CE.compro_nro_rc = t.compro_nro
```

Es decir, SQL Server necesita buscar por:

```sql
ente_rc, compro_tipo_rc, compro_nro_rc
```

Si el índice `ndx_compro_exportacion` está armado sobre `ente, compro_tipo, compro_nro` y no sobre las columnas `_rc`, no sirve para hacer `Index Seek` por ese predicado. Aunque tenga `lote` como `INCLUDE`, el motor no puede usar los `INCLUDE` para navegar el índice; solo las columnas clave del índice sirven para seek.

Por eso termina haciendo `Index Scan`: el índice puede “cubrir” datos para evitar lookup, pero **no cubre la forma de búsqueda**.

El índice útil para ese query debería tener como claves, en ese orden probable:

```sql
ente_rc,
compro_tipo_rc,
compro_nro_rc
```

e incluir:

```sql
lote
```

Ejemplo conceptual:

```sql
CREATE INDEX ndx_compro_exportacion_rc
ON compro_exportacion
(
  ente_rc,
  compro_tipo_rc,
  compro_nro_rc
)
INCLUDE
(
  lote
);
```

Otros motivos posibles, secundarios:

- `#t_compro_01` no tiene estadísticas útiles o tiene muchas filas, y el optimizador elige scan + hash/merge.
- Diferencia de tipos/collation entre `CE.compro_nro_rc` y `t.compro_nro`, causando conversión implícita.
- El `UPDATE` sobre temporal puede favorecer un plan de lectura completa si estima muchas coincidencias.
- El hint `WITH (INDEX = ...)` fuerza ese índice, pero no fuerza `SEEK`. Si las claves no sirven para seek, igual escanea.

Conclusión: con el query mostrado, revisaría primero la definición exacta de `ndx_compro_exportacion`. Si no empieza por `ente_rc, compro_tipo_rc, compro_nro_rc`, el `Index Scan` está justificado.
