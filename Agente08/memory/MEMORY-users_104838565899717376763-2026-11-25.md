VALE, cuando hablan de **llaves** se refieren a valores secretos que utiliza un algoritmo para **cifrar y descifrar** información.

No son permisos de usuario ni contraseñas comunes.

### Ejemplo aplicado al TK 6533

Supongamos que se carga este número ficticio:

`1234 5678 9012 3456`

1. **Al guardar**, el sistema utiliza una llave secreta y lo transforma en algo ilegible:

   `ENC:v1:8F3A7C91D2...`

2. En la base se almacena:

   - Valor cifrado: `ENC:v1:8F3A7C91D2...`
   - Últimos cuatro dígitos: `3456`
   - Versión de llave: `1`

3. En las pantallas y reportes se muestra:

   `************3456`

4. Cuando se genera el TXT, el proceso autorizado usa la llave para recuperar temporalmente:

   `1234567890123456`

5. El número completo se incorpora al TXT, pero **no vuelve a guardarse descifrado en la base**.

### ¿Dónde debería estar la llave?

La llave debe almacenarse fuera de las tablas y del código fuente, en un almacén seguro de secretos. De esa manera, alguien que consulte o copie la base solamente verá el contenido cifrado.

### “Llave de entrada” y “llave de salida”

En la reunión probablemente utilizaron esos términos para describir:

- **Entrada:** cifrar el número antes de guardarlo.
- **Salida:** descifrarlo únicamente cuando el exportador genera el TXT.

Técnicamente podría utilizarse una misma llave simétrica para ambas operaciones, protegida por permisos y con versiones para permitir su rotación.

La diferencia importante es:

- **Permiso:** determina qué proceso puede solicitar el descifrado.
- **Llave:** es el secreto criptográfico que permite realizarlo.

No serviría aplicar un hash, porque el hash no puede revertirse y el sistema necesita recuperar el número completo para generar determinados TXT.
