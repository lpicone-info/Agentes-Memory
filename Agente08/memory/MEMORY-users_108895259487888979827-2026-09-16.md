Jean, analicé el ticket InvGate **6230** y el código vigente de `estandar-trunk`.

**Clasificación:** Error / brecha funcional en Webpos.

**Conclusión**

Webpos **sí consulta las situaciones terapéuticas vigentes**, pero la implementación actual tiene dos limitaciones importantes:

1. **La pantalla 02C no muestra ni permite seleccionar una situación terapéutica.**
2. Si existen varias situaciones vigentes, el backend selecciona **una sola historia terapéutica**, no combina ni permite elegir explícitamente entre todas.

### Funcionamiento para topes

Para una 02C, el backend busca automáticamente una situación terapéutica vigente priorizando:

1. Situación con `gene_topes = 'N'` y `paga_copago = 'N'`.
2. Si no encuentra, una con `gene_topes = 'N'`.
3. Si tampoco encuentra, una con `paga_copago = 'N'`.

Esto está implementado en [`prs_histo_auto_remotas.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_histo_auto_remotas.sql:40).

Sin embargo, que la situación tenga `gene_topes = 'N'` **no alcanza necesariamente para excluir cualquier prestación del tope**. También se valida que la prestación esté relacionada con esa situación en `situ_prestaciones_exentas`, mediante [`prs_valida_prestac_exentas.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_valida_prestac_exentas.sql:28).

Por lo tanto:

- Situación vigente seleccionada.
- `gene_topes = 'N'`.
- Prestación relacionada como exenta en `situ_prestaciones_exentas`.

Recién con esa combinación la prestación queda excluida del cálculo del tope.

### Funcionamiento para copagos

El proceso de copagos también busca una situación con `paga_copago = 'N'`, mediante [`prs_situ_histo_valor.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_situ_histo_valor.sql:37).

Pero luego la lógica de [`prs_valida_of_copagos.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_valida_of_copagos.sql:191) hace lo siguiente:

- Si la situación está configurada para no pagar copago, excluye únicamente las prestaciones relacionadas en `situ_prestaciones_exentas`.
- Las demás prestaciones continúan ingresando al cálculo normal de copagos del plan, convenio o prestador.

La validación de copagos para Webpos se ejecuta desde [`prs_valida_copago_remoto.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_valida_copago_remoto.sql:82).

### Caso de varias situaciones terapéuticas

Cuando el afiliado posee varias situaciones vigentes, Webpos no las presenta para que el prestador seleccione una. El backend guarda un único campo `histo` en la transacción 02C, como se observa en [`prs_valida_of_auto_remotas.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_valida_of_auto_remotas.sql:1141).

Además, en [`prs_histo_auto_remotas.sql`](/home/desarrollo-ia-08/.openclaw/workspace/svn/estandar-trunk/backend/procedures/prs_histo_auto_remotas.sql:61) no hay un criterio explícito de ordenamiento para resolver varias situaciones igualmente válidas. Por eso, no se puede asegurar que se aplique la situación terapéutica esperada cuando existen varias vigentes.

### Relación con el ticket 6230

La evidencia del ticket indica que las situaciones **Maternidad** e **Infantiles** estaban configuradas para no generar copagos ni afectar topes, pero las autorizaciones Webpos **247320** y **248162** generaron excedentes y copagos.

El código permite explicar ese comportamiento por dos causas posibles:

- La prestación utilizada no estaba registrada en `situ_prestaciones_exentas` para la situación terapéutica.
- El afiliado tenía más de una situación vigente y Webpos tomó otra historia terapéutica distinta de la esperada.

**Respuesta concreta:** Webpos toma en cuenta la situación terapéutica para topes y copagos, pero no como una exención global automática. La aplicación depende de la situación terapéutica que el backend selecciona y de la relación específica de cada prestación en `situ_prestaciones_exentas`. Con varias situaciones vigentes, la resolución no es explícita ni controlable desde la pantalla 02C.
