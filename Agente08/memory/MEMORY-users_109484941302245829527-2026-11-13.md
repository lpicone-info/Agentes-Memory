Javier, el mensaje se produciría cuando el WS **recibe la transacción, pero no puede identificar al prestador**.

**Clasificación:** Configuración/datos maestros.

**Evidencia**
- El manual de WS establece como obligatorio el nodo `<Prestador>` con `CuitPrestador`; según la transacción también exige `lugarAtencion`.
- `estandar-trunk` busca el prestador activo por `efe_prestad` o por `cuit_prestad`.
- Si no lo encuentra localmente, Afilmed utiliza el rechazo **18 – Prestador inexistente**, no 204. Por lo tanto, **“(SM) 204” es una devolución funcional de la capa remota**, no un error local de Afilmed ni necesariamente de conectividad.

**Casos que pueden originarlo**
1. `CuitPrestador` vacío o ausente en el XML.
2. CUIT informado pero inexistente o dado de baja en `prestadores`.
3. Código de prestador vacío o inválido.
4. `lugarAtencion` inexistente, dado de baja o no asociado al prestador.
5. Nodo `<Prestador>` mal formado o no interpretado por el WS.

**Conclusión**
El caso más directo para reproducirlo sería ejecutar una transacción remota con un **CUIT de prestador no registrado como activo** —o sin informar el CUIT—. El WS respondería funcionalmente **204: “No hay datos del prestador”**. La frase “No existe respuesta del servidor” resulta engañosa: sí hubo una devolución del servicio, pero fue un rechazo funcional.

Para determinar cuál de estas condiciones ocurrió en una transacción concreta necesito el número de transacción y la base donde se ejecutó.
