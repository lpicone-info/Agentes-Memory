Javier, el recuadro **“Cambiar password”** sirve para obligar a uno o varios usuarios a cambiar su contraseña en el próximo ingreso.

### Cómo se utiliza

1. Se filtran los usuarios por grupo, sucursal, sector, rol, etc.
2. Se presiona **Consultar**.
3. Dentro del recuadro:
   - ✅ selecciona todos los usuarios recuperados.
   - ❌ desmarca todos.
   - **Aceptar** confirma la operación para los seleccionados.

### Qué hace internamente

Para cada usuario seleccionado:

- establece `ZZ_USUARI.cambia_pass = 'S'`;
- limpia sus intentos fallidos registrados en `ZZ_INTENTOS`;
- no asigna una contraseña temporal común;
- no ejecuta directamente el cambio de contraseña del login SQL.

En el siguiente ingreso, el sistema detecta la marca y muestra:

> Debe cambiar su contraseña...

Luego desconecta al usuario y abre la pantalla para que establezca una nueva contraseña.

### Diferencia con “Blanqueo pass”

- **Cambiar password:*** obliga al usuario a elegir una contraseña nueva en el próximo acceso.
- **Blanqueo pass:*** reemplaza la contraseña por una clave temporal, normalmente `inicio` o la configurada como clave compleja.

Por lo tanto, para exigir una renovación masiva sin comunicar una contraseña común, corresponde utilizar **“Cambiar password”**. No aplica a usuarios de API ni a instalaciones configuradas con Active Directory.

## 1. Login normal del sistema

Para los usuarios del aplicativo de escritorio, la clave principal se registra como contraseña de un **login de SQL Server**.

Al ingresar:

1. La pantalla carga el usuario y la clave en `SQLCA.LogId` y `SQLCA.LogPass`.
2. Ejecuta `CONNECT`.
3. SQL Server valida las credenciales.
4. Después del ingreso, el sistema consulta `ZZ_USUARI` para verificar vigencia, permisos y `cambia_pass`.

Es decir, el login normal **no recupera ni compara una contraseña guardada en texto en `ZZ_USUARI`**: la autenticación la realiza SQL Server.

## 2. Información almacenada en `ZZ_USUARI`

En `CELER_PROD` están estos campos:

| Campo | Función |
|---|---|
| `usuari` | Identificador del usuario |
| `pwd` | Representación heredada utilizada solamente por algunos usuarios web |
| `pwd_encript` | Hash SHA-1 de la contraseña utilizada por accesos web y validaciones complementarias |
| `cambia_pass` | Indica si debe cambiar la contraseña en el próximo ingreso |
| `tipo` | Define el tipo de usuario |
| `vigdes` / `vighas` | Vigencia del usuario |
| `baja_fecha` | Indica si fue dado de baja |

TRUNK genera el hash mediante:

```sql
HASHBYTES('SHA1', LTRIM(RTRIM(@prm_pass_cruda)))
```

El resultado es un valor binario, no la contraseña original.

## 3. Validación de usuarios web

Los procedimientos web, como:

- `ars_usuario_pass_valido`
- `crs_usuario_pass_valido`

realizan este proceso:

1. Reciben la clave ingresada.
2. Calculan su hash SHA-1.
3. Comparan ese resultado con `ZZ_USUARI.pwd_encript`.

La contraseña original no necesita recuperarse para realizar la validación.

## 4. Cambio de contraseña

Cuando un usuario tradicional cambia la clave:

1. El sistema comprueba la clave anterior intentando conectarse a SQL Server.
2. Cambia la contraseña real del login mediante `sys.sp_password`.
3. Actualiza `ZZ_USUARI.pwd_encript`.
4. Coloca:

```text
cambia_pass = [SECRETO REDACTADO]
```

Así se mantienen coordinadas la contraseña del motor y la información complementaria del aplicativo.

## 5. Recuperación o blanqueo

Las contraseñas **no se pueden recuperar ni visualizar en texto original**:

- SQL Server no permite leer la contraseña de un login.
- `pwd_encript` es un hash de una sola vía.
- Un hash SHA-1 no se “desencripta”.

Cuando el usuario olvida su clave, el sistema realiza un **blanqueo**:

1. Asigna una contraseña temporal nueva.
2. Actualiza el login de SQL Server.
3. Actualiza `pwd_encript`.
4. Marca:

```text
cambia_pass = [SECRETO REDACTADO]
```

En el próximo ingreso, el usuario debe usar la clave temporal y luego definir una nueva.
