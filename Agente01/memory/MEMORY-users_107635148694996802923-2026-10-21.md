### 1. Validación previa obligatoria

Antes de impactar deben identificarse todos los comprobantes afectados desde la fecha de aplicación y validarse las exclusiones que el cliente mantiene:

- acuerdos de pago pendientes;
- ajustes débito/crédito sin facturar;
- notas débito o crédito emitidas;
- comprobantes con conceptos de Seguros;
- facturas de Pronto Pago;
- comprobantes que técnicamente no puedan revertirse;
- contratos agrupados que no puedan refacturarse conjuntamente.

```text

No cambiar el corte
No reversar parcialmente
Enviar a gestión manual
Informar el motivo y comprobantes involucrados
```

Esto debe ocurrir antes del impacto. No sería seguro cambiar el corte y descubrir posteriormente que la factura no puede reversarse.

```text
No se revierte únicamente el contrato con la novedad.
```

## Tratamiento de los saldos

### Factura sin pagar

```text
Reversar deuda original
→ refacturar con el nuevo corte
→ queda pendiente la nueva factura
```

### Factura parcialmente pagada

```text
Registrar el recaudo aplicado
→ reversar la factura
→ liberar o trasladar contablemente la aplicación
→ emitir la nueva factura
→ reaplicar el recaudo hasta el valor disponible
```

El saldo remanente queda pendiente en la nueva factura.

### Factura totalmente pagada

```text
Reversar la factura
→ el pago queda temporalmente como crédito disponible
→ emitir la nueva factura
→ reaplicar el crédito a la nueva deuda
```

Si el nuevo importe es igual:

```text
Nueva factura queda cancelada
```

Si es mayor:

```text
Se aplica el crédito
→ queda saldo pendiente
```

Si es menor:

```text
Se cancela la nueva factura
→ la diferencia queda como saldo a favor
```

### Saldo vencido

Si la nueva definición dispone **No validar**, el saldo vencido no bloquea. Pero la deuda no puede eliminarse:

```text
Reversar comprobante original
→ refacturar el mismo período
→ trasladar/reaplicar pagos
→ conservar como vencido el saldo que corresponda
```

Debe definirse si la nueva factura conserva la fecha de vencimiento original. Recomiendo conservarla para no rejuvenecer artificialmente una deuda vencida.

### Saldo a favor

No bloquea, pero debe conservarse:

```text
Reversión
→ nueva facturación
→ aplicar saldo a favor
→ conservar remanente si excede la nueva deuda
```

## 5. Refacturación con el nuevo corte

La refacturación debe partir del inventario de la reversión y considerar:

- todos los contratos de la factura revertida;
- todos los períodos anulados;
- nuevo corte para el contrato de la solicitud;
- configuración vigente de los demás contratos;
- proporcionalidad correspondiente;
- conceptos, impuestos y vencimientos recalculados;
- agrupación correcta de los contratos.

No debe limitarse al contrato que cambió el corte.

```text
Factura agrupada original
├── Contrato A con cambio de corte

└── Contrato C sin novedad

→ recalcular A con corte nuevo

```

1. Recuperar los recaudos y créditos registrados en el inventario.
2. Aplicarlos a los nuevos comprobantes.
3. Respetar contrato, responsable pagador y orden de antigüedad.
4. No crear un nuevo RC para representar el mismo dinero.
5. Conservar la trazabilidad:
   ```text
   recibo original
   aplicación anterior
   reversión
   factura nueva
   aplicación nueva
   ```
6. Dejar como saldo a favor cualquier excedente.

- reversar inmediatamente después del impacto;
- refacturar todos los contratos incluidos en la factura revertida.

## Inconsistencias o problemas posibles

### 1. Factura ya pagada

Si se revierte una factura pagada:

```text
Factura pagada
→ reversión
→ pago queda como crédito o recibo disponible
→ nueva factura
→ reaplicación del pago
```

Si no se define la reaplicación, puede quedar:

- una nueva factura pendiente;
- un saldo a favor incorrecto;
- un recibo sin aplicar;
- doble deuda;
- pago aplicado al contrato o período equivocado.

La matriz dice “no validar saldos”, pero no define cómo trasladar los pagos.

### 2. Factura parcialmente pagada

Puede ocurrir que:

```text
Factura original: 100
Pago aplicado:      60
Nueva factura:     120
```

El sistema debe dejar:

```text
Pago reaplicado: 60
Saldo pendiente: 60
```

Si no se controla, la reversión podría eliminar la aplicación original sin reconstruirla.

### 3. Saldo a favor

Si el contrato tiene crédito:

```text
Saldo a favor antes del cambio: 80
Nueva factura:                  50
```

debe definirse si:

- se aplican 50;
- se conserva un saldo a favor de 30;
- se genera algún comprobante adicional;
- se mantiene la fecha y origen del crédito.

“No validar” no significa eliminarlo.

### 4. Facturación agrupada

Si una factura contiene:

```text
Contrato A — cambia el corte
Contrato B — no cambia
Contrato C — no cambia
```

la reversión de la factura puede afectar a los tres contratos.

El requerimiento indica que todos deben volver a facturarse. El riesgo es:

- refacturar solamente A;
- modificar incorrectamente el corte de B y C;
- generar comprobantes separados cuando antes estaban agrupados;
- perder aplicaciones de pago de los otros contratos;
- dejar diferencias en el comprobante agrupador.

Cada contrato debe conservar su configuración propia. Solo A debe tomar el nuevo corte.

### 5. Períodos superpuestos o faltantes

Al cambiar el corte pueden generarse:

- períodos duplicados;
- períodos sin facturar;
- días cobrados dos veces;
- días no cobrados;
- vencimientos fuera de secuencia;
- prorrateos incorrectos.

Debe comprobarse que la nueva facturación cubra exactamente el período que fue revertido.

### 6. Facturas de Pronto Pago

La nueva definición dice que no deben revertirse las facturas de Pronto Pago.

Pero si una factura agrupada contiene:

```text
Contrato A — factura ordinaria
Contrato B — Pronto Pago
```

no está definido si:

- se bloquea toda la factura;
- se separan los contratos;
- se revierte parcialmente;
- se gestiona todo manualmente.

Recomiendo bloquear el comprobante completo si no puede separarse con seguridad.

### 7. Notas débito/crédito

El requerimiento indica no reversar ND/NC y gestionarlas manualmente.

Esto puede dejar:

```text
Factura original revertida
Nota débito/crédito vigente
Nueva factura generada
```

El resultado podría ser un saldo incorrecto si la nota afecta el mismo período. Por eso, si existe una ND/NC relacionada, debería enviarse a gestión manual o bloquearse la refacturación automática.

### 8. Seguros

Si la factura contiene conceptos de Seguros, no debe revertirse automáticamente según la matriz.

Debe verificarse si el comprobante contiene conceptos mixtos:

```text
Plan de salud + Seguro
```

Si no puede separarse, el contrato debe quedar en gestión manual.

### 9. Acuerdos de pago y ajustes pendientes

Estos sí deben validarse. Si existen:

```text
No impactar
No cambiar el corte
No reversar parcialmente
Informar el motivo
```

Esto genera una diferencia importante frente a los saldos vencidos, que la nueva matriz indica no validar.

### 10. Fallas entre impacto y reversión

La nueva definición ordena:

```text
Impactar
→ reversar inmediatamente
```

Si el impacto se confirma y luego falla la reversión, queda:

```text
Cambio de corte aplicado
Factura anterior vigente
```

Si después falla la refacturación:

```text
Factura original reversada
Sin factura nueva
```

Por eso debe existir:

- una transacción única, si todo es SQL;
- o estados y compensación si intervienen procesos no transaccionales.

## Alcance de cuentas

La matriz indica que la reversión y refacturación aplican solamente para:

```text
Individual o acuerdo corporativo
→ Individual o acuerdo corporativo
```

No aplicaría automáticamente para:

```text
Individual → Colectiva
Colectiva → Individual
Colectiva → Colectiva
Colectiva/Subcuenta A → Colectiva/Subcuenta B
```

Esto debe validarse antes de iniciar el proceso. No se debería aplicar el mismo circuito a cuentas colectivas porque la factura puede contener múltiples contratos y reglas de agrupación diferentes.

- subcuenta;
- programa;
- corte actual y nuevo;

- comprobantes afectados;

- ND/NC;

- conservar los cortes originales de los demás;
- recalcular períodos y vencimientos;
- reaplicar pagos y saldos;
- verificar que no existan períodos duplicados o faltantes;
- emitir el resultado completo.

## Alternativas al cambio de corte

### Alternativa 1 — Mantener el corte actual

Es la opción de menor riesgo:

```text
→ se conserva el corte actual
→ no se reversa la factura por cambio de corte
```

El cambio de corte se realiza posteriormente mediante la operatoria manual normal.

Se puede permitir el cambio desde el próximo ciclo:

```text

→ se completa el período actual
→ el nuevo corte se aplica desde el siguiente ciclo
```

### Alternativa 3 — Generar una solicitud separada de Cambio de Corte

```text

→ mantiene corte vigente

Solicitud de Cambio de Corte
→ se procesa con la fecha permitida
→ utiliza el circuito actual de la ventana
```

Es la alternativa más compatible con la operatoria existente.

### Alternativa 4 — Reversión y refacturación automática

Es la alternativa solicitada en la nueva definición, pero requiere desarrollar:

```text
Inventario
→ impacto
→ reversión
→ refacturación agrupada
→ reaplicación de pagos
→ conciliación
```

Debe reservarse para cuentas individuales y acuerdos corporativos, excluyendo inicialmente:

- colectivos;
- Pronto Pago;
- ND/NC;
- Seguros;
- acuerdos pendientes;
- ajustes sin facturar.

## Recomendación

Para minimizar riesgo:

1. Mantener el corte actual como comportamiento predeterminado.
2. Permitir el cambio automático solo si:
   - la cuenta es individual o acuerdo corporativo;
   - no existen ND/NC, Seguros, Pronto Pago, acuerdos ni ajustes pendientes;
   - se puede reconstruir la factura completa;
   - se puede reaplicar todo pago o crédito;
   - el comprobante agrupado puede reprocesarse sin afectar inconsistencias.
3. Para los demás casos, generar resultado de **gestión manual**.
4. Considerar como primera alternativa diferir el cambio de corte al siguiente ciclo.

La mayor atención debe estar en que **“no validar saldos” no elimina la necesidad de tratarlos**. Los saldos, pagos y aplicaciones deben conservarse y reconciliarse después de la refacturación.

La facturación actual evita problemas de proporcionalidad porque el **Cambio de Corte de la ventana no suele recalcular retroactivamente una factura ya emitida**.

## Cómo funciona actualmente

El corte se trata como un parámetro del ciclo de facturación:

```text
Corte vigente
→ se mantiene para la factura ya generada
→ se registra el nuevo corte
→ el nuevo corte se utiliza en el siguiente ciclo de facturación
```

La ventana conserva o registra datos como:

```text
vto_grupo
emi_grupo
emi_modo
fecha de vigencia
```

Cuando corresponde, genera la novedad de cambio de datos de facturación —motivo `42`—. La facturación posterior utiliza el nuevo corte.

## Ejemplo

```text
Corte anterior:     15
Nuevo corte:        30
Factura vigente:    16/10 al 15/11
```

La operación actual normalmente mantiene esa factura completa con corte 15:

```text
16/10 al 15/11
→ no se divide
→ no se recalcula
→ no se modifica el valor ya facturado
```

Luego, en el próximo ciclo, el sistema utiliza el corte 30 para determinar el nuevo período y vencimiento.

Por eso no aparecen problemas de proporcionalidad: **el cambio no se aplica sobre una factura ya emitida en mitad de su período**.

## Qué cambia con el nuevo requerimiento

El nuevo requerimiento plantea:

```text
Fecha de aplicación: 01/11
Factura vigente:     16/10 al 15/11
→ reversar inmediatamente
→ refacturar con el nuevo corte
```

En ese escenario, la factura contiene días anteriores y posteriores a la fecha de aplicación:

```text
16/10 al 31/10 → corte anterior
01/11 al 15/11 → corte nuevo
```

Si se revierte toda la factura y se genera solamente una nueva con corte 30, el sistema tendría que decidir qué hacer con:

- el período `16/10–31/10`;
- el período `01/11–15/11`;
- el nuevo período `16/11–30/11`;
- el valor proporcional de cada tramo;
- la fecha de vencimiento;
- el saldo corriente;
- los pagos aplicados.

La facturación actual no tiene ese problema porque no realiza esa división retroactiva para un cambio de corte ordinario.

## Diferencia fundamental

| Operación actual de ventana | Nueva operación solicitada |
|---|---|
| Cambia el parámetro de corte | Cambia el parámetro y reconstruye facturación |
| Mantiene la factura vigente | Revierte factura vigente |
| Aplica el nuevo corte en el siguiente ciclo | Pretende aplicarlo desde la fecha de solicitud |
| No divide períodos ya facturados | Puede exigir prorratear períodos parciales |
| No mueve pagos de una factura vigente | Debe reversar y reaplicar pagos |

## Conclusión

La facturación actual no tiene problemas de proporcionalidad porque el cambio de corte se aplica como **configuración para ciclos futuros**, sin reabrir una factura vigente.

Si el nuevo proceso debe hacer:

```text
impacto inmediato
→ reversión de factura vigente
→ refacturación desde la fecha de aplicación
```

ya no se trata del mismo circuito actual de la ventana. Se necesita definir expresamente:

- períodos parciales;
- reglas de prorrateo;
- vencimientos;
- saldos corrientes;
- pagos aplicados;
- facturas agrupadas;
- fecha desde la cual rige el nuevo corte.

La alternativa más compatible con la operación vigente es:

```text
Mantener la factura actual con el corte anterior
→ aplicar el nuevo corte desde el siguiente ciclo
```

Así se reutiliza el comportamiento existente y no se introducen inconsistencias de proporcionalidad.

## 1. Cambio de corte antes de generar la factura del período

Ejemplo:

```text
Solicitud:          08/10
Factura del período: todavía no generada
```

```text
→ toma el nuevo corte
→ lo registra en los datos de facturación
→ genera la novedad de Cambio de Datos de Facturación, motivo 42
→ la próxima facturación utiliza el corte 30
```

No hay reversión ni prorrateo porque todavía no existe una factura para ese período.

## 2. Cambio de corte en el mismo período, pero con factura ya generada

Ejemplo:

```text
Corte actual:       15
Factura generada:   16/10 al 15/11
Nuevo corte:        30
Solicitud:          01/11
```

La factura ya contiene el período afectado. La ventana actual no divide automáticamente esa factura ni recalcula parcialmente los días.

```text
→ bloquear la aceptación
→ exigir reversión o gestión previa
```

1. compara el corte vigente con el nuevo;
2. verifica si la cuenta/subcuenta permite modificarlo;
3. guarda el nuevo `vto_grupo`;
4. si corresponde, genera la novedad de cambio de datos de facturación;
5. mantiene las validaciones actuales de cartera y facturación.

Si existe facturación futura, la regla actual puede impedir aceptar la solicitud hasta que la situación se regularice.

```text
→ se registra la novedad 42
→ el nuevo corte queda disponible para la facturación posterior
```

```text
→ cambiar el corte
→ refacturar
→ reaplicar el pago
```
