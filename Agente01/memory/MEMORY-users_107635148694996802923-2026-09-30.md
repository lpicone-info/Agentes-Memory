### [30/09/2026 10:42:47] Agente

En **Presmed**, `vigen_desde` indica desde qué fecha comienza a aplicar una configuración o relación. No existe un único `vigen_desde`: aparece en convenios, copagos, valores, prestadores, reintegros, afiliado-prestador, etc.

La regla habitual es:

```sql
vigen_desde = (
    SELECT MAX(vigen_desde)
    FROM tabla
    WHERE vigen_desde <= fecha_del_proceso
      AND baja_fecha IS NULL
)
```

Es decir, Presmed:

1. Toma la fecha del proceso: prestación, autorización, receta, expediente, etc.
2. Descarta vigencias futuras.
3. Busca la vigencia más reciente anterior o igual a esa fecha.
4. Verifica además que el registro no esté dado de baja.

### Ejemplo

Existen estos valores de copago:

| `vigen_desde` | Valor |
|---|---:|
| 01/01/2026 | 10.000 |
| 01/07/2026 | 15.000 |
| 01/10/2026 | 20.000 |

Para una prestación del `15/09/2026`, Presmed selecciona:

```text
01/07/2026 → 15.000
```

La vigencia del `01/10/2026` todavía no aplica.

### Importante

- `vigen_desde` no es la fecha de creación del registro.
- Puede cargarse una vigencia futura.
- Una nueva vigencia no necesariamente modifica la anterior: se agrega otra versión.
- Para fechas posteriores, la nueva versión reemplaza funcionalmente a la anterior.
- `baja_fecha` determina si el registro fue anulado o dejó de estar disponible.
- Algunas tablas también tienen `vigen_hasta`; en ellas debe cumplirse el intervalo completo.

Ejemplo de selección de copago: [d_prestad_copa_x_prestac.srd](/home/luispicone/.openclaw/workspace/svn/svarela-Coomeva-trunk/exe_presmed/Source%20Infomedical/d_prestad_copa_x_prestac.srd:19).

Ejemplo de reintegros: [uo_nv_valdatos.sru](/home/luispicone/.openclaw/workspace/svn/svarela-Coomeva-trunk/exe_presmed/Source%20Infomedical/uo_nv_valdatos.sru:2475).

Para determinar el comportamiento exacto necesito la **pantalla o tabla específica**, porque la fecha de comparación cambia según el proceso.

### Resumen del [RM 30339](https://redmine.infomedical.com.ar/issues/30339)

**Problema:** Presmed determina incorrectamente el programa principal vigente cuando un afiliado realiza un **cambio de cobertura** y el contrato tiene un día de corte diferente de 30.

Actualmente, la nueva cobertura puede considerarse vigente desde la fecha de aplicación, aunque funcionalmente debe comenzar **el día posterior al corte contractual**.

**Ejemplo, corte día 15:**

- Programa anterior vigente hasta `15/09/2026`.
- Programa nuevo vigente desde `16/09/2026`.
- Las autorizaciones anteriores al día 16 deben evaluarse usando el programa anterior.

Aplica tanto para:

- incremento de cobertura;
- disminución de cobertura;
- contratos cuyo día de corte cambió históricamente.

### Alcance

Debe corregirse la determinación de cobertura en Presmed para:

- Ambulatorio
- Cirugía
- Hospitalización
- IVR
- GIS

No incluye:

- programas anexos;
- facturación;
- cálculos tarifarios.

### Causa funcional

Se está usando la fecha de aplicación sin calcular correctamente la **fecha efectiva**, considerando:

```text
fecha efectiva = día siguiente al corte contractual vigente
```

Además, el corte no debe considerarse fijo: debe recuperarse el corte que estaba vigente para el contrato en el momento correspondiente.
