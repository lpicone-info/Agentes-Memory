## Redmine 28090 - Analisis inicial de `afs_reporte_pronto_pago`

Repo/contexto usado:
`/home/luispicone/.openclaw/workspace/coomeva-afilmed-trunk-srmontenegro`

SP wrapper analizado:
`backend/procedures/afs_reporte_pronto_pago.sql`

Funcionamiento principal:
- `afs_reporte_pronto_pago` deriva segun `@prm_tipo_reporte` a 4 SPs hijos:
  - `0` -> `afs_reporte_0_pronto_pago`
  - `1` -> `afs_reporte_1_pronto_pago`
  - `2` -> `afs_reporte_2_pronto_pago`
  - `3` -> `afs_reporte_3_pronto_pago`
- El llamado viene desde PowerBuilder por DataWindows `d_afs_reporte_0/1/2/3_pronto_pago`, cambiando `DataObject` segun tipo de reporte.

Hallazgos iniciales:
1. Bug probable en reporte tipo `0`: `afs_reporte_0_pronto_pago.sql` recibe `@prm_ente`, pero filtra fijo `AND C.ente = 1`. Las ramas `1`, `2` y `3` usan `AND C.ente = @prm_ente`. Esto puede devolver datos incorrectos o vacios si se consulta otro ente.
2. El wrapper no tiene `ELSE`; si `@prm_tipo_reporte` viene `NULL` o fuera de `0..3`, no devuelve resultset ni error claro. En PB puede verse como reporte vacio o fallo ambiguo.
3. Los parametros `@prm_filtro_cuenta` y `@prm_filtro_subcta_tipos` llegan al wrapper y a los hijos, pero los hijos parecen usar siempre filtro activo fijo con `'S','L'`. Requiere confirmacion funcional.
4. Inconsistencia de filtro por fecha: reportes `0`, `1`, `2` usan `C.fecha_emision <= @prm_fecha_hasta`, mientras reporte `3` usa en partes `C.fecha_emision < DATEADD(DAY,1,@prm_fecha_hasta)`. Si PB manda `fecha_hasta` a `00:00:00`, los reportes `0/1/2` pueden excluir comprobantes del mismo dia con hora posterior a medianoche.
5. En reporte tipo `3`, se arma universo con lineas `PP` y `OF`, pero el SELECT final filtra solo `WHERE C.tipo_linea = 'OF'`. Puede ser correcto si el reporte 3 es solo OF, pero es punto funcional fuerte a validar.
6. Reporte tipo `3` contiene muchos `RAISERROR (..., 0, 1) WITH NOWAIT`; no corta ejecucion, pero puede ensuciar salida/logs y afectar batch/PB segun conexion.

Recomendacion dada al usuario:
- Si el problema de Redmine 28090 afecta tipo `0`, primer candidato: `C.ente = 1` hardcodeado.
- Si el problema es diferencia de cantidades entre reportes o rangos de fechas, segundo candidato: manejo inconsistente de `fecha_hasta`.
