## Qué hace `afi_insertar_soli_auto`

El dispatcher recibe el XML, valida los datos y deriva según `soli_moti`.

Para **venta nueva (`soli_moti = 1`)**:

```sql
EXEC dbo.afi_insertar_soli_auto_venta_nueva
    @var_data_xml = @var_data_xml,
    @prm_id_proceso = @var_id_proceso OUTPUT

EXEC dbo.afu_genera_soli_auto_app
    @prm_id_proceso = @var_id_proceso
```

Para **inclusión (`soli_moti = 2`)**:

```sql
EXEC dbo.afi_insertar_soli_auto_inclusion
    @var_data_xml = @var_data_xml,
    @prm_id_proceso = @var_id_proceso OUTPUT

EXEC dbo.afu_genera_soli_auto_app
    @prm_id_proceso = @var_id_proceso
```

Antes de llamar a `afu_genera_soli_auto_app`, controla que el SP específico haya devuelto un `id_proceso`. Si no lo devuelve, aborta:

```sql
IF @var_id_proceso IS NULL
BEGIN
    RAISERROR(...)
    RETURN -1
END
```

Por lo tanto, la consideración técnica es:

> Después de insertar la solicitud automática, se obtiene su `id_proceso` y se genera inmediatamente su cabecera GMS, pero solamente para esa solicitud.

## Por qué se agregó

La llamada fue incorporada durante estos cambios:

- Revisión **37809** — Redmine **30345**, integración de venta nueva con GMS.
- Revisión **37849** — Redmine **30346**, integración de inclusiones con GMS.

En esas revisiones se agregó:

1. El retorno de `id_proceso` desde los SP de venta nueva e inclusión.
2. La ejecución inmediata de:

```sql
afu_genera_soli_auto_app @prm_id_proceso = ...
```

La intención aparente fue que la solicitud quedara preparada en GMS inmediatamente después de ingresar por el dispatcher, sin esperar a que el batch recorriera posteriormente todas las solicitudes pendientes.

## Qué hace el batch

El batch de solicitudes también ejecuta:

```powerscript
IF ls_tipo_proceso = 'AU' THEN
    wf_genera_soli_auto_app()
END IF
```

Y esa función llama:

```sql
EXEC dbo.afu_genera_soli_auto_app
```

sin informar `id_proceso`.

En ese caso, `afu_genera_soli_auto_app` procesa en forma masiva todos los registros pendientes de `SOLI_AUTO_CONTRATO`.

La diferencia es:

| Ejecución | Alcance |
|---|---|
| Desde `afi_insertar_soli_auto` | Solo el `id_proceso` recién insertado |
| Desde el batch | Todos los procesos automáticos pendientes |

## ¿La doble llamada genera duplicación?

En principio no, porque `afu_genera_soli_auto_app` tiene esta protección:

```sql
NOT EXISTS (
    SELECT 1
    FROM GMS_CAB G
    WHERE G.id_soli_externa = C.id_soli_externa
)
```

Si el dispatcher ya generó la cabecera `GMS_CAB`, cuando el batch vuelva a ejecutar el SP esa solicitud ya no cumple la condición y no se procesa nuevamente.

## Qué solicitudes tienen este comportamiento

La llamada interna existe actualmente para:

- `soli_moti = 1`: venta nueva.
- `soli_moti = 2`: inclusión.

No se realiza para:

- `soli_moti = 6`: cambio de cobertura.
- `soli_moti = 16`: cambio de fecha de antigüedad.
- `soli_moti = 48`: traslado de contrato existente.

Esto muestra que la llamada no es una regla general para toda solicitud automática; fue incorporada específicamente en los desarrollos de integración GMS de venta nueva e inclusiones.

## Conclusión

La consideración tomada parece haber sido:

> Garantizar que las solicitudes de venta nueva e inclusión, una vez insertadas por API, generen inmediatamente su cabecera y agenda GMS asociada.

Sin embargo, desde el diseño original documentado, el flujo previsto era:

1. `afi_insertar_soli_auto` inserta la solicitud automática.
2. El batch ejecuta `afu_genera_soli_auto_app`.
3. Luego el batch continúa con la generación definitiva de la solicitud.

Por eso actualmente hay **dos posibles puntos de invocación**:
