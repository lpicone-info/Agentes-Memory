## 7. Manejo de transacciones, errores y reintentos

### Impacto OK + comprobante OK

- Confirmar impacto.
- Ejecutar etapa de primera cuota.
- Confirmar generación.
- Resultado final `R`, salvo otros errores del proceso.

### Impacto OK + comprobante ERROR

- Mantener confirmado el impacto.
- Hacer rollback únicamente de la etapa de valorización/generación.
- Registrar el error en `GMS_ERR`.
- Dejar el proceso como `O` cuando existe una solicitud impactada correctamente.
- Habilitar reproceso exclusivo de primera cuota.

**Recomendación:** opción **B**, implementada como una etapa post-impacto explícita.

### Comprobante ya existente

- Buscar por `soli` y `baja_fecha IS NULL`.
- No ejecutar `afi_compro_primera_cuota`.
- Devolver `YA_EXISTENTE` con el identificador actual.
- Tratarlo como resultado idempotente exitoso, no como error.

### Reproceso de una solicitud

- No volver a ejecutar el impacto.
- Reintentar solamente valorización/generación.
- Antes de generar, repetir la verificación idempotente.
- Si otro proceso ya generó el comprobante, finalizar como `YA_EXISTENTE`.

### Error previo al impacto

- Mantener el comportamiento actual.
- No ejecutar valorización ni generación.
- Aplicar el rollback existente cuando corresponda.

### Prevención de duplicados

El criterio funcional confirmado es:

```text
soli = solicitud
baja_fecha IS NULL
```

Pero debe complementarse con:

- bloqueo transaccional sobre la solicitud/comprobante;
- verificación y generación dentro de la misma transacción;

El DDL actual sólo garantiza unicidad por:

- `ente + compro_tipo + compro_nro`;

No garantiza un único registro activo por `soli`.

Puede existir más de un comprobante histórico por solicitud. El flujo manual da de baja el vigente y crea uno nuevo. El automático no debe utilizar esa regeneración como comportamiento de reintento.
