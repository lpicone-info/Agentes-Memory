### [25/09/2026 11:11:28] Agente

En SQL Server, dentro del SP **B no existe una función nativa confiable que devuelva “mi caller inmediato es el SP A”**.

### Lo que sí podés consultar

```sql
SELECT @@NESTLEVEL
```

En un caso simple:

- `EXEC B` directamente → dentro de B suele valer `1`.
- `EXEC A`, y A ejecuta B → dentro de B suele valer `2`.

Esto permite detectar que existe anidamiento, pero **no identifica al SP A**. Además, otros wrappers, triggers o SQL dinámico también aumentan el nivel, por lo que no sirve como regla funcional robusta.

```sql
SELECT OBJECT_NAME(@@PROCID)
```

Solo devuelve el procedimiento actual, es decir, **B**.

### Alternativa recomendable

Hacer explícito el origen:

```sql
CREATE PROCEDURE dbo.B
    @prm_origen VARCHAR(30) = 'DIRECTO'
AS
BEGIN
    IF @prm_origen = 'SP_A'
    BEGIN
        -- Lógica correspondiente
    END
END
```

Y desde A:

```sql
EXEC dbo.B
    @prm_origen = 'SP_A'
```

Otra posibilidad es que A establezca `SESSION_CONTEXT`:

```sql
EXEC sys.sp_set_session_context
    @key = N'origen_ejecucion',
    @value = N'SP_A'

EXEC dbo.B
```

Dentro de B:

```sql
SELECT SESSION_CONTEXT(N'origen_ejecucion')
```

Pero hay que limpiar el valor después y manejar errores cuidadosamente porque las conexiones suelen reutilizarse mediante pooling.

### Si se necesita garantizar que B solo sea ejecutado por A

La solución correcta no es detectar el caller, sino controlar permisos:

- quitar a los usuarios el permiso de ejecutar B;
- otorgar permiso solamente sobre A;
- permitir que A llegue a B mediante la cadena de propiedad, `EXECUTE AS` o firma de módulos.

### Para diagnóstico

Extended Events puede registrar la secuencia A → B y reconstruir la pila de ejecución. Sirve para investigar qué ocurrió, pero no es una condición que B deba utilizar durante su funcionamiento normal.

**Conclusión:** `@@NESTLEVEL` puede diferenciar aproximadamente ejecución directa de anidada, pero no confirma que el caller sea A. Para una regla funcional, conviene pasar un parámetro explícito; para seguridad, restringir permisos sobre B.

Hay que verificar si el usuario utilizado por el servicio tiene alguno de estos permisos amplios:

- usuario real de conexión del servicio;
- roles de base de datos a los que pertenece;
- permisos directos e indirectos;
- si pertenece a `db_owner`;
- si el login es `sysadmin`.

## Wrapper `saludmp`

Actualmente existe:

```sql

```

y ese wrapper llama directamente al SP interno. Para cerrar correctamente el circuito se necesitan las dos modificaciones:

1. El wrapper debe llamar a:

```sql
dbo.afi_insertar_soli_auto
```

2. El usuario del servicio debe perder acceso directo a:

```sql
dbo.afi_insertar_soli_auto_traslado_existente
```

De esa manera, aunque otra operación del servicio intente ejecutar el SP específico, SQL Server lo rechazará.

## Opción más robusta: firma de módulo

Si se quiere una autorización explícita y auditable independiente de la cadena de propiedad, puede utilizarse un certificado:

- el usuario del servicio solo tiene permiso sobre el dispatcher;
- se firma `afi_insertar_soli_auto`;
- el usuario asociado al certificado recibe permiso sobre los procedimientos internos;
- el permiso adicional existe únicamente mientras se ejecuta el dispatcher firmado.

Es más seguro y explícito, pero tiene mayor costo operativo: cada `ALTER PROCEDURE` del dispatcher elimina la firma y obliga a firmarlo nuevamente.

## Recomendación para este desarrollo

Usaría inicialmente:

- dispatcher como único punto público;
- `DENY EXECUTE` específico sobre todos los SP internos;
- `GRANT EXECUTE` solamente sobre el dispatcher;
- llamada interna estática, sin SQL dinámico;
- validación con el usuario real del servicio.

Esto es mucho más robusto que `@@NESTLEVEL`, parámetros de origen o `SESSION_CONTEXT`, porque la garantía la aplica el motor de permisos de SQL Server.
