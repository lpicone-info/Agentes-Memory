Analisis tecnico - SP Consulta de Integrantes de un Contrato
Datos de referencia
•	Requerimiento: R29154 / Mantis 11367
•	Procedimiento analizado: afs_consulta_integrantes_contrato
•	Documento funcional revisado: A-04-DEF SPs de Consultas y Validaciones por Contrato_V05.docx
•	Punto funcional revisado: 4.1. SP: Consulta de Integrantes de un Contrato
•	Profile de base usado para validacion: PruebasCoreINFOMEDICAL
•	Caso de analisis: contrato 1005124
•	Fecha del analisis: 2026-05-27
Alcance
El objetivo del analisis fue revisar el comportamiento de los campos valor_tarifa_anexo y valor_tarifa_programa del procedimiento afs_consulta_integrantes_contrato, contrastando lo definido en el DEF contra el comportamiento observado para el contrato 1005124.
El caso reportado indica que para el periodo 05/2026 el contrato tiene dos comprobantes facturados: el primero contiene los integrantes 01, 02 y 03; el segundo corresponde al integrante 04, generado por una inclusion posterior. Al ejecutar el procedimiento, los integrantes 01, 02 y 03 informan valores 0.00, mientras el integrante 04 informa valor.
Evidencia funcional del DEF
En el punto 4.1. SP: Consulta de Integrantes de un Contrato, el DEF establece que los valores tarifarios deben consultarse desde el ultimo comprobante facturado al contrato, vigente y no reversado.
Para valor_tarifa_anexo, el DEF indica que debe devolver el valor de las tarifas aplicadas al integrante por programas anexos, tomando PREFACTURAS.impor cuando PREFACTURAS.factu_concep = 'ADI'.
Para valor_tarifa_programa, el DEF indica que debe devolver el valor de la tarifa aplicada al integrante para el programa del contrato, tomando PREFACTURAS.impor cuando PREFACTURAS.factu_concep <> 'ADI'.
El mismo punto del DEF tambien aclara que se toma PREFACTURAS porque ahi se encuentra detallado el valor por integrante.
Evidencia tecnica del SP compilado
La definicion compilada del procedimiento calcula una unica prefacturacion global para todo el contrato mediante una variable equivalente a @v_ult_prefac.
La logica actual selecciona el mayor prefac_cab del contrato que tenga comprobante emitido y no reversado. Luego, para cada integrante, calcula tarifas filtrando por ese mismo prefac_cab global.
Fragmento logico relevante:
SELECT TOP 1 @v_ult_prefac = P.prefac_cab
FROM PREFACTURAS P WITH (NOLOCK)
WHERE P.contra = @prm_contrato
 AND EXISTS (
 SELECT 1
 FROM COMPROBANTES C WITH (NOLOCK)
 WHERE C.prefac_cab = P.prefac_cab
 AND C.contra = P.contra
 AND NOT EXISTS (
 SELECT 1
 FROM COMPRO_REVERSO_DET R WITH (NOLOCK)
 WHERE R.compro_tipo = C.compro_tipo
 AND R.compro_nro = C.compro_nro
 )
 )
ORDER BY P.prefac_cab DESC
Luego el calculo tarifario queda acoplado a esa prefacturacion global:
FROM PREFACTURAS WITH (NOLOCK)
WHERE contra = A.contra
 AND inte = A.inte
 AND prefac_cab = @v_ult_prefac
En la version compilada se observo ademas que para valor_tarifa_programa se aplica impor * debe_haber, lo cual explica el valor neto informado para el integrante 04.
Reproduccion del caso contrato 1005124
La ejecucion del procedimiento afs_consulta_integrantes_contrato para el contrato 1005124 devuelve cuatro integrantes activos.
Resultado observado para los campos tarifarios:
Inte	valor_tarifa_anexo	valor_tarifa_programa	total_tarifa
01	0.00	0.00	0.00
02	0.00	0.00	0.00
03	0.00	0.00	0.00
04	0.00	205600.00	205600.00
Para el mismo contrato, la evidencia de facturacion del periodo 05/2026 muestra dos prefacturaciones vigentes/no reversadas:
prefac_cab	periodo	integrantes incluidos
1345710	05/2026	01, 02, 03
1358226	05/2026	04
La logica actual del SP toma 1358226 como ultimo prefac_cab global del contrato. Por esa razon, al consultar tarifas de los integrantes 01, 02 y 03, no encuentra registros en PREFACTURAS para esos integrantes dentro de 1358226, y devuelve 0.00.
Valores existentes en PREFACTURAS para el ultimo periodo
La informacion tarifaria de los integrantes 01, 02 y 03 existe en PREFACTURAS, pero asociada al prefac_cab 1345710, que pertenece al mismo periodo facturado 05/2026.
Con el criterio de ultimo periodo facturado y ultima prefacturacion aplicable por integrante, los valores quedan:

01	1345710	0.00	342700.00	342700.00
02	1345710	0.00	538200.00	538200.00
03	1345710	0.00	1054500.00	1054500.00
04	1358226	0.00	205600.00	205600.00
Causa raiz
La causa raiz es que el procedimiento interpreta ultimo comprobante facturado al contrato como un unico prefac_cab global para todo el contrato.
Ese criterio no cubre el escenario en el que el ultimo periodo facturado tiene mas de un comprobante o prefacturacion vigente/no reversada, especialmente cuando existe una inclusion posterior que genera una nueva factura solo para el integrante incluido.
En ese escenario, el ultimo prefac_cab global representa correctamente al integrante incluido posteriormente, pero no representa a los integrantes que fueron facturados previamente dentro del mismo periodo.
Recomendacion funcional
Se recomienda precisar el criterio funcional de esta forma:
Para los campos valor_tarifa_anexo y valor_tarifa_programa, se debe tomar el ultimo periodo facturado vigente/no reversado del contrato y, dentro de ese periodo, consultar para cada integrante la ultima prefacturacion/comprobante vigente/no reversado que tenga detalle en PREFACTURAS para ese integrante.
Este criterio conserva la idea funcional de ultimo comprobante facturado, pero evita perder valores cuando dentro del mismo periodo existen comprobantes separados por inclusiones posteriores.
Recomendacion tecnica para el SP
La modificacion sugerida es eliminar el uso de @v_ult_prefac como prefacturacion unica global para el calculo de tarifas y reemplazarlo por una seleccion de prefac_cab aplicable por integrante.
La estructura sugerida es:
1.	Determinar el ultimo periodo facturado vigente/no reversado del contrato.
2.	Para cada integrante A.inte, buscar dentro de ese periodo el ultimo prefac_cab vigente/no reversado donde exista detalle en PREFACTURAS para ese integrante.
3.	Calcular valor_tarifa_anexo y valor_tarifa_programa usando ese prefac_cab especifico del integrante.
Fragmento conceptual sugerido:
OUTER APPLY (
 SELECT TOP 1
 P2.prefac_cab
 FROM PREFACTURAS P2 WITH (NOLOCK)
 INNER JOIN PREFACTURAS_CAB PC2 WITH (NOLOCK)
 ON PC2.prefac_cab = P2.prefac_cab
 WHERE P2.contra = A.contra
 AND P2.inte = A.inte
 AND PC2.factu_perio = (
 SELECT MAX(PC3.factu_perio)
 FROM PREFACTURAS P3 WITH (NOLOCK)
 INNER JOIN PREFACTURAS_CAB PC3 WITH (NOLOCK)
 ON PC3.prefac_cab = P3.prefac_cab
 WHERE P3.contra = A.contra
 AND EXISTS (
 SELECT 1
 FROM COMPROBANTES C3 WITH (NOLOCK)
 WHERE C3.prefac_cab = P3.prefac_cab
 AND C3.contra = P3.contra
 AND C3.baja_fecha IS NULL
 AND NOT EXISTS (
 SELECT 1
 FROM COMPRO_REVERSO_DET R3 WITH (NOLOCK)
 WHERE R3.compro_tipo = C3.compro_tipo
 AND R3.compro_nro = C3.compro_nro
 )
 )
 )
 AND EXISTS (
 SELECT 1
 FROM COMPROBANTES C2 WITH (NOLOCK)
 WHERE C2.prefac_cab = P2.prefac_cab
 AND C2.contra = P2.contra
 AND C2.baja_fecha IS NULL
 AND NOT EXISTS (
 SELECT 1
 FROM COMPRO_REVERSO_DET R2 WITH (NOLOCK)
 WHERE R2.compro_tipo = C2.compro_tipo
 AND R2.compro_nro = C2.compro_nro
 )
 )
 ORDER BY P2.prefac_cab DESC
) OA_ULT_PREFAC_INTE
Luego el calculo tarifario deberia filtrar por OA_ULT_PREFAC_INTE.prefac_cab:
OUTER APPLY (
 SELECT
 SUM(CASE WHEN factu_concep = 'ADI' THEN impor * debe_haber ELSE 0 END) AS valor_anexo,
 SUM(CASE WHEN factu_concep <> 'ADI' THEN impor * debe_haber ELSE 0 END) AS valor_cuota
 FROM PREFACTURAS WITH (NOLOCK)
 WHERE contra = A.contra
 AND inte = A.inte
 AND prefac_cab = OA_ULT_PREFAC_INTE.prefac_cab
) OA_TARIFAS
Riesgos y consideraciones
•	El cambio afecta solo el origen de prefac_cab usado para calcular tarifas por integrante.
•	Debe validarse con contratos que tengan un unico comprobante en el ultimo periodo para confirmar que el resultado se mantiene igual.
•	Debe validarse con contratos que tengan mas de un comprobante en el ultimo periodo, especialmente inclusiones posteriores.
•	Debe confirmarse funcionalmente si el criterio correcto es ultimo periodo facturado con prefactura por integrante, porque el DEF original no explicita este escenario.
•	El calculo con debe_haber debe preservarse si se desea mantener el comportamiento neto actualmente compilado para conceptos con descuentos o movimientos negativos.
Validaciones ejecutadas

Conclusion
El comportamiento observado para el contrato 1005124 es consistente con la implementacion actual del SP, pero no cubre correctamente el caso funcional de multiples comprobantes en el mismo periodo para integrantes distintos.
La solucion recomendada es cambiar el calculo tarifario para que use el ultimo periodo facturado del contrato y determine el prefac_cab aplicable por integrante dentro de ese periodo. Con esa modificacion, los integrantes 01, 02, 03 y 04 recuperan los valores tarifarios correspondientes al periodo 05/2026 sin perder el criterio de comprobante vigente/no reversado.
