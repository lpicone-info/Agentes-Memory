## Pronto Pago ya pagado + cambio de cobertura

**No se recalcula automáticamente el Pronto Pago pagado.**

El proceso de reversión/refacturación de la solicitud automática selecciona únicamente comprobantes cuyo tipo tiene:

```sql
COMPRO_TIPOS.prontopago = 'N'
```

Por lo tanto, excluye los comprobantes de Pronto Pago (`prontopago = 'S'`).

### Resultado

| Situación | Comportamiento actual V104 |
|---|---|
| Pronto Pago no pagado | No se revierte automáticamente por este circuito |
| Pronto Pago pagado | No se recalcula ni se genera uno nuevo |
| Cambio de cobertura | Se aplica para facturaciones posteriores |
| Pago ya aplicado | No se libera ni se reaplica automáticamente |
| Nueva cobertura en el mismo período | El PP original puede quedar asociado a la condición anterior |

El reporte de Pronto Pago identifica los pagos mediante `PRONTOPAGO_PAGADO`, pero eso no significa que el circuito de cambio de cobertura tenga implementada la reversión y reaplicación del pago.

## Qué requeriría recalcularlo correctamente

Para modificar un Pronto Pago ya pagado se necesitaría un circuito específico que:

1. Revierta el comprobante original y su descuento.
2. Libere el pago o crédito aplicado.
3. Recalcule la factura con la nueva cobertura.
4. Calcule nuevamente el descuento de Pronto Pago.
5. Genere el nuevo Pronto Pago, si corresponde.
6. Reaplique el importe pagado.
7. Controle diferencias, saldo a favor o saldo pendiente.

Ese circuito completo **no está implementado en la V104 entregada**.

### Conclusión

> Si el Pronto Pago ya fue pagado y posteriormente se cambia la cobertura, la V104 no lo recalcula automáticamente. El Pronto Pago original permanece sin modificación y la nueva cobertura impacta en las facturaciones posteriores.

La conclusión se basa en el código entregado, particularmente en `afu_soli_auto_app_fact_rev_incluir.sql`, donde se excluyen los comprobantes parametrizados como Pronto Pago.

| `ERROR_FACTURACION` | Final fallido parcial | La solicitud fue grabada, pero falló la facturación |
| `PROCESADA` | Final exitoso | Finalizaron generación y procesamiento económico sin errores registrados |

## Clasificación recomendada para el aplicativo

### Final exitoso completo

```text
PROCESADA
```

Significa:

```text
Solicitud grabada
+ reversión/facturación finalizada
+ sin errores detectados
```

### Final exitoso sin facturación

```text
FACTURACION_OMITIDA
```

Debe evaluarse junto con:

```text
mensaje_facturacion
```

Puede significar:

- contrato colectivo;
- no había acción económica pendiente;
- no correspondía reversión/refacturación automática.

Para `soli_moti=49`, que corresponde a contratos colectivos, este puede ser el resultado final esperado:

```text
Solicitud impactada correctamente
+ facturación automática omitida por tratarse de un colectivo
```

No debe visualizarse automáticamente como error.

### Final fallido durante la grabación

```text
ERROR_GENERACION_SOLICITUD
GENERACION_GMS_INICIADA_SIN_FIN
```

También puede obtenerse:

```text
NO_RECIBIDA
```

si el XML fue rechazado antes de crear `SOLI_AUTO_CONTRATO`.

### Solicitud grabada, pero proceso económico fallido

```text
ERROR_REVERSION
ERROR_FACTURACION
```

Estos estados representan un resultado parcial:

```text
La solicitud puede existir o estar impactada,
pero la normalización económica no concluyó correctamente.
```

No deben tratarse como éxito integral.

### Estados transitorios

Mientras se obtenga cualquiera de estos estados, el aplicativo debe continuar consultando:

```text

PENDIENTE_GENERACION_SOLICITUD

FACTURACION_EN_PROCESO
```
