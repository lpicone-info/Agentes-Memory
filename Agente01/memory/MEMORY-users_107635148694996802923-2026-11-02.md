## Conceptos

- **SL:** comprobante de Primera Cuota generado por Afilmed.
- **RC:** recaudo recibido, normalmente seleccionado desde la administración de recaudos sin identificar.
- El ente recaudador debe tener configurada la marca `primera_cuota = 'S'` para que el RC pueda utilizarse como Primera Cuota.

## Venta Nueva

1. El botón de búsqueda se habilita cuando la cuenta/subcuenta exige Primera Cuota.
2. Se puede asociar:
   - Un **SL generado por el sistema**.
   - Un **RC** seleccionado entre recaudos sin identificar.
3. El RC debe:
   - No estar anulado.
   - No estar reintegrado.
   - No estar identificado o aplicado a otra cartera.
   - Pertenecer a un ente recaudador marcado para Primera Cuota.
4. Si existe un RC y el usuario genera un SL, el SL reemplaza al RC.
5. Si ya existe un SL y se genera otro antes de impactar la solicitud:
   - El nuevo SL reemplaza al anterior.
   - El SL anterior queda con `baja_fecha`.
   - El nuevo comprobante activo es el que tiene `baja_fecha IS NULL`.
6. Al grabar la solicitud como **Aceptada**, se actualizan los campos:

```text
recibo_compro_tipo
recibo_compro_nro
recibo_compro_letra
recibo_compro_punto
```

7. Al impactar:
   - Si el comprobante es **SL**, se valida el recaudo contra el `id_comprobante` del SL activo.
   - Si el comprobante es **RC**, se relaciona directamente el recaudo ingresado con el contrato.

## Inclusiones

El comportamiento es equivalente, con estas diferencias funcionales:

1. La búsqueda de Primera Cuota se realiza sobre el contrato existente.
2. Si el contrato es **Pospago**:
   - No se permite ingresar RC.
   - No se genera SL.
   - Se informa:  
     **“Contrato Pospago no requiere Primera Cuota. La solicitud sólo puede ser Rechazada”.**
3. Si el contrato es **Prepago** y la subcuenta exige Primera Cuota, debe existir un SL o RC para poder impactar.
4. Si la tarifa es de tipo **Categoría + Parentescos**, puede permitirse la inclusión sin SL/RC porque no es posible valorizar la Primera Cuota en ese momento.
5. También existe la excepción para inclusiones donde todos los beneficiarios sean **BB Gestante**: no es obligatorio generar SL ni registrar RC.
6. Si se utiliza RC, el documento del recaudo debe coincidir con el contratante informado en la solicitud. De lo contrario, se informa:

```text
El recaudo ingresado no corresponde al contratante
```

## Regeneración del SL

La EF posterior de regeneración establece que, mientras la solicitud no esté impactada:

- Se puede modificar la fecha de aplicación.
- Se puede generar el SL varias veces.
- El último SL reemplaza al anterior.
- Sólo debe visualizarse el SL activo, es decir, el que no tiene `baja_fecha`.
- Una vez impactada la solicitud, el SL ya no se valoriza nuevamente; sólo puede reimprimirse.
- Si la Primera Cuota corresponde a un RC, no existe un SL para reimprimir.

# 1. Descripción funcional

La solicitud permite modificar la fecha de antigüedad de uno o varios integrantes vigentes de un contrato.

También permite informar la entidad de salud anterior mediante:

```text
anter_prepa
```

El cambio puede ser:

- **Parcial:** sólo se seleccionan determinados integrantes.
- **Total:** se selecciona todo el grupo familiar mediante la opción de cambio de contrato.

La fecha modificada no se actualiza directamente desde la pantalla. Primero se genera y acepta la solicitud; luego, al impactarla, se actualiza la información definitiva del afiliado.

## Datos funcionales principales

| Dato | Descripción |
|---|---|
| Contrato | Contrato sobre el cual se solicita el cambio |
| Integrante | Integrante al que se modificará la antigüedad |
| Fecha de antigüedad | Nueva fecha solicitada |
| Entidad anterior | Prepaga o entidad anterior (`anter_prepa`) |
| Fecha de aplicación | Mes desde el cual rige la solicitud |
| Cambio de contrato | Indica si se modifica todo el grupo familiar |

# 2. Circuito manual

La ventana corresponde a:

```text
Solicitudes → Cambio de Fecha de Antigüedad
```

## Secuencia funcional

1. Se ingresa la entidad y el contrato.
2. El sistema recupera el grupo familiar.
3. Se seleccionan los integrantes afectados.
4. Se informa:
   - Fecha de antigüedad.
   - Entidad anterior.
5. Se valida la información.
6. Se graba la solicitud.
7. La solicitud pasa por el circuito de autorización.
8. Cuando queda impactada, se actualiza `AFILIADOS`.

## Cambio parcial

Se seleccionan únicamente los integrantes que deben modificar su antigüedad.

El sistema controla que:

- Haya al menos un integrante seleccionado.
- Los integrantes estén vigentes.
- La fecha de antigüedad sea válida para cada integrante.

## Cambio total

Se marca la opción de cambio de contrato.

En ese caso:

- Deben incluirse todos los integrantes vigentes del grupo.
- La misma fecha de antigüedad se aplica a todos.
- La entidad anterior debe ser la misma para todos los integrantes.

# 3. Validaciones manuales

## Obligatoriedades

Para poder grabar la solicitud se requiere:

- Seleccionar al menos un integrante, salvo que se haya seleccionado el cambio total.
- Informar la fecha de antigüedad.
- Informar la entidad anterior.
- Informar contrato y entidad/prepaga.
- Contar con una fecha de aplicación válida.

Mensajes principales:

```text
Seleccione algún integrante del grupo familiar
La fecha de antigüedad no acepta valores nulos.
El campo Entidad anterior no acepta valores nulos ni blancos
```

## Validaciones de fechas

### Fecha de antigüedad contra fecha de ingreso

La fecha de antigüedad no puede ser posterior a la fecha de ingreso del integrante:

```text
La fecha antigüedad no puede ser superior a la fecha de inicio de servicio del asociado
```

### Fecha de aplicación contra fecha de ingreso

La fecha de aplicación no puede ser anterior al inicio de servicio de los integrantes seleccionados:

```text
La fecha de aplicación no puede ser Inferior a la fecha de inicio de servicio para el integrante ...
```

### Rango de fecha de aplicación

La fecha de aplicación debe encontrarse dentro del rango permitido para el motivo. Si queda fuera:

```text
La fecha de Aplicación no puede ser posterior al ...
La fecha de Aplicación no puede ser anterior al ...
La solicitud sólo se podrá Rechazar
```

## Titularidad

El sistema busca un titular vigente para la fecha de aplicación mediante:

```text
afs_busca_nuevo_titular
```

Si no puede identificar un titular, la solicitud no puede continuar correctamente:

```text
Error al buscar al candidato a titular
```

# 5. Procedimientos manuales y de impacto

## Procedimiento que realiza la actualización definitiva

```text
dbo.afu_fechas_ingre_antig
```

Parámetros principales:

```text
@prepaga
@contrato
@integrante
@antig_fecha
@anter_prepa
```

La actualización realizada es conceptualmente:

```text
AFILIADOS.antig_fecha = nueva fecha
AFILIADOS.anter_prepa = entidad anterior
AFILIADOS.modi_fecha = GETDATE()
```

## Proceso batch de impacto

El procedimiento:

```text
dbo.gms_genera_solicitudes
```

identifica el motivo `16` y, al impactar la solicitud, recorre los registros de `SOLI_AFILIADOS` activos:

```text
WHERE soli = @soli
AND baja_fecha IS NULL
AND antig_fecha IS NOT NULL
```

Por cada integrante ejecuta:

```text
dbo.afu_fechas_ingre_antig
```

Si la actualización falla, el proceso informa:

```text

```

# 6. Circuito automático

El punto de entrada es:

```sql
EXEC dbo.afi_insertar_soli_auto
     @var_data_xml = @xml
```

El dispatcher identifica:

```text
soli_moti = 16
```

y deriva a:

```text
dbo.afi_insertar_soli_auto_cambio_fecha
```

Ese procedimiento:

1. Valida que el motivo sea `16`.
2. Obtiene el contrato y la fecha de aplicación.
3. Busca la clase vigente del contrato.
4. Valida que la subcuenta esté activa.
5. Busca la regla vigente para el cambio de antigüedad.
6. Valida el rango permitido de fecha.
7. Valida la acción de inhabilitación configurada.
8. Valida que existan integrantes.
9. Valida fecha de antigüedad y entidad anterior.
10. Valida integrantes vigentes.
11. Valida titular vigente.
12. Valida recargos.
13. Valida que no exista otra solicitud pendiente o futura incompatible.
14. Graba `SOLI_AUTO_CONTRATO`.
15. Graba `SOLI_AUTO_INTEGRANTES`.
16. Devuelve `id_proceso`.

El procedimiento automático **no actualiza inmediatamente `AFILIADOS`**. Primero registra el proceso automático. La solicitud se genera e impacta posteriormente mediante el circuito GMS/batch.

# 7. Datos obligatorios para el XML automático

La cabecera debe informar, como mínimo:

```xml
<solicitud
    id_soli_externa="..."
    id_radicacion="..."
    soli_moti="16"
    prepaga="..."
    contra="..."
    fecha_aplicacion="..."
    cambia_contrato="S">
```

Valores admitidos para:

```text
cambia_contrato = S o N
```

Cada integrante debe informar:

```xml
<integrantes>
    <integrante
        inte="01"
        antig_fecha="2026-01-01"
        anter_prepa="1" />
</integrantes>
```

Para cada integrante son obligatorios:

```text
inte
antig_fecha
anter_prepa
```

El procedimiento también controla:

- Que no haya integrantes repetidos.
- Que todos informen la misma fecha de antigüedad.
- Que todos informen la misma entidad anterior.
- Que los integrantes existan y estén vigentes.
- Que `antig_fecha` no sea posterior a `ingre_fecha`.
- Que `antig_fecha` no sea anterior a `naci_fecha`.
- Que la fecha de aplicación no sea anterior al ingreso.
- Que `cambia_contrato = S` incluya todos los integrantes vigentes.

# 8. Reglas de rechazo automático

El proceso automático rechaza o no genera la solicitud cuando:

- No existe clase vigente para el contrato.
- La subcuenta no está activa.
- No existe una regla vigente para el motivo 16.
- La fecha de aplicación queda fuera del rango permitido.
- No existen integrantes.
- Faltan `inte`, `antig_fecha` o `anter_prepa`.
- Hay integrantes repetidos.
- Algún integrante no está vigente.
- La fecha de antigüedad es posterior al ingreso.
- La fecha de antigüedad es anterior al nacimiento.
- No existe titular vigente.
- Existen recargos incompatibles.
- Ya existe una solicitud de cambio de antigüedad pendiente.
- Existe una solicitud anterior impactada con fecha futura.
- `cambia_contrato = S` no contiene todos los integrantes vigentes.

# 9. Diferencia entre grabar e impactar

| Etapa | Resultado |
|---|---|
| Grabar solicitud manual | Se registra `SOLICITUDES` y `SOLI_AFILIADOS` |
| Crear proceso automático | Se registra `SOLI_AUTO_CONTRATO` y `SOLI_AUTO_INTEGRANTES` |
| Generar solicitud batch | Se crean los registros operativos de Afilmed |
| Aceptar | La solicitud queda autorizada para continuar |
| Impactar | Se actualiza `AFILIADOS.antig_fecha` y `AFILIADOS.anter_prepa` |
| Error durante impacto | No se completa la modificación y se informa error de actualización |

## Conclusión

Para impactar manualmente una solicitud de Cambio de Fecha de Antigüedad se requiere que exista al menos un integrante seleccionado —o que se haya elegido el cambio total—, fecha de antigüedad, entidad anterior, fecha de aplicación válida y titularidad resoluble.

Para generarla automáticamente se debe utilizar `soli_moti=16`, informar contrato, fecha de aplicación, indicador de cambio total/parcial e integrantes con `inte`, `antig_fecha` y `anter_prepa`. El procedimiento `afi_insertar_soli_auto_cambio_fecha` crea el proceso, mientras que la actualización efectiva de `AFILIADOS` se realiza posteriormente durante el impacto mediante `gms_genera_solicitudes` y `afu_fechas_ingre_antig`.
