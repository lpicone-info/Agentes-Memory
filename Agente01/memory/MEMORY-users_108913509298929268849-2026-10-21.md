# 1. Objetivo

El procedimiento recibe una solicitud de AFE 2.0 y determina si cada beneficiario puede acceder a una campaña comercial.

Evalúa:

- datos de la solicitud;
- cuenta y subcuenta;
- programa y tarifa;
- campaña;
- beneficiarios;
- auditoría médica;
- morosidad;
- edad, género y parentesco;
- condición de nuevo;
- cantidad mínima para campañas 2x1;
- programas adicionales;
- descuentos configurados.

No crea la solicitud ni modifica afiliados. Su función es **validar y devolver un resultado**.

---

# 2. Cómo recibe la información

El procedimiento recibe un único documento XML:

```text
@prm_data_xml
```

El XML contiene:

- datos generales de la solicitud;
- responsable pagador;
- integrantes;
- programas adicionales, cuando corresponda.

Ejemplo conceptual:

```xml
<solicitud
    version="1"
    soli_moti="1"
    prepaga="1"
    cod_camp_comercial="253"
    cuenta_dest="2"
    subcta_dest="FSMP"
    plan_dest="OPLF"
    tari_dest="FPLUNQ"
    fecha_inicio_servicio="2026-09-01">

    <responsable_pagador
        docu_tipo="CC"
        docu_nro="303451001" />

    <integrantes>
        <integrante
            inte="01"
            docu_tipo="CC"
            docu_nro="9900010001"
            naci_fecha="1982-02-14"
            sexo="M"
            paren_real_destino="T" />
    </integrantes>
</solicitud>
```

La definición del contrato está documentada al inicio del procedimiento: [líneas 11-18](</home/luispicone/.openclaw/workspace/svn/srmontenegro-Version104-Afilmed-SolicitudesAutomaticas/backend/procedures/afs_valida_campanias_afe20.sql:11>).

# 3. Dos formas de informar los beneficiarios

## 3.1. Solicitud nueva

Cuando el XML no informa `soli`:

- los beneficiarios se leen directamente del XML;
- se calcula la edad a partir de `naci_fecha`;
- se determina si están activos;
- se valida que tengan todos los datos obligatorios.

Se utiliza cuando AFE 2.0 todavía no tiene una solicitud creada.

## 3.2. Solicitud existente

Cuando el XML informa `soli`:

- los beneficiarios se obtienen desde la solicitud existente;
- no se utiliza el detalle de integrantes enviado en el XML;
- se recuperan los estados de auditoría de cada integrante;
- se recalcula la edad a la fecha de inicio del servicio.

La diferencia está implementada en [líneas 623-688](</home/luispicone/.openclaw/workspace/svn/srmontenegro-Version104-Afilmed-SolicitudesAutomaticas/backend/procedures/afs_valida_campanias_afe20.sql:623>).

# 5. Validación de cuenta y subcuenta

El procedimiento reutiliza los mismos procedimientos que utiliza Venta Nueva.

## Cuenta

Consulta:

```text
afs_cuentas
```

Verifica que la cuenta:

- exista;
- esté vigente;
- no esté dada de baja;
- no esté inhabilitada para la fecha de aplicación.

## Subcuenta

Consulta:

```text
afs_busca_subcta_vig_hab_nb
```

Verifica que la subcuenta:

- exista;
- pertenezca a la cuenta;
- pertenezca a la prepaga;
- esté vigente;
- esté habilitada para Venta Nueva.

La validación está en [líneas 556-582](</home/luispicone/.openclaw/workspace/svn/srmontenegro-Version104-Afilmed-SolicitudesAutomaticas/backend/procedures/afs_valida_campanias_afe20.sql:556>).

# 6. Validación de los integrantes

Para cada beneficiario se comprueba:

- número de integrante;
- documento;
- sexo;
- fecha de nacimiento;
- edad;
- parentesco;
- ausencia de duplicados;
- pertenencia a la campaña indicada.

No se permite que un XML mezcle distintas campañas entre sus integrantes.

También se determina si cada beneficiario está activo según su fecha de baja.

Si todos los integrantes están dados de baja, la validación no puede continuar.

---

# 7. Tipos de solicitud

El procedimiento contempla principalmente:

## Venta Nueva

Se informa normalmente:

```text
soli_moti = 1
```

El responsable se considera nuevo si no tiene contratos previos.

Si tiene contratos, puede resultar no nuevo para una campaña que exige nuevos.

## Inclusión

Se informa normalmente:

```text
soli_moti = 2
```

En este caso el contrato es obligatorio.

Además se revisa:

- contrato informado;
- morosidad;
- cantidad de contratos;
- condición de nuevo según las reglas de inclusión.

La condición de contrato obligatorio está en [líneas 507-510](</home/luispicone/.openclaw/workspace/svn/srmontenegro-Version104-Afilmed-SolicitudesAutomaticas/backend/procedures/afs_valida_campanias_afe20.sql:507>).

---

# 8. Validación de la campaña

La campaña se consulta mediante:

```text
afs_campanias_config
```

Se verifica que sea válida para:

- prepaga;
- fecha de inicio del servicio;
- código de campaña;
- tipo de solicitud.

Si no existe una configuración compatible, se rechaza la validación completa.

Después se recupera la definición completa de la campaña, incluyendo:

- tipo de campaña;
- modalidad;
- tipo de cobertura;
- si permite solamente nuevos;
- género;
- rango de edades;
- condición de morosidad;
- si exige padrón;
- vigencia;
- tipo de solicitud permitido.

---

# 9. Programas y tarifas

## Programa principal

El programa principal se valida con:

```text
afs_busca_subcta_planes
```

La tarifa principal se valida con:

```text
afs_subcta_plan_tari
```

Esto confirma que el programa y la tarifa realmente estén disponibles para:

- cuenta;
- subcuenta;
- fecha de aplicación.

## Programas adicionales

Para campañas de cobertura múltiple, los adicionales se obtienen:

- desde el XML, si la solicitud todavía no existe;
- desde `SOLI_ADICIONALES`, si la solicitud ya existe.

Las tarifas adicionales se validan con:

```text
afs_subcta_plan_adi_tari
```

Además, las combinaciones repetidas de programa y tarifa se validan una sola vez, aunque varios integrantes utilicen la misma configuración.

---

# 10. Programas adicionales anulados

Un adicional puede informar:

```xml
anulado="S"
```

Ese adicional no se incorpora a la evaluación.

Si informa:

```xml
anulado="N"
```

o no informa el atributo, se considera activo.

El valor solamente puede ser:

```text
S o N
```

Cualquier otro valor genera un error de entrada.

---

# 11. Responsable pagador: condición de nuevo

El procedimiento busca al responsable pagador por tipo y número de documento.

Luego consulta sus contratos.

La condición se determina así:

| Situación | Resultado |
|---|---|
| No tiene registro previo | Nuevo |
| Venta Nueva con contratos previos | No nuevo |
| Inclusión con más de un contrato | No nuevo |
| Cualquier otra situación permitida | Nuevo |

Esta condición impacta especialmente en campañas configuradas como:

```text
solo_nuevos = S
```

---

# 12. Morosidad

La morosidad se calcula mediante las reglas existentes de AFILMED.

Se consideran:

- contrato;
- cuenta;
- subcuenta;
- fecha de aplicación;
- campaña;
- meses de mora permitidos.

El resultado se informa como:

```text
sin_deuda = S
```

o:

```text
sin_deuda = N
```

Si la campaña no admite morosos y el resultado es `N`, la asignación queda no factible.

---

# 13. Auditoría médica

Cuando se informa una solicitud existente, se consulta la auditoría de cada integrante.

Se recuperan:

- estado de auditoría;
- si ese estado impacta o no en la campaña.

Si:

```text
estado_impacta = N
```

el beneficiario:

- no cuenta para el mínimo de integrantes;
- queda no factible;
- recibe la causal:

```text
ESTADO_AUDITORIA_NO_IMPACTA
```

Cuando no existe auditoría para una evaluación nueva, el integrante se considera impactable por defecto.

---

# 14. Validaciones comerciales por beneficiario

Para cada combinación beneficiario-programa se consultan las reglas de campaña.

Las variables principales son:

| Variable | Qué representa |
|---|---|
| `f_inicio_servicio` | Fecha de inicio dentro del rango permitido |
| `f_fin_servicio` | Fecha de inicio antes del vencimiento |
| `tiene_l_negocio` | Línea de negocio permitida |
| `filtro_suc_comer` | Sucursal comercializable permitida |
| `tiene_subcta_tipos` | Tipo de subcuenta permitido |
| `tiene_cuenta` | Cuenta permitida |
| `tiene_plan` | Programa permitido |
| `nuevo` | Cumple condición de nuevo |
| `sin_deuda` | Cumple condición de morosidad |
| `genero` | Género permitido |
| `edad_desde` | Cumple edad mínima |
| `edad_hasta` | Cumple edad máxima |
| `tiene_parentesco` | Parentesco permitido |
| `inc_archivo` | Cumple padrón o la campaña no lo exige |
| `tiene_tarifa` | Tarifa permitida |

La matriz se obtiene mediante:


# 16. Campañas 2x1

En campañas tipo `2`, la cantidad mínima se obtiene del cronograma de descuentos.


Significa que el grupo debe tener al menos tres beneficiarios válidos.

- impactables;
- misma campaña;
- mismo programa.

No separa el conteo por tarifa ni por línea de negocio.

```text
cantidad_grupo = 1
cantidad_minima = 3
factible = N
```

Si el grupo alcanza el mínimo, todas las asignaciones pueden resultar factibles.
