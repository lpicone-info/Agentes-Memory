- Para ABM PRESMED, las reglas fijas relevantes son: SQL ASCII CRLF sin BOM, sin punto y coma y sin `RTRIM`; formato de procedures con `USE prestaci`, drop seguro `OBJECT_ID`, `CREATE PROCEDURE dbo`, `AS BEGIN/END`, `RETURN`, `sp_procxmode unchained`, validacion CREATED/FAILED y `GRANT EXECUTE` a `prestaci_role`; no ejecutar SQL ni compilar/importar PB22 sin autorizacion explicita.

- En PowerScript PRESMED: no agregar comentarios, no usar `ISNULL`, no comparar dato con `''` para validar vacio, usar `lib.of_vacio(...)`. En `itemchanged` usar variable `data`; si row viene vacio en detalle de un registro, usar `ll_row = row` y si `lib.of_vacio(ll_row)` entonces `ll_row = 1`.
- Importante PB: para convertir a decimal se usa `Dec(data)`, no `decimal(data)`. Las variables pueden declararse `Decimal`, `Decimal{2}`, `Dec` o `Dec{2}`.
- Para numericos en validacion PB, si corresponde validar vacio/cero usar `lib.of_vacio(long(data))`. Si `data` viene vacio y la DW ya tiene default cargado, recuperar `this.object.<columna>[ll_row]` antes de validar.
- Para DataWindows de ABM PRESMED: no deben tener SQL embebido; deben recuperar por stored procedure. La DW individual debe permitir update en propiedades PB con columnas `update=yes`, keys `key=yes`, `update='tabla'`, `updatewhere` y `updatekeyinplace=no`.
- Daniel remarco que `d_conve_farma_produ_2` es diseno `freeform`, no tabular, y debe respetarse cuando se use como modelo de detalle/edicion. La lista puede quedar tabular siguiendo `d_conve_farma_produ_1`.

## RECETA_PRESMED_ABM V3 / Estandar acordado
- Daniel descarto usar V2 para ventanas complejas porque genera objetos que existen pero pueden quedar inutilizables si inventa botones/eventos/procedures o reconstruye DW sin respetar el modelo.
- V3 debe usar una ventana modelo preprocesada como autoridad para controles, eventos, funciones, acciones, cantidad de DataWindows y dependencias. Si el modelo no tiene un boton/control seleccionado, no se debe inventar. Si una accion no esta seleccionada, no generar llamada PB ni procedure SQL asociado.
- Antes de generar, preprocesar la ventana modelo y mostrar/inventariar controles (`dw`, `cb`, `sle`, `st`, etc.), eventos, funciones, variables, dataobjects y dependencias en una grilla con tilde incluir/no incluir. El resultado reusable debe guardarse como profile, ej. `MODEL_PROFILE_wp_conve_farma_produ_v1.json`.
- En `wp_conve_farma_produ.srw` el preproceso real encontro 3 DW relevantes: `d_conve_farma_produ_2` -> filtro/cabecera (`dw_filtro`, freeform), `d_conve_farma_produ_0` -> ingreso/edicion (`dw_ingreso`, conservar layout), `d_conve_farma_produ_1` -> listado/consulta (`dw_todo`, tabular/listado). Destino para `conve_produ_mandatarias`: `d_conve_produ_mandatarias_2`, `_0`, `_1`.
- Preproceso real de `wp_conve_farma_produ`: no aparece `cb_baja` ni `cb_importar`; `pb_bor` existe pero invisible y no representa baja logica SQL. Por eso el profile V3 apaga baja y no debe generar `prd_` salvo que haya otra variante/modelo o seleccion explicita con dependencia resuelta.
- Estandar DW acordado: para automatizar hay que duplicar la DW modelo y preservar layout, bandas, controles internos, nombres de columnas, orden de columnas, tipos PB del resultset y propiedades visuales. No reconstruir la DW desde columnas de la tabla destino cuando `preservar_resultset_modelo = si`.
- Estandar resultset acordado: no tocar el resultset del proceso ni de la DW en primera generacion. El mapeo de columnas se resuelve en el `prs_`: cada columna del resultset modelo debe salir con el mismo alias y orden esperado por la DW. Si una columna del resultset modelo no existe en la tabla destino, devolver `'' as <columna_modelo>` en el `prs_`.
- No quitar columnas del resultset modelo en primera generacion. Si no se usan, conservarlas ocultas o alimentadas con `''`. No agregar columnas nuevas adelante ni intercaladas; si el programador pide columnas adicionales, agregarlas al final del resultset y al final visual de la DW.
- Daniel explico que esta es la forma real de trabajo manual: duplicar ventana/DW/procedure y mapear nombres de tabla/columnas en el `prs_`, manteniendo DW andando primero. Luego, eventualmente, el programador oculta o retira columnas de a poco.
