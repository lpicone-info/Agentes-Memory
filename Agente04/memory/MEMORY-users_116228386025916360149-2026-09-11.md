## 5. Transiciones normales

El flujo principal es:

```text
A  ->  C  ->  L
```

| Transición | Procedure | Condición |
|---|---|---|
| `A -> C` | `pru_lote_cierre` | Se cierra la carga del lote |
| `C -> L` | `pru_lote_cierre_aud` | Todas las recetas fueron auditadas |
| `A -> L` | `pru_lote_cierre` + `pru_lote_cierre_aud` | No quedan recetas pendientes al cerrar la carga |

El último caso permite que un lote pase de `A` a `L` dentro del mismo proceso si no tiene recetas pendientes de auditoría.

## 14. Diferencia con `expe_farma_recetas.ok`

No deben mezclarse ambos campos.

### `expe_farmacias.ok`

Representa el estado del lote:

```text
A = En carga
C = En auditoría
L = Auditado/listo para liquidar
```

### `expe_farma_recetas.ok`

Representa el estado de cada receta:

```text
N = Pendiente/a revisar
X = Aprobada
R = Rechazada
S = Sin error/aprobada según proceso
```

Por ejemplo, `pru_farma_borra_auditoria` cambia:

```sql
expe_farma_recetas.ok = 'N'
expe_farmacias.ok = 'C'
```

Es decir, vuelve las recetas a revisión y el lote a estado `C`.

## Conclusión

La lógica funcional confirmada para `expe_farmacias.ok` es:

```text
Alta/importación       -> A
Cierre de carga        -> C
Cierre de auditoría    -> L
Reapertura auditada    -> C
Reapertura no auditada -> A
Reversión de auditoría -> C
Conciliación especial  -> L directo
Procedure legado       -> L directo
```

El circuito normal recomendado para desarrollo debe considerar únicamente:

```text
A -> C -> L
```

y permitir los retornos:

```text
L -> C
C -> A
```

La base no impide técnicamente otros caracteres, porque el campo no tiene una restricción de valores. El control actual depende de los procedures y de las ventanas PowerBuilder.
