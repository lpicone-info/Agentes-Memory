### Receta rechazada

Cuando `ok = 'R'`:

```text
reconocido = 0
crédito afiliado = 0
```

En pantalla se identifica expresamente como **Rechazada**.

### Receta auditada

Cuando `ok = 'X'`:

1. Calcula el descuento de cada ítem presentado y auditado.
2. Si el importe auditado del ítem supera al presentado, lo limita al presentado.
3. Reconstruye los totales auditados de la receta:
   - Para ítems con débito utiliza valores auditados.
   - Para ítems sin débito utiliza valores presentados.
4. Calcula:

```text
reconocido =
    (total auditado - importe auditado del afiliado)
    - (total auditado × descuento farmacia / 100)
```

5. Ajusta el resultado:

```text
Si reconocido < 0:
    reconocido = 0

Si reconocido > reclamado:
    reconocido = reclamado
```

Referencias: [cálculo auditado](/home/luispicone/.openclaw/workspace/svn/std-jcastilla/backend/procedures/prs_farma_liq_detalle.sql:264) y [límites](/home/luispicone/.openclaw/workspace/svn/std-jcastilla/backend/procedures/prs_farma_liq_detalle.sql:355).

## Riesgos técnicos detectados

### 1. Unión incompleta al consultar una farmacia específica

Cuando `@farma = 0`, la unión con `expe_farma_recetas` incluye:

```text
ofi + expe + farma + lote + rece_nro
```

Cuando se consulta una farmacia específica, falta la condición:

```text
c.lote = a.lote
```

Si una farmacia reutiliza el mismo `rece_nro` en diferentes lotes del expediente, existe riesgo de cruzar o duplicar recetas.

### 2. Selección no determinística del descuento

El procedimiento asigna `@farma_debito` desde `expe_farmacias` filtrando solamente por oficina y expediente, aunque puede haber varias farmacias o lotes. Luego aplica ese valor a todos los registros temporales.

Si `farma_dto` difiere entre filas del expediente, el descuento utilizado podría depender de la fila que SQL Server asigne por último.
