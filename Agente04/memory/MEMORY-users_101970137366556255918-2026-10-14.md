```sql
USE prestaci
GO

IF OBJECT_ID('dbo.nombre_sp') IS NOT NULL
BEGIN
    DROP PROCEDURE dbo.nombre_sp

    IF OBJECT_ID('dbo.nombre_sp') IS NOT NULL
        PRINT '<<< FAILED DROPPING PROCEDURE dbo.nombre_sp >>>'
    ELSE
        PRINT '<<< DROPPED PROCEDURE dbo.nombre_sp >>>'
END
GO

CREATE PROCEDURE dbo.nombre_sp
(
    @prm_ofi  SMALLINT,
    @prm_expe INT
)
AS
BEGIN
    SELECT
        a.farma,
        f.manda_farma,
        f.razon,
        a.lote,
        c.afi_dto,
        a.rece_nro,
        a.prepaga,
        a.contra,
        a.inte,
        a.emi_fecha,
        a.ticket_nro,
        a.rece_vta_valor,
        a.audi_vta_valor,
        a.ok
    FROM dbo.expe_farma_recetas a
    INNER JOIN dbo.expe_farmacias c
        ON c.ofi = a.ofi
        AND c.expe = a.expe
        AND c.farma = a.farma
        AND c.lote = a.lote
    INNER JOIN dbo.farmacias f
        ON f.farma = a.farma
    WHERE a.ofi = @prm_ofi
        AND a.expe = @prm_expe
        AND a.ok = 'N'
        AND a.baja_fecha IS NULL
        AND c.audi_fecha IS NULL
        AND c.carga_fecha IS NOT NULL
        AND c.baja_fecha IS NULL
    ORDER BY
        f.manda_farma,
        a.lote,
        a.prepaga,
        a.contra,
        a.inte,
        a.emi_fecha,
        a.rece_nro
END
GO

EXEC sp_procxmode 'dbo.nombre_sp', 'anymode'
GO

IF OBJECT_ID('dbo.nombre_sp') IS NOT NULL
    PRINT '<<< CREATED PROCEDURE dbo.nombre_sp >>>'
ELSE
    PRINT '<<< FAILED CREATING PROCEDURE dbo.nombre_sp >>>'
GO

GRANT EXECUTE ON dbo.nombre_sp TO prestaci_role
GO
```

Marcelo, agregar parámetros mejora la performance únicamente si permiten reducir significativamente las filas consultadas.

## Parámetros con mayor impacto

Si la ventana conoce farmacia y lote, agregaría:

```sql
@prm_farma INT,
@prm_lote  TINYINT
```

Y en el `WHERE`:

```sql
AND a.farma = @prm_farma
AND a.lote = @prm_lote
```

Esto aprovecha mejor la clave de `expe_farma_recetas`:

```text
ofi, expe, farma, lote, rece_nro
```

El SP quedaría dirigido a un lote concreto, evitando recorrer todas las farmacias y lotes del expediente.

## Si conoce solamente la mandataria

También podría agregarse:

```sql
@prm_manda_farma INT
```

Con:

```sql
AND f.manda_farma = @prm_manda_farma
```

Pero generalmente será menos selectivo que farmacia y lote.

## Evitar parámetros opcionales con `OR`

No recomiendo:

```sql
AND (@prm_farma IS NULL OR a.farma = @prm_farma)
```

Ese patrón puede impedir que Sybase aproveche correctamente el índice.

Si el filtro debe ser opcional, conviene separar las consultas mediante `IF`:

```sql
IF @prm_farma IS NULL
BEGIN
    -- Consulta general
END
ELSE
BEGIN
    -- Consulta con a.farma = @prm_farma
END
```

## Índice potencialmente útil

Si normalmente se consultan todas las recetas pendientes de un expediente, el parámetro adicional no aplica. En ese caso podría evaluarse un índice sobre:

```sql
CREATE NONCLUSTERED INDEX ix_expe_farma_recetas_pendientes
ON dbo.expe_farma_recetas
(
    ofi,
    expe,
    ok,
    baja_fecha,
    farma,
    lote,
    rece_nro
)
GO
```

Este índice acompaña los filtros:

```sql
a.ofi = @prm_ofi
a.expe = @prm_expe
a.ok = 'N'
a.baja_fecha IS NULL
```

La conveniencia real depende de la cantidad y distribución de registros. Debe verificarse con el plan de ejecución antes de crearlo.

## Recomendación

- Si el proceso trabaja sobre una farmacia/lote seleccionado: agregar `@prm_farma` y `@prm_lote`.
- Si debe listar todos los pendientes del expediente: mantener solamente `@prm_ofi` y `@prm_expe`, y evaluar el índice.
- El `ORDER BY` seguirá generando un ordenamiento porque combina columnas de distintas tablas; agregar parámetros reducirá el volumen a ordenar.
