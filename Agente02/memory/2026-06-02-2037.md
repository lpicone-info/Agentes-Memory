Cómo se recuperan los datos si hay falla:

- restaurar archivos adjuntos;

**RPO**
`Recovery Point Objective`.

Es **cuánta información como máximo se acepta perder** ante un incidente.

Ejemplo:
- RPO 15 minutos: puedo perder como máximo los últimos 15 minutos de datos.
- RPO 24 horas: puedo perder hasta lo cargado desde el último backup diario.

**RTO**
`Recovery Time Objective`.

Es **cuánto tiempo máximo se acepta estar caído** hasta volver a operar.

Ejemplo:
- RTO 1 hora: el sistema debe volver a estar operativo en una hora.
- RTO 8 horas: puede recuperarse dentro de una jornada.

**“Por tipo de dato”**
Quiere decir que no todos los datos tienen la misma criticidad.

Ejemplo:
- Transacciones médicas/autorizaciones: RPO 15 min, RTO 1 h.
- Afiliados y contratos: RPO 1 h, RTO 2 h.
- Reportes históricos: RPO 24 h, RTO 24 h.
- Logs/auditoría: retención larga, pérdida mínima.

**Métricas de aplicación e infraestructura**

Aplicación:

- cantidad de errores;

- memoria;
- disco;
- red;
- uso de SQL Server;
- conexiones activas;

**Tracing distribuido**
Es seguir una operación completa aunque pase por varios componentes.

Ejemplo:
1. Usuario entra a WebPos.
2. WebPos llama a una API o servicio.
3. La API consulta SQL Server.
4. SQL Server ejecuta un stored procedure.
5. La respuesta vuelve al usuario.

Con tracing distribuido, toda esa cadena queda vinculada con un mismo identificador de correlación, por ejemplo `traceId` o `correlationId`.
