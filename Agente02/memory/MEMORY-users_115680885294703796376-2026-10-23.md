## Por qué puede tardar dentro del SP

### 1. Parameter sniffing

Cuando se ejecuta directamente con valores literales, SQL Server compila un plan adaptado a esos valores.

Dentro del procedimiento puede reutilizar un plan generado previamente para otra combinación de:

- `@contra` específico o `NULL`;
- `@origen` específico o `'Z'`;
- `@cuenta` específica o `NULL`;
- `@subcta` específica o `NULL`;
- `@cod_interno`;
- `@prm_activo`.

Las condiciones siguientes son sensibles a ese problema:

```sql
a.contra = prm.contra OR prm.contra IS NULL
a.ori = prm.origen OR prm.origen = 'Z'
c.cuenta = prm.cuenta OR prm.cuenta IS NULL
c.subcta = prm.subcta OR prm.subcta IS NULL
```

Cuando el plan fue compilado para un caso muy selectivo y luego se usa para un caso masivo, o al revés, puede aparecer un scan o un join inadecuado.

El hecho de que recompilar `afi_morosidad_analisis` haya mejorado el tiempo es compatible con esta hipótesis.

### 2. El `SELECT` externo puede no ser exactamente equivalente

Hay que verificar que la prueba por afuera tenga exactamente:

- los mismos valores;
- los mismos tipos de datos;
- la misma conversión de fechas;
- los mismos joins;
- las mismas condiciones de baja y vigencia;
- el mismo contexto de transacción;
- las mismas opciones de sesión.

También pueden influir caché de datos, concurrencia y bloqueos de esquema.

`READ UNCOMMITTED` reduce bloqueos de lectura, pero no corrige un plan ineficiente ni evita bloqueos de compilación.

### 2. Uso de `OR` que dificulta las búsquedas

El patrón:

```sql
columna = parametro OR parametro IS NULL
```

permite una consulta genérica, pero frecuentemente produce planes menos selectivos.

La mejora más efectiva puede ser separar caminos:

```text
@contra IS NULL       → consulta general
@contra IS NOT NULL   → consulta acotada
@origen = 'Z'         → consulta general
@origen <> 'Z'        → consulta acotada
```

No necesariamente hay que duplicar todo el procedimiento. Puede dividirse solo la inserción problemática.

### 3. `SUBCTA_CONTRATOS` está en `LEFT JOIN`, pero no filtra realmente

En [las líneas 494-508](/home/luispicone/.openclaw/workspace/svn/lcamaratta-PresmedWebInicial/backend/procedures/afi_morosidad_analisis.sql:494) se hace:

 AND ISNULL(s.inhib_morosidad, 'N') = 'N'

Pero no se selecciona ningún campo de `s` ni se utiliza después un filtro `WHERE s...`.

## ¿Conviene hacer una inserción y después actualizar?

**Puede mejorar el plan, pero no siempre.**

La división tiene sentido si se hace en dos fases lógicas:

### Fase 1: conjunto candidato

Cargar solamente los afiliados que cumplen los filtros principales:

### Fase 2: resolver datos de vigencia

Obtener el último registro vigente de:

- `AFI_CLASE`;
- `AFI_PLANES`;
- `AFI_OPCION`.

Esto permite que SQL Server conozca el tamaño real del conjunto intermedio y genere mejores estadísticas temporales.

Pero no recomiendo hacer una actualización masiva de cada columna sin medir, porque se agrega:

- otra escritura en `tempdb`;
- otra pasada sobre la tabla;
- más logging;
- mayor complejidad.

La separación debe reducir drásticamente el conjunto antes de la segunda fase. Si ambas fases recorren casi la misma cantidad de filas, puede ser peor.

## ¿Conviene reemplazar `MAX` por `OUTER APPLY`?

**No automáticamente.** `OUTER APPLY` puede mejorar el caso selectivo, pero también puede producir un `Nested Loops` y ejecutar una búsqueda por cada afiliado.

Para las relaciones obligatorias:

- `AFI_CLASE`;
- `AFI_PLANES`;

correspondería conceptualmente `CROSS APPLY`.

Para la relación opcional:

- `AFI_OPCION`;

correspondería `OUTER APPLY`.

Ejemplo conceptual:

```sql
CROSS APPLY
(
    SELECT TOP (1)
           c.vigen_desde,
           c.cuenta,
           c.subcta,
           c.clase_afi
    FROM AFI_CLASE c
    WHERE c.prepaga = a.prepaga
      AND c.contra = a.contra
      AND c.vigen_desde <= prm.fecha
    ORDER BY c.vigen_desde DESC
) c
```

Pero hay dos precauciones:

1. `TOP (1)` puede cambiar el resultado si actualmente existen dos filas con la misma `vigen_desde`. La consulta actual con `MAX` podría devolver ambas.
2. Para una población muy grande, `APPLY` puede ser peor que una solución set-based con `ROW_NUMBER()` y materialización temporal.

Por eso:

- población pequeña y muy filtrada: `APPLY` puede ser favorable;
- población grande: conviene calcular vigencias en bloque con `ROW_NUMBER()` o una tabla temporal intermedia;
- siempre debe verificarse que los índices permitan buscar por las claves y ordenar por `vigen_desde DESC`.

- comprobantes y demás tablas.

Después de la primera ejecución, esas páginas quedan en memoria y las siguientes lecturas pueden ser mucho más rápidas.

## Importante: no limpia el plan

`DBCC DROPCLEANBUFFERS` limpia principalmente la caché de datos, pero **no elimina el plan de ejecución**.

Por eso, si querés diferenciar los problemas:

| Prueba | Qué evalúa |
|---|---|
| Primera ejecución después de `DROPCLEANBUFFERS` | Lectura física desde disco + ejecución |
| Ejecuciones siguientes | Datos ya cacheados |
| Ejecución con `OPTION (RECOMPILE)` | Plan compilado para esos parámetros |
| Mismo plan con distintos parámetros | Posible parameter sniffing |

La rapidez posterior puede deberse a:

1. datos ya cargados en memoria;
2. plan ya compilado;
3. ausencia de bloqueos en esa ejecución;
4. combinación de los tres factores.

## Precaución

`DBCC DROPCLEANBUFFERS` afecta al buffer pool de toda la instancia, no solamente a este procedimiento ni a esta base. Puede empeorar temporalmente el rendimiento de otras aplicaciones.

Debe usarse únicamente en una base de prueba o en una ventana controlada. No conviene usarlo antes de cada ejecución en producción.

## Forma correcta de medir

Separaría las mediciones:

```text
1. Ejecución fría:
   después de limpiar buffers
   mide disco + CPU + ejecución

2. Ejecución tibia:
   segunda ejecución sin limpiar
   mide CPU + ejecución con datos cacheados

3. Ejecución con recompilación:
   mismo caso, pero con OPTION (RECOMPILE)
   permite evaluar el efecto del plan
```

sin limpiar buffers entre ambas. Así se aísla mejor el problema del plan.
