### [31/08/2026 11:48:10] Agente

Yes, I used a cursor in `pru_api_expe_importar_cabeceras`.

Reason: `ue_run` is not only doing inserts/updates. It processes each valid row and calls procedural business logic in sequence: `pri_expedientes`, `pru_expedientes`, `prd_expedientes`, `pru_expe_reabrir`, `prs_fecha_de_pago`, `pru_expedientes_ajus`, `pru_expedientes_carga`, `pru_expedientes_ivacal`, `pru_expedientes_audit`, `pru_expe_capitas`, `pru_percepcion_iibb`.

So the cursor was the conservative translation of the PowerBuilder flow: one row, prepare values, execute the same dependent procedures, mark row processed.

Your performance concern is valid. A set-based version would likely be faster, but it would require either:

1. Refactoring the called procedures to accept table/lote input.
2. Replacing procedure calls with direct set-based operations against `expedientes` and related tables.
3. Carefully reproducing side effects: audit, re-open/delete behavior, adjustments, capitas, IIBB, calculated due date, generated expediente numbers.

That is a bigger development because the current business logic is procedural and distributed. For a first API wrapper, cursor-based processing is slower but lower risk and closer to `ue_run`. For high-volume imports, the correct second step is a dedicated set-based batch processor by `lote`.
