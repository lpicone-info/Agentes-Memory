assistant: Leandro, con el código propuesto, el lookup del contexto se ejecutaría cada vez que un DAO llama a:

```java

```

Lo más conveniente es resolver el `DataSource` una sola vez y reutilizarlo:

```java
private DataSource dataSource;

private ConectionUtils() {
    try {
        Context context = new InitialContext();
        dataSource = (DataSource) context.lookup(
            "java:comp/env/jdbc/WSafil"
        );
    } catch (NamingException e) {
        throw new IllegalStateException(
            "No se encontró el pool jdbc/WSafil",
            e
        );
    }
}

public Connection connect() throws DataAccessException {
    try {
        Connection conn = dataSource.getConnection();
        conn.setAutoCommit(true);
        return conn;
    } catch (SQLException e) {
        throw new DataAccessException(
            "No se pudo obtener una conexión del pool",
            e
        );
    }
}
```

Así:

- El contexto JNDI se consulta una sola vez al crear `ConectionUtils`.
- Cada ejecución solicita una conexión al pool.
- `conn.close()` no destruye la conexión física: la devuelve al pool.
- Tomcat administra la creación, validación y reutilización de conexiones.

### JMeter test structure

Create this hierarchy:

```text
Test Plan
└── Thread Group
    ├── HTTP Request Defaults
    ├── HTTP Header Manager
    ├── HTTP Request
    ├── Response Assertion
    └── Summary Report
```

Configure the Thread Group:

```text
Threads: 50
Ramp-up: 30 seconds
Loop Count: Infinite
Duration: 300 seconds
```

Configure HTTP Request Defaults:

```text
Protocol: http
Server: TOMCAT_SERVER
Port: 8080
```

Configure the HTTP Request:

```text
Method: POST
Path: /WSafil/getLocalidades
Body Data: SOAP XML request
```

Example SOAP body:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<soapenv:Envelope
    xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/">
    <soapenv:Header/>
    <soapenv:Body>
        <!-- Service operation and parameters -->
    </soapenv:Body>
</soapenv:Envelope>
```

Add an HTTP Header Manager:

```text
Content-Type: text/xml; charset=UTF-8
SOAPAction: required-action
```

Add assertions to verify:

- HTTP status is `200`.
- Response contains an expected value.
- Response does not contain `<soap:Fault>`.

### Recommended executions

Run the same test before and after enabling the pool:

```text
Smoke:   1 user, 1 minute
Normal:  10 users, 5 minutes
Load:    50 users, 10 minutes
Stress:  100–200 users, 10 minutes
Soak:    50 users, 30–60 minutes
```

Use the GUI only to prepare and validate the test. Execute the real load test from the command line:

```bash
jmeter -n \
  -t wsafil.jmx \
  -l results.jtl \
  -e \
  -o report
```

Compare:

- Throughput.
- Error percentage.
- Average response time.
- `p90`, `p95` and `p99`.
- Tomcat CPU and memory.
- SQL Server active connections.
- Pool active, idle and waiting connections.

For this specific SOAP application, I recommend JMeter. k6 is cleaner for automated tests written as JavaScript, while Gatling is strong for code-based Java/JVM test suites. Neither provides a clear advantage over JMeter for this initial comparison.

Official documentation: [JMeter web test plan](https://jmeter.apache.org/usermanual/build-web-test-plan.html) · [JMeter CLI and reports](https://jmeter.apache.org/usermanual/get-started.html) · [k6 API testing](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/) · [Gatling](https://docs.gatling.io/)

Tomcat/NetBeans puede copiar ese descriptor durante el despliegue y reemplazar:

```text

```

Para mantener exclusivamente la configuración externa:

1. El WAR no debe contener `META-INF/context.xml`.

```text

```

4. Verificar el WAR:

```bash
jar tf WSafil.war | grep META-INF/context.xml
```

No debería devolver resultados.

5. Evitar que NetBeans haga `undeploy/deploy`, porque el `undeploy` puede eliminar el descriptor externo. Es preferible desplegar el WAR y reiniciar/reload sin borrar el contexto.

Tomcat también permite deshabilitar los descriptores embebidos:

```xml
<Host
    name="localhost"
    appBase="webapps"
    deployXML="false"
    copyXML="false">
```

Pero esto afecta a todas las aplicaciones de ese `Host`, por lo que no conviene cambiarlo sin revisar las demás aplicaciones.

Fuente: [Tomcat Host configuration: deployXML y copyXML](https://tomcat.apache.org/tomcat-9.0-doc/config/host.html)
