**Hipótesis técnica:** si hoy una transacción implica varios viajes Java-SQL, armado de objetos, validaciones intermedias y carga de temporales desde Java, un wrapper SQL que reciba el XML completo, lo parsee en base, cargue temporales y orqueste los SPs en una sola ejecución puede mejorar por reducción de roundtrips, menor serialización/deserialización y ejecución más cercana a los datos.

**Pero:** si el XML es grande o complejo, parsearlo en SQL Server también puede ser costoso. La mejora real aparece si el costo actual dominante es la ida y vuelta entre Java y SQL o la orquestación en Java. Si el cuello está dentro de los SPs existentes, el wrapper casi no va a mejorar.

Mi recomendación técnica sería: **sí tiene sentido como optimización candidata**, especialmente como wrapper transaccional único, pero habría que medir antes/después con tiempos separados: parseo Java, validación Java, cantidad de llamadas JDBC, duración de cada SP y tiempo total end-to-end. Sin esa medición, afirmar mejora sería una hipótesis, no una conclusión.
