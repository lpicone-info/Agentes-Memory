## Los 9 segundos no los resuelve `maxWait`

Son tiempos diferentes:

```text
maxWait
→ tiempo esperando una conexión libre

query timeout
→ tiempo permitido para ejecutar SQL

socket timeout
→ tiempo máximo de espera de comunicación
```

`maxWait="3000"` solo evita esperar más de tres segundos para obtener una conexión. Una consulta puede continuar ejecutándose durante 9 segundos o mucho más.

Conviene establecer un timeout explícito de consulta, por ejemplo 20–30 segundos, mediante:

```java
statement.setQueryTimeout(30);
```

o un interceptor compatible con la versión de Tomcat.

## Capacidad aproximada

Con 20 conexiones y consultas de 9 segundos:

```text
20 / 9 ≈ 2,2 peticiones por segundo
```

Si llegan más de 2,2 peticiones por segundo de manera sostenida:

- el pool se satura;
- los threads esperan;
- cada request conserva XML y objetos;
- `maxWait=3000` comienza a devolver errores;
- si el cliente reintenta inmediatamente, puede agravar la saturación.

También debe limitarse `maxThreads` del conector Tomcat. Un pool de 16 conexiones con 200 threads HTTP permite que demasiadas solicitudes queden esperando y reteniendo memoria.

```java
import java.io.IOException;
import java.io.InputStream;
import java.util.Properties;
import com.autorem.exceptions.DataAccessException;
import javax.naming.Context;
import javax.naming.InitialContext;
import javax.naming.NamingException;
import javax.sql.DataSource;
import java.sql.*;
import org.apache.log4j.Logger;

public class ConectionUtils {

    private static final Logger log =
        Logger.getLogger("ConectionUtils");

    private final DataSource dataSource;
    private final Properties properties;

    private ConectionUtils() {
        this.dataSource = loadDataSource();
        this.properties = loadProperties();
    }

    private static class InstanceHolder {
        private static final ConectionUtils INSTANCE =
            new ConectionUtils();
    }

    public static ConectionUtils getInstance() {
        return InstanceHolder.INSTANCE;
    }

    private DataSource loadDataSource() {
        try {
            Context context = new InitialContext();

            return (DataSource) context.lookup(
                "java:comp/env/jdbc/AutoRemWebAplication"
            );
        } catch (NamingException e) {
            log.error(
                "No se encontró el pool de conexiones "
                    + "jdbc/AutoRemWebAplication",
                e
            );

            throw new IllegalStateException(
                "No se encontró el pool de conexiones "
                    + "jdbc/AutoRemWebAplication",
                e
            );
        }
    }

    private Properties loadProperties() {
        Properties result = new Properties();
        InputStream input = null;

        try {
            ClassLoader loader =
                Thread.currentThread()
                    .getContextClassLoader();

            input = loader.getResourceAsStream(
                "com/autorem/configuration/"
                    + "webmed.properties"

                    "No se encontró webmed.properties"

            result.load(input);
            return result;

        } catch (IOException e) {

                "No se pudo cargar webmed.properties",
                e

            throw new IllegalStateException(
                "No se pudo cargar webmed.properties",
                e
            );

        } finally {
            if (input != null) {
                try {
                    input.close();
                } catch (IOException e) {
                    log.warn(
                        "No se pudo cerrar "

                        e
                    );
                }
            }
        }
    }
```


El nuevo SP debe recuperar primero las transacciones de la página:

```sql
SELECT transac
INTO #TRANSACCIONES_PAGINA
FROM TEMP_AUTO_REMOTAS_PAGING_DATA
WHERE session_id = @prm_session_id
AND RowID BETWEEN @desde AND @hasta;
```

Como `RowID` actualmente se calcula mediante una CTE y no está almacenado físicamente, debería reconstruirse con el mismo orden:


Después se obtienen todos los detalles:

```sql
SELECT
    AR.transac,
    AI.nomen,
    AI.prestac,
    P.exten_deno AS deno_prestac,
    CASE
        WHEN AI.pago_copa = 'P'
        THEN AI.copa_valor
    END AS copa_valor,
    N.abre_deno,
    AI.canti,
    AI.prestac_valor,
    PR.ape_razon
        + ISNULL(', ' + PR.nombre_abre, '')
        AS nombre_prestad,
    AI.excedente,
    AI.pago_exce
FROM #TRANSACCIONES_PAGINA PAG
INNER JOIN AUTO_REMOTAS AR
    ON AR.transac = PAG.transac
INNER JOIN AUTO_PRESTAC_ITEMS_REMOTAS AI
    ON AI.transac = AR.transac
INNER JOIN PRESTACIONES P
    ON P.nomen = AI.nomen
   AND P.prestac = AI.prestac
INNER JOIN NOMENCLADORES N
    ON N.nomen = AI.nomen
LEFT JOIN PRESTADORES PR
    ON PR.prestad = AR.efe_prestad
WHERE AI.baja_fecha IS NULL;
```

### [21/10/2026 15:59:44] Agente

El pool introduce un límite **intencional**. Ese “cuello de botella” es un mecanismo de protección, no un defecto.

### Con pool

La petición 41:

1. espera una conexión libre;
2. obtiene una conexión cuando termina otra operación;
3. o falla después de `maxWait` si la espera supera el límite.

Esto mantiene controlados:

- el número de conexiones contra SQL Server;
- los threads que ejecutan trabajo real;
- la memoria utilizada;
- el riesgo de bloqueos;
- la carga de CPU.

### Sin pool

La petición 41 probablemente abriría otra conexión física. Al aumentar la concurrencia:

- se crean más sesiones SQL;
- aumenta el handshake y el consumo de memoria;
- SQL Server puede saturar CPU, locks o workers;
- Tomcat mantiene más requests activas;
- finalmente el cuello aparece en SQL Server, en el sistema operativo o en la JVM.

Es decir, **el cuello de botella no desaparece: se desplaza a un punto menos controlado y normalmente más peligroso**.

Además, sin pool se pierde la reutilización de conexiones y aumenta el costo de abrir/cerrar cada sesión.

### Objetivo correcto

El pool debe dimensionarse para la capacidad real del sistema. Si una operación tarda aproximadamente 9 segundos:

```text
20 conexiones / 9 segundos ≈ 2,2 operaciones por segundo
```

Si llegan más de 2,2 operaciones por segundo de forma sostenida, cualquier configuración terminará acumulando espera. La diferencia es que el pool permite rechazar o regular esa carga antes de que se descontrole todo el servidor.

Por eso el valor correcto no es “el máximo posible”, sino el máximo que SQL Server y la JVM pueden procesar manteniendo tiempos y memoria estables.
