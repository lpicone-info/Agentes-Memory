### [10/08/2026 11:28:46] Agente

Leandro, yo lo encararía como un **ABM declarativo**, no como un ABM “mágico” basado solamente en SQL dinámico.

La idea equivalente a `w_clase_abm_simple` sería tener una definición por ABM donde solo se declare lo específico:

```ts
const claseAbm = {
  entidad: "clase",
  tabla: "clase",
  primaryKey: "clase_id",

  lista: {
    columnas: ["clase_id", "descripcion", "activo"],
    ordenDefault: "descripcion"
  },

  formulario: {
    campos: [
      { name: "descripcion", type: "text", required: true, maxLength: 80 },
      { name: "activo", type: "checkbox" }
    ]
  },

  persistencia: {
    modo: "storedProcedure",
    grabar: "dbo.sp_clase_grabar"
  }
}
```

Con eso reutilizás casi todo:

- `AbmPage`
- `AbmGrid`
- `AbmForm`
- `useAbmController`
- validaciones comunes
- manejo de alta/modificación/baja
- confirmaciones
- búsqueda
- paginado
- auditoría
- estados de carga/error
- permisos
- llamada al backend

Lo específico queda reducido a metadata, validaciones particulares y el impacto real.

Sobre el SP genérico con SQL dinámico: **puede servir, pero solo para ABMs simples y muy controlados**. No dejaría que el frontend mande libremente tabla/campos y que el SP ejecute. Eso abre riesgos fuertes: seguridad, permisos, inyección, impacto accidental en tablas no previstas, bypass de reglas de negocio.

Una versión razonable sería híbrida:

1. **ABMs simples**
   Usan un motor genérico de CRUD.
   El backend conoce una lista blanca de entidades permitidas, tablas, columnas editables y clave primaria.
   El SQL dinámico se arma solo desde metadata registrada del lado servidor, usando `QUOTENAME`, `sp_executesql` y parámetros.

2. **ABMs con lógica de negocio**
   Usan el mismo frontend genérico, pero al grabar llaman un SP específico.
   Esto mantiene el equivalente a `ue_grabar`: cada ABM decide cómo impacta, pero no reescribe toda la pantalla.

3. **ABMs complejos**
   Heredan/reutilizan el layout y hooks base, pero agregan componentes propios, validaciones cruzadas o flujos especiales.

El backend podría tener algo así:

```ts
POST /api/abm/:entidad/list
GET  /api/abm/:entidad/:id
POST /api/abm/:entidad/save
POST /api/abm/:entidad/delete
GET  /api/abm/:entidad/schema
```

Pero `:entidad` no debería mapear directo a una tabla recibida desde el cliente. Debería resolverse contra un registro interno:

```ts
{
  entidad: "clase",
  tabla: "dbo.clase",
  pk: "clase_id",
  columnasPermitidas: ["descripcion", "activo"],
  spGrabar: "dbo.sp_clase_grabar"
}
```

Para automatizar el schema y la grilla, hay tres niveles posibles:

- **Inferencia desde SQL Server**: leer `sys.columns`, PK, tipos, nullable, longitudes.
- **Overrides declarativos**: labels, orden, visibilidad, componente visual, reglas funcionales.
- **Generación asistida**: crear un archivo inicial de metadata desde la tabla y luego ajustarlo manualmente.

No confiaría solo en la introspección de base, porque la base sabe que un campo es `varchar(50)`, pero no sabe si en pantalla debe ser combo, si se oculta, si es solo lectura, qué label funcional lleva o si depende de otro campo.

La arquitectura que veo más sólida sería:

```text
ABM Definition
   ↓
Frontend genérico
   - grilla
   - formulario
   - toolbar
   - validaciones cliente
   - estados
   - permisos visuales

Backend genérico
   - validación de entidad permitida
   - validación de campos permitidos
   - normalización de payload
   - auditoría
   - transacción

Persistencia
   - CRUD genérico para tablas simples
   - SP específico para reglas de negocio
```

El punto clave: **reutilizar pantalla, flujo y contrato**, no necesariamente forzar una única forma de grabar todo.

Mi recomendación técnica sería empezar con un **núcleo ABM reutilizable + metadata por entidad + persistencia híbrida**. Eso copia bien la filosofía de PowerBuilder: una ventana base potente, definición mínima por ABM, y punto de extensión específico para grabar.
