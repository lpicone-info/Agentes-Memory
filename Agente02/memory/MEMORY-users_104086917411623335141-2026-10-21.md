## Cómo podría generar memoria alta

Cuando no hay conexiones disponibles:

1. Los threads HTTP quedan esperando una conexión.
2. Cada thread mantiene en memoria:
   - XML recibido.
   - Objeto `Mensaje`.
   - Objetos de cabecera, afiliado y prestaciones.
   - Stack del thread.
   - Respuesta en construcción.
3. Siguen entrando solicitudes.
4. Se acumulan threads esperando.
5. Aumenta el heap y la frecuencia del garbage collector.

El servicio construye todo el objeto XML antes de solicitar/procesar la conexión:

[TransactionServ.java:29](/home/luispicone/.openclaw/workspace/svn/lcamaratta-V25.08.001/ws_auto_remotas/src/java/com/autorem/service/TransactionServ.java:29)

Y obtiene la conexión mediante:

Por lo tanto, muchos requests bloqueados esperando el pool pueden aumentar sensiblemente el uso de memoria.

## Relación con CPU alta

El pool agotado, por sí solo, generalmente produce **threads esperando**, no CPU alta. La CPU puede subir por consecuencias indirectas:

- Garbage collection frecuente debido a la acumulación de requests.
- Parseo y generación de muchos XML simultáneos.
- Muchos threads activos y cambios de contexto.
- Logging de errores o conexiones abandonadas.
- Reintentos por deadlocks.
- Procedimientos SQL costosos ejecutándose en paralelo.
- Base SQL al límite, haciendo que las conexiones permanezcan ocupadas más tiempo.
- Pool ampliado recientemente y enviando demasiadas consultas concurrentes a SQL Server.

Es importante distinguir si la CPU alta corresponde a:

```text
Java/Tomcat
SQL Server
o ambos
```

## Hipótesis más probable

El pool podría ser la consecuencia de procedimientos lentos:

```text
SQL demora
   ↓
las conexiones permanecen ocupadas
   ↓
NumActive llega a 40
   ↓
nuevas peticiones esperan hasta 10 segundos
   ↓
se acumulan threads y XML en memoria
   ↓
aumenta GC, memoria y posiblemente CPU Java
```

Por eso no recomiendo aumentar `maxActive` directamente. Si SQL ya está saturado, pasar de 40 a 80 conexiones puede empeorar CPU, bloqueos y memoria.

## Correlación con SQL Server

Mientras `NumActive` esté alto, ejecutar:

```sql

    s.status,
    s.host_name,
    s.program_name,
    s.login_name,

    r.blocking_session_id,
    r.wait_type,

FROM sys.dm_exec_sessions s
```
