## Resumen

Se analizo el Redmine `28221`. El pedido funcional es que el WS `02C` pueda validar por DNI; actualmente el flujo operativo conocido valida por `NumeroCredencial`.

## Evidencia tecnica

- El XML del WS ya parsea `TipoDocBeneficiario` y `NroDocBeneficiario` en `ws_auto_remotas/src/java/com/autorem/entities/Beneficiario.java`.
- `AutorizacionesDAO` ya tiene logica parcial para resolver afiliado por documento antes de generar la transaccion.
- El SP usado para buscar por documento es `ars_busca_afi_x_documento`, ubicado en `backend/procedures/ars_busca_afi_x_documento.sql`.
- La transaccion `02C` ejecuta `prs_valida_of_auto_remotas`, segun `ws_auto_remotas/src/java/com/autorem/enumerator/TransactionEnum.java`.
- Para busqueda por `NumeroCredencial`, el metodo relevante esta en `ws_auto_remotas/src/java/com/autorem/daos/AutorizacionesDAO.java` y llama principalmente al SP `ars_busca_contra_x_creden`.
- Si `ars_parametros.valor` esta en `S`, tambien intenta `ars_busca_contra_x_creden_en_tramite`.
- La base del WS se configura en `ws_auto_remotas/src/java/com/autorem/configuration/webmed.properties`.
- La clase que lee esa configuracion es `ws_auto_remotas/src/java/com/autorem/utils/ConectionUtils.java`.
- Las claves usadas son `user`, `password`, `server`, `base`, `port` y `tipoServer`.
- El datasource JNDI `jdbc/prestaci` aparece comentado, por lo que para este flujo manda `webmed.properties`.

## Hipotesis

El bloqueo principal esta en la validacion previa de `TransaccionValidator.validarEntrada()`: para software distinto de `WebPostInfomedical`, exige credencial y eso puede impedir que una `02C` con DNI llegue a `AutorizacionesDAO`, donde ya existe la logica para buscar afiliado por documento.

## Solucion posible

Modificar `TransaccionValidator.validarEntrada()` para aceptar, para `02C`, alguna de estas alternativas:

- `NumeroCredencial`
- `Entidad + Contra + Inte`
- `Entidad + TipoDocBeneficiario + NroDocBeneficiario`

Luego dejar que `AutorizacionesDAO.ejecutarAutorizacion()` use el flujo existente: si viene documento, llama a `ars_busca_afi_x_documento`, obtiene `contra/inte`, recupera credencial vigente con `cargarCredenByContra()` y continua con `pri_auto_remotas_webpos` + `prs_valida_of_auto_remotas`.

## Llamada SOAP conceptual

La llamada seria al SOAP `TransactionServ`, operacion `EjecutarTransaccion`, enviando `mensajeXml` con `TipoTransaccion` = `02C` y el DNI en `Beneficiario`, sin `NumeroCredencial`.

Campos clave dentro del XML:

- `EncabezadoMensaje/TipoTransaccion`: `02C`
- `EncabezadoMensaje/Software/NombreSoftware`: si no es `WebPostInfomedical`, con el codigo actual probablemente falle por falta de credencial antes de buscar por DNI.
- `EncabezadoAtencion/Beneficiario/Entidad`
- `EncabezadoAtencion/Beneficiario/TipoDocBeneficiario`
- `EncabezadoAtencion/Beneficiario/NroDocBeneficiario`
- `EncabezadoAtencion/Credencial` vacio o sin `NumeroCredencial`

Endpoint conceptual segun deploy: `.../ws_auto_remotas/TransactionServ`.

## Riesgo funcional

El SP `ars_busca_afi_x_documento` usa seleccion tipo `TOP 1`. Hay que confirmar funcionalmente si un DNI con mas de un afiliado vigente o multiples contratos debe tomar el primero o rechazar por ambiguedad.
