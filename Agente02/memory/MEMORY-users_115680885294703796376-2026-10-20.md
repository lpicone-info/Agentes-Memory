```sql
    EXEC prs_situ_histo_valor ...
END
```

O definir explícitamente cuándo el valor enviado tiene precedencia.

### Categoría

Debe conservarse la categoría recibida. Presmed Web no debería pasar por resoluciones de categoría basadas en terminal, CUIT o lugar propias de WebPOS/servicios externos.

### Fechas

`fecha`, `orden_fecha` y `vali_fecha` deben conservarse. Ninguna rama genérica por `aufree IS NOT NULL` debería reemplazarlas para Presmed Web.

## 8. Copago y excedente intencionales

Deben distinguirse los valores ingresados deliberadamente de los calculados:

```text
copa_valor_ori  → valor intencional
pago_copa_ori   → forma de pago intencional
copa_valor      → resultado efectivo

excedente_ori   → valor intencional
pago_exce_ori   → forma de pago intencional
excedente       → resultado efectivo
```

Si todavía no existen campos originales para excedente, conviene incorporarlos. Usar el mismo campo para valor intencional y calculado hace imposible determinar cuál debe prevalecer.

## Recomendación final

Usaría:

```text
aufree       = '-4'    -- Presmed Web
tipo_transac = '02C'   -- Generación de autorización
```

Con estas reglas:

```text
Presmed Web
├── envía datos administrativos e intencionales
├── no calcula valores efectivos
├── SQL calcula cobertura, convenio, copago y excedente
├── SQL determina estados y rechazos
├── convenio se valida siempre
├── no se ejecutan reglas exclusivas de WebPOS
└── se preserva el origen PMWEB
```

`tipo_transac = NULL` conservaría demasiado del recorrido de la ventana legacy. `02C` representa mejor la operación real; la diferenciación respecto de WebPOS debe hacerse mediante el origen propio en `aufree`.
