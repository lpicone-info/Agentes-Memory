### [22/09/2026 08:39:35] Agente

`register` suele ser más eficiente **para controles HTML nativos** porque los deja como inputs no controlados por React.

### Con `register`

```tsx
const { register } = useFormContext();

<Form.Control
  {...register("apellido")}
/>
```

El valor vive principalmente en el elemento DOM y React Hook Form lo administra mediante referencias y eventos. Al escribir cada tecla:

- no se actualiza un `value` React en el componente;
- no se fuerza un render del input por cada carácter;
- solo se notifican los suscriptores que realmente necesitan ese dato, por ejemplo errores o `useWatch`.

### Con `useController`

```tsx
const { field, fieldState } = useController({
  name: "apellido",
  control
});

<Form.Control {...field} />
```

El campo pasa a comportarse como controlado:

- `field.value` se vuelve una prop React;
- cada cambio ejecuta `field.onChange`;
- el componente que usa `useController` puede renderizarse nuevamente para reflejar ese valor o su estado de validación.

Esto **no vuelve a renderizar todo el formulario**, como ocurre habitualmente con Formik. La suscripción sigue siendo granular. Pero para un input nativo simple agrega una capa de render que no es necesaria.

### Aplicado a la rama actual

Los componentes remotos actuales:

- [`FormInputRHF.tsx`](/home/luispicone/.openclaw/workspace/svn/lcamaratta-PresmedWebInicial/presmed_web/frontend/src/ui/FormInputRHF.tsx)
- [`FormSelectRHF.tsx`](/home/luispicone/.openclaw/workspace/svn/lcamaratta-PresmedWebInicial/presmed_web/frontend/src/ui/FormSelectRHF.tsx)

usan `useController`. Es una implementación válida y ya mejora significativamente respecto de Formik porque cada componente está suscripto a su propio campo, pero todavía podría optimizarse usando `register` para inputs y selects nativos.

En cambio, `useController` sí está justificado para:

- `NumericFormat`;
- `PatternFormat`;
- combos personalizados;
- máscaras;
- componentes que no exponen directamente la interfaz estándar `name/value/onChange/onBlur/ref`.

### Regla práctica

| Control | Recomendación |
|---|---|
| `<input>` nativo | `register` |
| `<select>` nativo | `register` |
| `<textarea>` nativo | `register` |
| `react-number-format` | `useController` |
| combo propio/controlado | `useController` |
| date picker externo | `useController` |
| componente que transforma valores | `useController` |

La diferencia no es que `useController` sea incorrecto. La distinción es:

> `register` maximiza el beneficio de inputs no controlados; `useController` ofrece integración y control para componentes complejos.

Por lo tanto, no propondría rehacer inmediatamente los componentes remotos. Primero mediría con React DevTools Profiler. Si el objetivo es optimizar al máximo los campos de texto simples, la siguiente mejora sería crear una variante interna basada en `register`, manteniendo `useController` para los componentes especiales.

En este componente:

```tsx
const { field, fieldState } = useController({
  name,
  control
});
```

si `control` es `undefined`, `useController` intenta obtenerlo desde el contexto creado por:

```tsx
<FormProvider {...methods}>
  ...
</FormProvider>
```

Conceptualmente funciona así:

```tsx
const methods = useFormContext();

const effectiveControl = control ?? methods.control;
```

Por lo tanto, sigue usando `useController`, con un campo controlado. La diferencia es únicamente de dónde obtiene la instancia de `control`:

- `control` explícito: se pasa como prop.
- `control` omitido: se obtiene de `FormProvider`.
- Sin `control` y sin `FormProvider`: se produce un error de contexto.

No equivale a esto:

```tsx
register(name)
```

### Diferencia real

`useController` devuelve:

```tsx
{
  field: {
    name,
    value,
    onChange,
    onBlur,
    ref
  },
  fieldState
}
```

Y normalmente se renderiza así:

```tsx
<Form.Control {...field} />
```

Eso convierte el control en controlado porque `value` se entrega como prop React.

En cambio `register` devuelve handlers y referencia:

```tsx
const registration = register(name);

<Form.Control {...registration} />
```

El input queda principalmente no controlado y React Hook Form lee su valor mediante la referencia al elemento.

Por eso, en los componentes actuales, aunque se omita el `control`:

```tsx
<FormInputRHF name="apellido" />
```

sigue utilizándose `useController` internamente. Para usar la estrategia no controlada habría que implementar el componente con:

```tsx
const { register } = useFormContext();

<Form.Control {...register(name)} />
```

La ausencia del parámetro `control` solo evita pasarlo manualmente; **no cambia la estrategia de integración ni el comportamiento de renderizado**.

### Implementación completa

```tsx
import React from "react";
import { Col, Form } from "react-bootstrap";
import {
  get,
  useFormContext,
  useFormState
} from "react-hook-form";
import type {
  FieldPath,
  FieldValues,
  FormControlProps
} from "react-hook-form";

interface FormInputRHFProps<
  TFieldValues extends FieldValues
> extends Omit<
    FormControlProps,
    "name" | "value" | "onChange" | "onBlur"
  > {
  name: FieldPath<TFieldValues>;
  label?: string;
  className?: string;
  classNameLabel?: string;
  lg?: number;
  md?: number;
  sm?: number;
  xl?: number;
  xxl?: number;
  handleBlur?: (
    event: React.FocusEvent<HTMLInputElement>
  ) => void;
  type?: string;
}

export const FormInputRHF = <
  TFieldValues extends FieldValues = FieldValues
>({
  className = "",
  name,
  label,
  classNameLabel = "",
  type = "text",
  placeholder = `Ingrese ${label || ""}`,
  lg,
  md,
  sm,
  xl,
  xxl,
  handleBlur,
  ...rest
}: FormInputRHFProps<TFieldValues>) => {
  const { register } = useFormContext<TFieldValues>();

  const { errors, touchedFields } = useFormState({
    name
  });

  const registration = register(name);

  const error = get(errors, name) as
    | { message?: string }
    | undefined;

  const isTouched = Boolean(get(touchedFields, name));
  const message = error?.message;

  const params: {
    lg?: number;
    md?: number;
    sm?: number;
    xl?: number;
    xxl?: number;
    as?: React.ElementType;
  } = {
    lg,
    md,
    sm,
    xl,
    xxl
  };

  if (lg || md || sm || xl || xxl) {
    params.as = Col;
  }

  return (
    <Form.Group
      className={className}
      controlId={name}
      {...params}
    >
      {label && (
        <Form.Label className={classNameLabel}>
          {label}
        </Form.Label>
      )}

      <Form.Control
        {...rest}
        {...registration}
        type={type}
        placeholder={placeholder}
        onBlur={(event) => {
          registration.onBlur(event);
          handleBlur?.(event);
        }}
        isValid={isTouched && !message}
        isInvalid={isTouched && !!message}
      />

      <Form.Control.Feedback type="invalid">
        {message}
      </Form.Control.Feedback>
    </Form.Group>
  );
};
```

  differenceInCalendarDays,
  isAfter,
  isBefore,
  isValid,
  parseISO
} from "date-fns";

const emptyToUndefined = (value: unknown) => {
  if (value === "" || value === null || value === undefined) {
    return undefined;
  }

  return value;
};

const optionalNumber = z.preprocess(
  emptyToUndefined,
  z.coerce.number().finite().optional()
);

const optionalPositiveInteger = z.preprocess(
  emptyToUndefined,
  z.coerce.number().finite().int().positive().optional()
);

const requiredPositiveInteger = z.preprocess(
  emptyToUndefined,
  z.coerce
    .number()
    .finite()
    .int()
    .positive()
);

const dateField = (message: string) =>
  z
    .string()
    .min(1, message)
    .refine((value) => isValid(parseISO(value)), {

Entonces si los input tipo Number se manejan como string internamente, que sentido tiene declararlos como Number?

### [22/09/2026 13:08:51] Agente

El `<input type="number">` entrega un **string**, pero el dato de negocio continúa siendo numérico. La declaración como `number` corresponde al **resultado validado**, no necesariamente al estado interno mientras el usuario escribe.

```text
Input HTML       Schema Zod        Payload/API
"25"        →    25            →   25
""          →    undefined     →   undefined
"abc"       →    error
```

Con el schema propuesto:

```ts
z.preprocess(
  emptyToUndefined,
  z.coerce.number().positive().optional()
)
```

- Zod recibe `"25"`.
- Lo convierte a `25`.
- Valida que sea positivo.
- El `onSubmit` recibe un `number`.

Por eso conviene distinguir los tipos:

```ts
type AutorizacionFormInput = z.input<typeof schema>;
type AutorizacionFormOutput = z.output<typeof schema>;
```

Y configurar RHF así:

```ts
useForm<
  AutorizacionFormInput,
  unknown,
  AutorizacionFormOutput
>({
  resolver: zodResolver(schema)
});
```

El formulario puede mantener el valor crudo recibido del DOM, mientras el submit recibe el valor convertido.

## ¿Por qué no dejar todo como string?

Porque después habría que convertir manualmente antes de:

- comparar cantidades;
- validar enteros y positivos;
- enviar el payload;
- realizar cálculos;
- invocar servicios tipados;
- guardar valores numéricos en la base de datos.

Esto sería incorrecto:

```ts
cantidad: "10"
prestador: "1250"
sucursal: "3"
```

El contrato funcional debería ser:

```ts
cantidad: 10
prestador: 1250
sucursal: 3
```

## Alternativa: convertir desde `register`

También podría hacerse:

```tsx
register(name, {
  valueAsNumber: true
});
```

Pero presenta un problema: un input vacío suele convertirse en `NaN`. Por eso sería preferible:

```tsx
register(name, {
  setValueAs: (value) =>
    value === "" ? undefined : Number(value)
});
```

En ese caso, RHF ya almacenaría números y el schema podría utilizar:

```ts
z.number().positive().optional()
```

Sin embargo, esto requeriría que `FormInputRHF` permita pasar opciones de registro y que todos los campos numéricos apliquen consistentemente la transformación.

## Recomendación para esta aplicación

Mantendría esta separación:

- **Estado editable del input:** string o vacío.
- **Schema Zod:** convierte y valida.
- **Resultado del submit:** número.
- **Payload:** número.

Es decir, declarar `number` sí tiene sentido, pero como **salida normalizada del schema**, no como representación obligatoria del valor mientras el usuario escribe.

También revisaría los nombres de los tipos para que esto quede claro:

```ts
AutorizacionFormInput
AutorizacionFormData
AutorizacionPayload
```

En la propuesta actual, los helpers con `z.preprocess` cumplen esa función, aunque `z.input` puede inferirse como `unknown`. Antes de integrarlos convendría ajustar su tipado para que el contrato de entrada no quede demasiado amplio.

### [22/09/2026 15:09:47] Agente

Conviene parametrizar `dateField` para que distinga entre:

- **Obligatoria:** `""`, `null` o `undefined` producen error.
- **Opcional:** esos valores se convierten en `undefined`.
- En ambos casos, una fecha informada debe ser válida.

```ts
import { isValid, parseISO } from "date-fns";
import { z } from "zod";

interface DateFieldOptions {
  required?: boolean;
  requiredMessage?: string;
  invalidMessage?: string;
}

const emptyToUndefined = (value: unknown) =>
  value === "" || value === null || value === undefined
    ? undefined
    : value;

export const dateField = ({
  required = true,
  requiredMessage = "Ingrese fecha",
  invalidMessage = "Ingrese una fecha válida"
}: DateFieldOptions = {}) => {
  const validDateSchema = z
    .string({
      error: (issue) =>
        issue.input === undefined
          ? requiredMessage
          : invalidMessage
    })
    .refine(
      (value) => isValid(parseISO(value)),
      { message: invalidMessage }
    );

  return z.preprocess(
    emptyToUndefined,
    required
      ? validDateSchema
      : validDateSchema.optional()
  );
};
```

### Fecha obligatoria

```ts
fecha: dateField({
  requiredMessage: "Ingrese fecha de autorización",
  invalidMessage: "La fecha de autorización no es válida"
})
```

Resultados:

```text
""           → error: Ingrese fecha de autorización
undefined    → error: Ingrese fecha de autorización
"incorrecta" → error: La fecha de autorización no es válida
"2026-09-22" → válido
```

### Fecha opcional

```ts
fechaBaja: dateField({
  required: false,
  invalidMessage: "La fecha de baja no es válida"
})
```

Resultados:

```text
""           → undefined
null         → undefined
undefined    → undefined
"incorrecta" → error: La fecha de baja no es válida
"2026-09-22" → válido
```

Es importante que `.optional()` esté dentro del `z.preprocess`:

```ts
z.preprocess(emptyToUndefined, validDateSchema.optional())
```

No así:

```ts
z.preprocess(emptyToUndefined, validDateSchema).optional()
```

En el segundo caso, el valor original `""` no es `undefined`; se ejecuta el preprocess, se transforma después en `undefined` y el schema interno obligatorio puede rechazarlo.

Una alternativa con una API más explícita sería exportar wrappers:

```ts
export const requiredDateField = (
  options?: Omit<DateFieldOptions, "required">
) =>
  dateField({ ...options, required: true });

export const optionalDateField = (
  options?: Omit<DateFieldOptions, "required">
) =>
  dateField({ ...options, required: false });
```

Uso:

```ts
fecha: requiredDateField({
  requiredMessage: "Ingrese fecha"
}),

fechaBaja: optionalDateField({
  invalidMessage: "Ingrese una fecha de baja válida"
})
```

Recomendaría esta última variante porque al leer un schema queda inmediatamente claro si la fecha es obligatoria u opcional.

## Qué ocurre con una 02C importada

La importación se ejecuta mediante:

```text
pri_expe_transac_remotas
    ↓
pri_expe_transac_remotas_server
```

El procedimiento toma la transacción desde `AUTO_REMOTAS`, usando:

```sql

ar.expe
ar.tipo_transac
ar.orden_fecha
ar.fecha
ar.prestaciones
```

y genera los registros correspondientes en el expediente.

Para una 02C utiliza su propia autorización:

```text
sucur = ar.sucur

```

En cambio, para una 02A, 02D, 02L o 02Q utiliza la autorización relacionada:

```sql
CASE
  WHEN ar.tipo_transac IN ('02A','02Q','02D','02L')
  THEN ar.sucur_rel
  ELSE ar.sucur
END
```

y:

```sql
CASE
  WHEN ar.tipo_transac IN ('02A','02Q','02D','02L')
  THEN ar.auto_rel
  ELSE ar.auto
END
```

## Diferencia funcional

```text
02C
└── Solicita/genera la autorización
    └── Puede importarse directamente a expediente si está aprobada

02A
└── Informa o consume una prestación
    └── Puede relacionarse con una autorización previa mediante auto_rel
```

Por lo tanto:

- Una **02C aprobada** puede importarse directamente.
- Una **02A** también puede importarse y normalmente referencia la autorización mediante `sucur_rel` y `auto_rel`.
- No es obligatorio que una 02C sea consumida previamente por una 02A para poder entrar al expediente.
- La disponibilidad final depende de que el tipo de transacción tenga `tr_tran_tipos.liquida = 'S'`, condición que también aplica en `prs_arma_expe_transac`.

Además, tanto una 02C generada por WebPOS (`aufree = -1`) como una generada desde APP (`aufree = -3`) cumplen el filtro `aufree IS NOT NULL` y pueden ser candidatas a importación.
