## Hallazgos y riesgos

### 1. Control de liquidaciones posiblemente inefectivo

La validación contra:

- `EXPE_HONORARIOS`
- `EXPE_ORDENES`
- `EXPE_INTERNACIONES`

marca la transacción con error, pero esta ya fue incorporada a `#TEMP_TRANSAC`.

Los `UPDATE` posteriores trabajan con `#TEMP_TRANSAC` y no verifican nuevamente `procesado = 'N'` ni `error IS NULL`. Por eso, según el flujo SQL, una transacción puede:

1. Ser informada como perteneciente a una liquidación.
2. Ser dada de baja igualmente.

Este comportamiento aparece entre:

- [pru_bajas_transac.sql](</home/luispicone/.openclaw/workspace/svn/lcamaratta-V25.08.001/backend/procedures/pru_bajas_transac.sql:244>)
- [pru_bajas_transac.sql](</home/luispicone/.openclaw/workspace/svn/lcamaratta-V25.08.001/backend/procedures/pru_bajas_transac.sql:271>)

### 2. Tipos no admitidos se omiten silenciosamente

Para tipos distintos de `02A`, `02D`, `02L`, `02C` y `02I`, el procedimiento marca `procesado = 'S'`, pero la asignación del mensaje:

```sql
'No es posible anular este tipo de transacción'
```

está comentada.

Consecuencia: la transacción no se baja, pero tampoco aparece entre los rechazos.

### 3. Otros casos pueden quedar sin resultado

Una transacción inexistente, con estado distinto de `A` o con ciertas combinaciones de valores nulos puede no ingresar en el conjunto procesable y tampoco recibir un mensaje de error.

La interfaz podría comunicar éxito aunque esa transacción no haya sido modificada.

### 4. Mensaje de éxito ambiguo

Después de mostrar las transacciones rechazadas, la pantalla siempre informa:

> “La baja ha sido exitosa para las transacciones seleccionadas.”

Esto también ocurre cuando hubo rechazos, por lo que el mensaje representa una ejecución parcial como si todas las transacciones hubieran sido dadas de baja.

### 5. Egresos históricos bloquean una `02I`

La validación busca cualquier registro en `AUTO_EGRESOS`, pero no aplica:

```sql
baja_fecha IS NULL
```

Una autorización con un egreso ya dado de baja puede seguir siendo rechazada como **“Autorización con egresos registrados”**.

### 6. Se sobrescriben fechas de baja anteriores

Los `UPDATE` sobre tablas dependientes no suelen limitarse a registros con `baja_fecha IS NULL`. Si existen registros previamente dados de baja para la misma transacción o autorización, su fecha histórica puede reemplazarse por la fecha actual.

### 7. Manejo transaccional dudoso en el llamador

`wp_monitor_prestac` contiene una función `wf_procedure_baja` que ejecuta el procedimiento y hace `COMMIT`, pero el botón actual no utiliza esa función: llama directamente a `Retrieve()` sobre `d_transac_bajas`.

Esto deja la persistencia dependiente del estado global de `SQLCA.autocommit`, sin un `COMMIT` o `ROLLBACK` explícito en el evento del botón.
