## Analisis RFP seguridad Presmed/WebPos
- WebPos usa login propio usuario/clave y valida contra SQL Server mediante SP `ars_usuario_pass_valido`; para Pressmed hay logica especifica en ese SP. Password comparada con `HASHBYTES('SHA1', ...)`; no OAuth/MFA.
- En WebPos se encontro AES-256-CBC solo en reset de password con clave/IV hardcodeados; no alcanza como cumplimiento corporativo AES-256 transversal.
- No se encontro implementacion real de OAuth, MFA, HIPAA, HL7 o FHIR en WebPos.
- Para Presmed PowerBuilder (`prestaciones.exe`, `gi_codapli = 2`), login por `w_login`: asigna `SQLCA.LogId` / `SQLCA.LogPass` y hace `CONNECT` directo a SQL Server; luego usa SPs/tablas propias (`zzs_valido_usuario`, `zzi_usuari_conect`, `zz_usuari`, `zz_grupusua`, `zz_accesos`).
- Presmed PB tiene modalidad `AD` que oculta login y toma usuario Windows via OLE/LDAP; sirve como antecedente SSO corporativo, pero no equivale a OAuth/OIDC ni MFA.
- Hay base para SOAP/HTTPS y mensajes tipo HL7 v2 en integraciones existentes, pero no FHIR. Hay wrappers criptograficos (`infocrypt.dll`) y TripleDES en Traditum; no equivale a AES-256 corporativo aplicado transversalmente.
- Recomendacion dada: no declarar OAuth/OIDC+MFA, AES-256, auditoria HIPAA y FHIR como disponibles hoy en WebPos o Presmed PB; declararlos como roadmap comprometido. Para Presmed PB, recomendar arquitectura hibrida con capa intermedia moderna para OAuth/OIDC, MFA, FHIR y auditoria centralizada.
- Explicacion dada: AES-256 para datos en reposo protege datos almacenados. Puede habilitarse desde SQL Server con TDE (Transparent Data Encryption), cifrando `.mdf`, `.ndf`, `.ldf`, backups posteriores y `tempdb` si hay DB con TDE. Es transparente para PB/WebPos, pero no cifra adjuntos externos ni oculta datos a usuarios/apps con permiso. Requiere version/edicion compatible, resguardo estricto de certificado/clave y definicion de alcance.
