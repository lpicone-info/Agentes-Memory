La observación es correcta: React Hook Form permite utilizar `values` para actualizar los valores reactivamente. La elección de `reset()` no era porque `values` no sirviera, sino para separar dos necesidades distintas.

## 1. `reset()` y `resetSignal` cumplen funciones diferentes

El ejemplo tenía:

```tsx
const [resetSignal, setResetSignal] = useState(0);
```

Ese estado no contenía los valores del formulario. Solo servía como señal para que componentes hijos reiniciaran estado local auxiliar, por ejemplo:

- resultados de búsquedas;
- selección de un afiliado;
- modales abiertos;
- listas cargadas externamente;
- estados visuales que no pertenecen a RHF.

El reinicio de valores de RHF sería:

```tsx
methods.reset(initialValues);
```

Por lo tanto:

```text
reset()       → reinicia los valores registrados en RHF
resetSignal   → notifica a hijos que deben limpiar estado externo/local
```

No son equivalentes.

## 2. Diferencia entre `defaultValues`, `values` y `reset`

### `defaultValues`

```tsx
useForm({
  defaultValues: initialValues
});
```

Se utilizan únicamente como valores iniciales. RHF los mantiene internamente y no reacciona automáticamente si cambia el objeto `initialValues`.

### `values`

```tsx
useForm({
  values: initialValues
});
```

Es reactivo. Cuando cambia la referencia de `initialValues`, RHF actualiza los valores del formulario.

Esto es apropiado cuando el formulario debe reflejar siempre una fuente externa, por ejemplo:

```text
Redux/API → values → formulario
```

Pero tiene una consecuencia importante: si cambian los valores externos, puede sobrescribir lo que el usuario está editando.

### `reset()`

```tsx
methods.reset(newValues);
```

Permite decidir explícitamente cuándo se reinicializa el formulario:

```tsx
useEffect(() => {
  methods.reset(initialValues);
}, [initialValues, methods]);
```

También permite controlar qué se conserva:

```tsx
methods.reset(initialValues, {
  keepDirtyValues: true,
  keepErrors: true
});
```

## 3. Por qué inicialmente propuse `reset()`

En `AutorizacionCarga`, `initialValues` se construye a partir de datos como:

- defaults del usuario;
- sucursal;
- prepaga;
- parámetros de autorización;
- cabecera;
- fecha actual.

No todos los cambios de esos datos deberían necesariamente sobrescribir lo que el usuario ya ingresó.

Por ejemplo:

```text
El usuario completa afiliado y prestaciones
        ↓
Se actualiza un dato de Redux
        ↓
values reactivo reemplaza el formulario completo
        ↓
Se pierden datos editados
```

Con `reset()` el momento de reinicialización queda explícito y permite decidir si se reemplaza todo o solo parte:

```tsx
reset(initialValues);
```

o:

```tsx
reset(initialValues, {
  keepDirtyValues: true
});
```

## 4. ¿Podemos usar `values` en esta pantalla?

Sí. De hecho, podría ser una mejor opción si la intención funcional es que los datos externos siempre sean la fuente de verdad.

La implementación sería:

```tsx
const initialValues = useMemo(
  () => buildInitialValues(defaults, cabecera),
  [defaults, cabecera]
);

const methods = useForm<AutorizacionFormInput>({
  resolver: zodResolver(schema),
  values: initialValues,
  resetOptions: {
    keepDirtyValues: true,
    keepErrors: true
  }
});
```

Pero hay que definir claramente qué significa cada actualización externa:

- Si cambia la cabecera porque se cargó una autorización existente, probablemente debe reemplazarse todo.
- Si cambia un parámetro auxiliar, probablemente no debe tocarse lo que el usuario editó.
- Si se inicia una nueva autorización, debe limpiarse todo.
- Si se consulta un afiliado, deben actualizarse solo sus campos relacionados.

Por eso `values` no elimina la necesidad de diseñar la política de actualización.

## 5. Recomendación para `AutorizacionCarga`

Usaría una combinación:

### `defaultValues`

Para la creación inicial del formulario:

```tsx
const methods = useForm({
  resolver: zodResolver(schema),
  defaultValues: initialValues
});
```

### `reset()`

Para eventos explícitos:

```tsx
const iniciarNuevaAutorizacion = () => {
  reset(buildInitialValues(defaults));
  setResetSignal((value) => value + 1);
};
```

```tsx
const cargarAutorizacion = (data: AutorizacionFormInput) => {
  reset(data);
  setResetSignal((value) => value + 1);
};
```

### `setValue()`

Para actualizaciones parciales:

```tsx
setValue("ape", afiliado.apellido);
setValue("nombre", afiliado.nombre);
setValue("edad", afiliado.edad);
```

### `values`

Lo usaría solamente si decidimos que Redux/API debe sobrescribir reactivamente el formulario completo. En ese caso:

```tsx
useForm({
  resolver: zodResolver(schema),
  values: initialValues,
  resetOptions: {
    keepDirtyValues: true
  }
});
```

## Conclusión

Tu lectura de la documentación es correcta: `values` permite actualización reactiva y debe considerarse seriamente.

La decisión sería:

- **`values`** si la fuente externa debe controlar reactivamente el formulario.
- **`reset()`** si la reinicialización debe ocurrir en eventos explícitos y controlados.
- **`setValue()`** para actualizar campos puntuales.
- **`resetSignal`** únicamente para limpiar estado auxiliar de los hijos.

Para `AutorizacionCarga`, no usaría `values` sin definir antes qué cambios externos pueden sobrescribir datos del usuario. Mi recomendación inicial de `reset()` buscaba evitar esa sobrescritura accidental; no implica que `values` sea incorrecto.

## 2. Diferencias de API importantes

Formik utilizaba:

```tsx
push(item);
remove(index);
replace(index, item);
```

RHF utiliza:

```tsx
append(item);
remove(index);
replace([item]);
```

En RHF, `replace` reemplaza el array completo. Para reemplazar una posición individual existe `update(index, item)`, pero no lo usaría dentro de `PrestacionRow`.

`update()` desmonta y vuelve a montar la fila. Para modificar campos de una fila conviene usar `setValue()`.

## 3. ID interno del array

Actualmente cada prestación ya tiene:

```ts
id: generateUUID()
```

RHF también agrega un identificador interno llamado `id`. Para evitar una colisión usaría:

```tsx
useFieldArray({
  control,
  name: "prestaciones",
  keyName: "fieldId"
});
```

Y la clave React:

```tsx
key={field.fieldId}
```

Otra posibilidad futura es eliminar el `id` propio de `PrestacionFormItem` y utilizar directamente el generado por RHF, si ese identificador no tiene ninguna función de negocio.

Nunca debe utilizarse:

```tsx
key={index}
```

porque al eliminar una fila React podría reutilizar incorrectamente el estado de otra.

## 4. Migración de `PrestacionRow`

Formik:

```tsx
const { values, setFieldValue, setFieldError } =
  useFormikContext<AutorizacionFormValues>();
```

RHF:

```tsx
import {
  useFormContext,
  useWatch
} from "react-hook-form";
```

```tsx
const {
  control,
  getValues,
  setValue,
  setError,
  clearErrors,
  trigger
} = useFormContext<AutorizacionFormValues>();

const base = `prestaciones.${index}` as const;

const item = useWatch({
  control,
  name: base
});
```

`useWatch` suscribe la fila solamente a sus propios datos. Cuando cambia otra prestación, esta fila no debería volver a renderizarse innecesariamente.

## 5. Actualización de una fila

En lugar de:

```tsx
setFieldValue(base, { ...item, ...patch }, false);
```

puede utilizarse:

```tsx
const setRow = (
  patch: Partial<PrestacionFormItem>
) => {
  const currentItem = getValues(base);

  setValue(
    base,
    {
      ...currentItem,
      ...patch
    },
    {
      shouldDirty: true,
      shouldTouch: false,
      shouldValidate: false
    }
  );
};
```

No usaría `useFieldArray().update()` aquí porque desmontaría y volvería a montar la fila.

## 6. Manejo de errores

Formik:

```tsx
setFieldError(`${base}.prestac`, "Prestación inexistente");
```

RHF:

```tsx
setError(`${base}.prestac`, {
  type: "manual",
  message: "Prestación inexistente"
});
```

Para limpiar:

```tsx
clearErrors(`${base}.prestac`);
```

O varios campos:

```tsx
clearErrors([
  `${base}.prestac`,
  `${base}.nomen`
]);
```

El schema Zod valida duplicados por:

```text

```

Como esa validación involucra más de una fila, conviene ejecutar:


después de:

- eliminar una fila;
- cambiar nomenclador;
- seleccionar una prestación;
- limpiar todas las prestaciones.

No lo ejecutaría en cada tecla del código, porque perjudicaría el rendimiento. La carga por código ya sucede en `blur`, que es un buen momento para validar.

Los elementos de:


- definir cuántas filas renderizar;
- obtener la clave estable de React.

No deben considerarse la fuente reactiva del contenido de la fila. Por eso:


