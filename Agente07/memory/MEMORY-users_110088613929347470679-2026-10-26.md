## Qué está bien resuelto

### 1. La caché se crea en los procesos principales

```text
pri_transac_remotas
prs_valida_of_auto_remotas
```

Ambos crean:

```sql
#AR_MOROSIDAD_CACHE
```

Los SP invocados internamente pueden acceder a esa tabla porque las tablas temporales locales son visibles para los procedimientos hijos de la misma sesión.

### 2. Se reutiliza únicamente el resultado base

`afi_morosidad_estado` almacena:

```text
nivel
mensaje
estado
```

La primera llamada ejecuta:

```text
afi_moro_analisis_ddjj_tran
afi_morosidad_analisis
```

Las llamadas siguientes recuperan esos valores de la caché.

Después de recuperar el resultado, `afi_morosidad_estado` continúa evaluando:

- Tipo de autorización.
- Condición programada o urgente.
- Prestación.
- Complejidad.
- Reglas de restricción.

Por lo tanto, dos prestaciones de distinta complejidad pueden seguir obteniendo decisiones finales diferentes aunque compartan el mismo nivel base de morosidad.

### 3. Existe aislamiento entre transacciones

La tabla es temporal y pertenece a la sesión SQL. Además, se crea dentro de la ejecución del SP principal.

Por diseño:

```text
Transacción A → caché A
Transacción B → nueva caché B
```

Cuando el procedimiento finaliza, SQL Server elimina automáticamente la tabla temporal creada dentro de él, incluso en los `RETURN` anticipados.

### 4. Mantiene compatibilidad con otros procesos

Si `afi_morosidad_estado` se ejecuta desde Presmed u otro circuito donde no existe `#AR_MOROSIDAD_CACHE`, continúa calculando normalmente:

```sql
IF OBJECT_ID('tempdb..#AR_MOROSIDAD_CACHE') IS NOT NULL
```

No queda obligado a que todos los llamadores creen la tabla.

## Riesgos técnicos

### 1. La caché no tiene clave

Actualmente guarda solamente:

```text
nivel
msg
estado
```

No registra:

```text
prepaga
contrato
fecha
```

Es válido mientras cada ejecución de los SP principales procese exclusivamente un afiliado y contrato. Esa condición se cumple actualmente, pero queda implícita.

Una implementación más robusta identificaría el resultado por:

```text
prepaga + contrato + fecha
```

Así se evita una reutilización incorrecta si en el futuro el procedimiento procesa más de un contrato.

### 2. No impide registros duplicados

La tabla no tiene clave ni restricción de una única fila:

```sql
IF (SELECT COUNT(*) FROM #AR_MOROSIDAD_CACHE) > 0
```

y luego recupera:

```sql
SELECT @nivel = nivel, ...
FROM #AR_MOROSIDAD_CACHE
```

Actualmente la lógica inserta una sola vez, pero no existe una garantía estructural. Si por una modificación futura se insertaran dos filas, el resultado seleccionado sería indeterminado.

### 3. Creación no defensiva en `prs_valida_of_auto_remotas`

Este SP ejecuta directamente:

```sql
CREATE TABLE #AR_MOROSIDAD_CACHE
```

A diferencia de `pri_transac_remotas`, no realiza antes:

```sql
IF OBJECT_ID(...) IS NOT NULL
    DROP TABLE ...
```

Con los llamadores actuales no debería colisionar, pero podría fallar si en el futuro es ejecutado desde un procedimiento padre que ya creó una tabla temporal con el mismo nombre.

### 4. La modalidad `calculo_morosidad = 'M'` no utiliza la caché

Cuando:

```text
PREPAGAS.calculo_morosidad = 'M'
```

se consulta directamente `AFI_ESTADOS_CONTRA` en cada llamada. Funcionalmente es correcto y mucho menos costoso que los dos análisis generales, pero estrictamente no se evita toda repetición.

### 5. No resuelve por sí sola todo RM30601

El cambio reduce llamadas SQL costosas. No modifica:

- Pool de conexiones.
- WAR.
- Administración de memoria de Tomcat.
- Streams o recursos Java.
- Esperas por disponibilidad de conexiones.

Por lo tanto, es una optimización válida para una causa concreta de demora, pero no demuestra por sí sola que desaparezca el crecimiento de memoria o cualquier timeout del SOAP.

## Conclusión

**Sí, aprobaría el enfoque funcional y técnico**, condicionado a demostrar:

1. Una sola ejecución de `afi_moro_analisis_ddjj_tran` por transacción.
2. Como máximo una ejecución de `afi_morosidad_analisis`.
3. Resultados independientes por prestación y complejidad.
4. Ausencia de cruces entre afiliados en conexiones reutilizadas.
5. Resultados iguales antes y después para aceptaciones, rechazos y pendientes.
6. Mejora medible en transacciones `02A/02C` con múltiples prestaciones.

Recomendaría reforzar la tabla temporal con claves de contrato y fecha, aunque el diseño actual es funcionalmente viable bajo el supuesto de un solo afiliado por ejecución.
