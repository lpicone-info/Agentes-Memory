- User Gabriel asked to evaluate Redmine ticket 30121 for Infomedical version 25.03.005, specifically the DTI document/informe from agent Mafalda.
- Key confirmed finding: DTI's image/error is correct if it says SQL cannot insert NULL into column `conve` of table `conve_auditoria`.
- Technical chain validated: `pri_conve_odon_reglas` resolves `@conve_prestac` from `conve_prestaciones` using `conve`, `nomen`, `prestac`, hardcoded `concep = 5`, and `baja_fecha IS NULL`. If no row matches, `@conve_prestac` remains NULL.
- Then `pri_conve_odon_reglas_auditoria` receives `@prm_conve = @conve_prestac`; its lookup `SELECT @var_conve = conve FROM conve_prestaciones WHERE conve_prestac = @prm_conve` leaves `@var_conve` NULL, and `pri_conve_auditoria @conve = @var_conve` attempts to insert into `conve_auditoria(conve, fecha_hora, activi, usuario)`, causing the NOT NULL error on `conve`.
- Important correction to earlier hypothesis: the error in 25.03.005 is not primarily explained by PowerBuilder transaction/COMMIT handling; the concrete DTI image error is explained by a NULL propagated to audit because `conve_prestac` could not be resolved.
- Confirmed answer to Gabriel's latest question: `concep = 5` is hardcoded/forced in backend SQL, not passed from the PowerBuilder screen. `wp_odon_conve_reglas.srw` calls `pri_conve_odon_reglas` without sending `concep`; the procedure contains `and concep = 5` directly.
- This was observed in local code branches including `mpariso-Infomedical-trunk` and `mpariso-V25.08.001`; there is a comment saying other concepts should be considered, but the code still filters fixed by `5`.
- Suggested technical conclusion: either guard the flow so it does not audit/insert when `conve_prestac` is unresolved, or revise the `concep = 5` filter if functionally other concepts are valid.

## 2026-07-21 16:22 UTC - Redmine 30121 / concepto 5 y reglas odontologicas

- Gabriel asked why `concep` is fixed at `5` according to documentation, manuals and Redmine.
- Finding: `concep = 5` represents Honorarios and `concep = 6` represents Gastos. Evidence came from Redmine #12224 and source constants such as `prs_valida_of_convenio.sql`, where `@con_CONCEP_HONORARIOS = 5` and `@con_CONCEP_GASTOS = 6` are defined.
- For odontologia, local source assumes the same rule: `pri_conve_odon_reglas.sql` searches `conve_prestaciones` using `and concep = 5`; `pru_garan_odon_conve.sql` also applies odontological rules filtering `c.concep = 5`.
- No manual/documentation evidence was found stating functionally that odontological rules must always use only concept 5. The best conclusion is that this is a legacy assumption: “reglas odontologicas = prestacion de Honorarios”.
- Gabriel then asked whether it is correct for an odontological prestation to have a concept different from `5`. Answer given: it can be correct depending on the nomenclador/convenio setup, because the model allows prestations associated to concepts through `nomen_conceptos` / `conve_prestaciones` and Redmine #16098/#18087 support that prestations can depend on enabled concepts by nomenclator.
- Functional conclusion: it is not inherently wrong for an odontological prestation to be concept `6` or another valid concept. The risky part is that `pri_conve_odon_reglas.sql` assumes `concep = 5` and therefore fails to find `conve_prestac` when the convenio has that prestation only under another concept, causing the later audit NULL error.

## 2026-07-21 16:22 UTC - Webservice autorizaciones transaccion 01A / Codigo de Seguridad invalido

- Gabriel switched to a webservice authorization issue. Transaction type `01A` is eligibility/affiliate validation. The response returns `<MensajeDisplay>Codigo de Seguridad invalido</MensajeDisplay>`.
- Source review conclusion: the rejection message corresponds to rejection code `1449`, defined in `recha_motivos` as `Código de Seguridad invalido.`
- For transaction `01A`, token use is configured as mandatory in `tr_tran_tipos`: `usa_token = 'S'` and `obliga_token = 'S'` for `tran_tipo = '01A'` and others.
- Flow traced: request token is received by `webpos/controlador/transaccionar.php` from `$_POST['token']`; `webpos/modelo/transaccion.php` passes it to `pri_transac_webpos_total`; that SP receives it as `@prm_token`, stores it in `auto_remotas.token`, then the `01A` flow executes `prs_valida_of_afiliado_remoto`, which calls `prs_valido_token_tr`.
- In `prs_valido_token_tr.sql`, validation looks for an `afi_token` row matching affiliate document type, document number and token: `t.docu_tipo = afi.docu_tipo`, `t.docu_nro = afi.docu_nro`, `t.token = ar.token`.
- If no matching token row is found, `@var_validez_t` remains NULL and the SP sets `@out_error = 1449`. This means 1449 is for no match between affiliate/document/token. Distinguish from `1450` token disabled and `1451` token expired.
- Gabriel asked where to report the token in the XML request for `01A`. Confirmed XML tag is `<CodigoSeguridad>123</CodigoSeguridad>`, not `<Token>`.
- Exact XML path: `<Mensaje><EncabezadoAtencion><Credencial><NumeroCredencial>...</NumeroCredencial><CodigoSeguridad>123</CodigoSeguridad></Credencial></EncabezadoAtencion>...</Mensaje>`.
- Java parsing evidence: `Credencial.java` reads `XmlUtils.obtenerValor(rootElement, "CodigoSeguridad")` and sends it through `getEncabezadoAtencion().getCredencial().getCodigoSeguridad()` to the backend.
- Practical conclusion: for transaction `01A`, if `<CodigoSeguridad>` is missing, empty, malformed, or belongs to a different affiliate/document than the credential/request, it reaches `auto_remotas.token` as null/incorrect and triggers `Código de Seguridad invalido` / 1449.

## 2026-07-21 19:30 UTC - Redmine 30010 / afi_deriv_aportes vigencia no primer dia

- Francisco is working on Redmine 30010: data correction for `afi_deriv_aportes` records whose `vigen_desde` day is different from the first day of the corresponding month. He asked to confirm possible origin processes.
- Work was done on updated SVN trunk: local working copy `mpariso-Infomedical-trunk` was updated to revision `84086`.
- Database profile used: `fiat_prod_test` / `Fiat_Prod_Test`. Reference query: `select * from afi_deriv_aportes where day(vigen_desde) <> 1`.
- DB evidence: `15589` rows in `afi_deriv_aportes` have `DAY(vigen_desde) <> 1`; `11932` match exactly with `AFILIADOS.ingre_fecha`; `11110` were created on `17/04/2017`, strongly suggesting historical load/migration/padron; `3755` are non-titulars with `deriva = 'N'`, `legajo IS NULL`, and a titular in the same contract with the same vigency, suggesting propagation to dependents/family rather than primary origin.
- Main technical conclusion: yes, there are processes that can generate `afi_deriv_aportes.vigen_desde` with a day different from `1`, because they use `AFILIADOS.ingre_fecha` or an imported/received `vigen_desde` without normalizing to first day of month.
- Concrete evidence in source: `backend/procedures/afu_procesa_ddjj.sql` reads `@alta_afi = afiliados.ingre_fecha` around line 83 and inserts it into `afi_deriv_aportes` as `vigen_desde` around line 99. The `backend/tools/afu_procesa_ddjj.sql` variant does the same.
- Concrete evidence in source: `backend/ssis/R6812-Padron/ImportacionPadron/GenerateAFI_DERIV_APORTES.dtsx` generates `vigen_desde = AFI.ingre_fecha`, likely tied to historical padron/import behavior.
- Other possible flows: `afi_importar_deriv_aportes.sql` imports `t.vigen_desde` directly from temporal; `afu_soli_deriv_aportes.sql` stores received `@prm_vigen_desde` into `soli_deriv_aportes`; `afu_afi_deriv_aportes_xsoli.sql` later copies `s.vigen_desde` into `afi_deriv_aportes`; `afi_afi_deriv_aportes_ddjj_trans.sql` sets `#TEMP_PARAMS_X.vigen_desde = @prm_vigen_desde` and preserves it in the MERGE if the caller sends a non-normalized date.
- Answer given to Francisco: importacion DDJJ that strictly reports only month/year may not generate this by itself, unless a stored procedure infers the date. For FIAT, evidence points mainly to historical padron/load using `ingre_fecha`, then propagation to family/dependent records.
