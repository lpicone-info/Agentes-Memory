Maru, mirando la rama `25.08.001`, el proceso está centralizado en `backend/procedures/afi_compro_impresion.sql`.

**Proceso**
1. `afi_compro_impresion` arma una tabla temporal `#IMPRESION` con los comprobantes a imprimir/reimprimir.
2. Carga datos del comprobante: `ente`, `compro_tipo`, `compro_nro`, `prepaga`, `contra`, `inte`, `cuenta`, `subcta`, vencimientos, importes, saldo, deuda, créditos.
3. Lee `prepa_afi_reglas.contra_forma`.
4. Lee `PREPAGAS.barra_ente_rec`.
   - Si `barra_ente_rec IS NULL`: asume `PF`.
   - Si `barra_ente_rec > 0`: busca `ENTE_RECAUDADOR.tipo_barra`.
   - Si `barra_ente_rec = 0`: usa `NG`, no genera código de barras.
5. Si corresponde regenerar, calcula `IMP.barra`.
6. Luego inserta ese valor en `COMPRO_IMPRESION.barra` y finalmente actualiza `COMPROBANTES.codi_barra`.

Además, genera aparte `barra_afip` con `dbo.afn_get_afip_codibarra`, que no es el código de pago sino el código fiscal AFIP/CAE.

**Datos Codificados**
Para el código de pago, el orden depende del formato:

**SIRO cerrado (`tipo_barra = 'SC'`)**
Función: `backend/function/afn_get_cod_barra_SIRO_cerrado.sql`

Orden real codificado:
1. Código de empresa/recaudador: `ENTES.cpagofacil`, 4 dígitos.
2. Código de deudor: si hay `contra`, toma `afi_contra2.contra2`; si no hay `contra`, toma `cuenta_subcta2.subcta2` usando `prepaga/cuenta/subcta`.
3. Primer vencimiento en formato `AAMMDD`.
4. Importe primer vencimiento.
5. Días entre primer y segundo vencimiento.
6. Importe segundo vencimiento.
7. `id_cliente_bancoROELA`.
8. Primer dígito verificador.
9. Segundo dígito verificador.

Diferencia por `contra_forma`: para `S` Consalud y `H` Mutual, el SIRO se genera con `importe/importe2/importe3`, es decir sin sumar deuda vencida. Para el resto usa `total_final1/2/3`, que incluye deuda.

**Caseros / SB Salud (`contra_forma = 'C'` o `'K'`)**
Función: `afn_get_caseros_codibarra`

Orden:
1. Empresa `cpagofacil`, 4 dígitos.
2. Importe primer vencimiento, sin deuda.
3. Fecha primer vencimiento en año + día juliano.
4. Letra del comprobante como ASCII.
5. Número de comprobante.
6. Moneda fija `0`.
7. Diferencia de importe del segundo vencimiento.
8. Días entre primer y segundo vencimiento.
9. Dos dígitos verificadores.

**Afiliado vs Empresa**
La diferencia principal no es un procedimiento separado por “afiliado” y “empresa”, sino los datos disponibles:
- Para comprobantes de afiliado hay `contra/inte`.
- Para comprobantes de empresa puede venir `cuenta/subcta`.
- SIRO contempla ambos casos: si no hay `contra`, busca referencia por `cuenta/subcta`.
- Los formatos Rapipago/Ospelsym/KOS usan `contra`; si el comprobante viene solo por `cuenta/subcta`, no tienen una rama equivalente visible en esta lógica.
- Caseros/Medimas codifican principalmente empresa, importes, vencimientos, letra/número de comprobante y moneda; no codifican explícitamente `contra` ni `cuenta/subcta`.

**Orden de Validaciones**

1. **Parseo del XML**
   El WS entra por `TransactionServ.EjecutarTransaccion`, crea `Mensaje`, parsea el XML y llama a `AutorizacionesBO.ejecutarTransacciones`.
   Referencia: `ws_auto_remotas/src/java/com/autorem/service/TransactionServ.java:28`

2. **Validación Java mínima de entrada**
   `TransaccionValidator.validarEntrada()` intenta validar:
   - si falta credencial;
   - si el software es `WebPostInfomedical`, permite credencial o contrato;
   - intenta validar prestador, aunque esa condición tiene una comparación defectuosa y además el método termina devolviendo siempre `true`.
   
   En la práctica, aunque cargue error, el flujo sigue a DAO.
   Referencia: `ws_auto_remotas/src/java/validadores/TransaccionValidator.java:30`

3. **Construcción de transacción**
   `Transaction.getInstance()` arma una transacción genérica para `01C`, carga defaults desde properties:
   - prepaga;
   - tipo de efector;
   - ámbito ambulatorio/internación;
   - usuario;
   - lugar de atención por defecto si no vino;
   - fecha de transacción, o fecha actual si no puede parsearla.
   
   Referencia: `ws_auto_remotas/src/java/com/autorem/transaction/Transaction.java:21`

4. **Validaciones/completado en DAO antes de insertar**
   En `AutorizacionesDAO.ejecutarAutorizacion()`:
   - busca parámetro `ars_param_general`;
   - si vino documento, intenta resolver afiliado por `ars_busca_afi_x_documento`; si no existe, rechaza con excepción;
   - si no vino contrato ni credencial, exige dato según parámetro: credencial, documento o contrato;
   - exige CUIT de prestador;
   - si vino credencial, busca `contra/inte` por credencial vigente o en trámite;
   - si vino contrato, busca credencial vigente o en trámite;

   - precarga cada prestación con `pri_auto_prestac_items_remotas`;

   Referencias: `ws_auto_remotas/src/java/com/autorem/daos/AutorizacionesDAO.java:78`, `:115`, `:127`, `:148`, `:162`, `:235`, `:290`, `:293`
