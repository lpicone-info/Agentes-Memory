- RM30040: analisis sobre duplicados activos por documento en `Prestaci`. El proceso desde `Ospecon_Prod` hacia `Prestaci` no actualiza por documento, sino por `prepaga + contra + inte`; por eso pueden quedar multiples afiliados activos con el mismo documento cuando cambia el contrato calculado, otro integrante conserva el mismo documento, o una baja no viaja contra la misma clave operativa.
- RM30040 caso concreto: `Prestaci.AFILIADOS` `prepaga = 1`, `contra = 20181621754`, `inte = 1`. Conclusion: no viajo la baja del integrante Ospecon `15758/01`; viajo otro integrante activo con el mismo documento, `15758/05`. En mayo 2025 se importo como `inte 1` con `baja_fecha NULL`, y en julio 2025 volvio a viajar como `inte 5`, quedando ambos activos en Prestaci.
- RM30103: se refiere al WS de Farmacia, especificamente a la validacion de afiliado para mandatarias. El documento funcional lo nombra como operacion SOAP `ValidacionAfiliadosGeneral`, con parametros actuales `cuitFarma`, `prepaga`, `numeroCategoria` y `petAdic1..6`; el pedido es sumar parametro de token y validar que este activo para el afiliado informado.
- RM30103: el WS referido no es `getTokenAfiliado`; ese servicio genera el token. `getTokenAfiliado` recibe `Docu_tipo` y `Docu_nro`, ejecuta `afi_genera_token`, genera token de 3 caracteres, baja tokens vigentes anteriores del mismo documento, inserta en `afi_token` y calcula vencimiento con `parametros_generales.clave = 'validez_token'`.
- RM30103 / Portal prestador: cuando una transaccion informa token, se guarda en `auto_remotas.token` y se valida con `prs_valido_token_tr` contra `afi_token` por documento del afiliado.
- RM30103 / Validacion token: depende de `parametros_generales` (`Generan token de seguridad = N` desactiva validacion global), `tr_tran_tipos.usa_token`, `tr_tran_tipos.obliga_token`, presencia o ausencia de token, `auto_rel > 0` (no valida), excepciones en `prestad_exen_token`, y vigencia/baja/vencimiento en `afi_token`. Rechazos: token invalido/inexistente `1449`, token dado de baja antes de la transaccion `1450`, token vencido `1451`.
- RM30103 / Transacciones que admiten token en `MutualRioIV_Prod_Test`: `01A`, `02A`, `02C`, `02D`, `02F`, `02I`, `02J`, `02L`, `02Q`. Obligatorias actuales: `01A`, `02C`. En `MutualRioIV_Prox_Ver`, el parametro global `Generan token de seguridad` esta en `N`, por lo que la validacion queda apagada aunque existan flags por transaccion.
- RM30103 / Punto clave: pide crear parametro tipo `Token_ws_validacion_farmacia`: `N` = el token no debe ser obligatorio, pero si viene se valida; `S` = el token debe venir y se valida. Esto replica comportamiento actual de `obliga_token` aplicado puntualmente al WS de validacion de farmacia. Falta incorporar parametro de entrada token en el WS Farmacia y engancharlo a la logica de validacion existente sobre `afi_token`.
