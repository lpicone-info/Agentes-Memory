## Proceso de anulación en Afilmed

Afilmed dispone de dos opciones:

- **Cuentas corrientes → Anulación individual de comprobantes**, mediante `wp_anulacion`.
- **Cuentas corrientes → Anulación masiva de comprobantes**, mediante `wp_anulacion_masiva`.

En ambos casos, la anulación termina ejecutando:

```sql
dbo.afu_comprobante_anula
```

### 1. Selección y validaciones

Antes de invocar el procedimiento, PowerBuilder controla:

1. Que el comprobante exista para la clave:
   - `COMPROBANTES.ente`
   - `COMPROBANTES.compro_tipo`
   - `COMPROBANTES.compro_nro`

2. Que no se encuentre anulado:
   - `COMPROBANTES.anu_fecha IS NULL`.

3. Que no sea un comprobante original o resultante de una reversión vigente en `COMPRO_REVERSO_DET`.

4. Cuando la regla 71 está activa, que `COMPROBANTES.factu_perio` coincida con el período abierto en `PERIODOS.factu_perio` para el grupo de emisión del contrato.

5. Que el punto de venta exista y que:
   - `PUNTOS.emite_factura_elec <> 'S'`.

6. Que no tenga cobros activos asociados en `DETALLE_COBRO` y `COBRO`.

7. Que no tenga una cobranza pendiente de procesamiento en `COBRANZA_DIARIA`.

8. En la anulación masiva, que no tenga aplicaciones vigentes en `COMPRO_APLICACIONES`, salvo que el usuario marque expresamente **“Permitir la anulación de comprobantes con aplicaciones”**.

9. Que se haya indicado un motivo de anulación.

La opción masiva utiliza `afs_anulacion_masiva` para obtener los comprobantes candidatos, pero este procedimiento **solamente lista registros; no realiza la anulación**.

## ¿Qué hace `afu_comprobante_anula`?

Recibe:

```sql
@ente
@compro_tipo
@compro_nro
@anu_moti
@anu_fecha
@prm_anula_soli -- opcional, valor predeterminado 'S'
```

Sus principales efectos son:

### Comprobante y facturación

- Desaplica las aplicaciones vigentes mediante `afu_desaplicar_compro_item`.
- Actualiza `COMPROBANTES`:
  - `anu_fecha`
  - `anu_moti`
  - `baja_fecha`
  - `anu_usu`
- Da de baja los registros vigentes de:
  - `COMPRO_ITEMS`
  - `COMPRO_PAGOS`
  - `PREFAC_COMPROBANTES`
  - `PREFAC`
- Elimina físicamente el registro correspondiente de `COMPRO_IMPRESION`.

### Aplicaciones y saldos

`afu_desaplicar_compro_item`:

- Da de baja las relaciones de `COMPRO_APLICACIONES`.
- Restituye los saldos de los comprobantes e ítems involucrados.
- Cambia `COMPROBANTES.cance` a `'N'` en los comprobantes desaplicados.

### Ajustes y aportes

Según las reglas 216 y 265:

- Da de baja o desasigna el comprobante de:
  - `AJUSTES`
  - `AJU_INTERNOS`
  - `AJU_CTA_SUBCTA`
  - `AJU_INTERNOS_CUENTA`
- Desaplica aportes mediante `afu_desaplicar_aportes`.
- Puede modificar:
  - `APORTES`
  - `APORTES_AJUSTES`
  - `AFI_DERIV_APORTES.meses_a_estimar`
  - `APORTES.oportunidad_uso`
  - importes facturados y facturables de los aportes.
- Puede dar de baja lotes y registros de aportes reales mediante `afd_aportes_real_x_aju`.

### Solicitudes

Cuando:

- el comprobante pertenece a un contrato;
- `@prm_anula_soli = 'S'`;
- el tipo de comprobante tiene `COMPRO_TIPOS.financiero = 'N'`;

el procedimiento establece:


para las solicitudes del contrato procesadas en el período del comprobante. Esto permite que vuelvan a ser consideradas por procesos posteriores.

El script debería invocar una vez por comprobante:

```sql
EXEC dbo.afu_comprobante_anula

     @compro_tipo   = ...,
     @compro_nro    = ...,
     @anu_moti      = ...,

     @prm_anula_soli = ...
```

La lista debe identificar cada comprobante por la clave completa **ente + tipo + número**. El número por sí solo no es suficiente.

## Riesgos principales

1. **El SP no reproduce las validaciones de Afilmed.**  
   Las validaciones de período, comprobante electrónico, cobros, cobranzas pendientes, reversos y estado previo están implementadas principalmente en PowerBuilder. Un script que invoque directamente el SP podría anular comprobantes que la pantalla rechazaría.

2. **Comprobantes electrónicos.**  
   El SP no verifica `PUNTOS.emite_factura_elec`. Podría marcarse internamente como anulado un comprobante electrónico sin realizar el tratamiento fiscal correspondiente.

3. **Aplicaciones vigentes.**  
   El SP las desaplica automáticamente. Si el script no controla previamente `COMPRO_APLICACIONES`, modificará saldos de otros comprobantes relacionados.

4. **Cobros y cobranzas.**  
   El SP no impide la anulación de comprobantes cobrados o con cobranzas pendientes. Esto puede dejar inconsistencias entre cuenta corriente, caja y cobranza.

5. **Reprocesamiento de solicitudes.**  
   Con `@prm_anula_soli = 'S'`, ciertas solicitudes quedan con `SOLICITUDES.proce_fecha = NULL` y podrían volver a facturarse. El script debe definir explícitamente si ese efecto es requerido.

6. **Aportes y ajustes.**  
   La anulación puede devolver importes facturables, modificar oportunidades de uso, incrementar meses a estimar o dar de baja aportes estimados y lotes de aportes reales.

7. **Atomicidad insuficiente dentro del SP.**  
   `afu_comprobante_anula` no posee un `TRY/CATCH` ni una transacción propia integral. Solamente controla explícitamente el error de la primera llamada a `afu_desaplicar_compro_item`. Un error posterior podría dejar modificaciones parciales si el invocador no administra correctamente la transacción.

8. **Procesamiento parcial de la lista.**  
   Afilmed confirma cada comprobante individualmente. Si el script confirma uno por uno, puede quedar una parte anulada y otra no. Si utiliza una única transacción para toda la lista, un error obliga a revertir todo el lote y aumenta el tiempo de bloqueo.

9. **Concurrencia.**  
   El estado del comprobante puede cambiar entre la validación y la ejecución: podría recibir un cobro, una aplicación o ser anulado por otro proceso.

10. **Auditoría del usuario.**  
    `COMPROBANTES.anu_usu` se obtiene mediante `afs_suser_sname`. Si el script se ejecuta con un usuario técnico, quedará auditado ese usuario y no necesariamente la persona responsable de la anulación.

11. **Repetición o comprobante inexistente.**  
    El SP no valida que haya actualizado exactamente una cabecera. Una clave inexistente o ya anulada puede finalizar sin un error suficientemente explícito y ejecutar parcialmente operaciones relacionadas.

**Conclusión:** el SP correcto es `dbo.afu_comprobante_anula`, pero no debería invocarse directamente sobre la lista sin reproducir previamente las validaciones funcionales de `wp_anulacion_masiva` y administrar una transacción controlada por comprobante.

## Problema reportado

En Afilmed, al editar y guardar una solicitud existente, el celular del titular desaparece cuando se cumplen estas condiciones:

1. La solicitud tiene motivo **`1 - Afiliación`**.
2. Existe un celular vigente del titular en `SOLI_CELULARES`.
3. Se modifica algún dato de la solicitud, pero no el celular.
4. Se graban los cambios.

## Causa técnica en `25.03_FIX`

Durante `wf_grabar_cel`:

1. Para el titular de una solicitud de Afiliación se ejecuta `afd_soli_cel`.
2. Este procedimiento realiza una baja técnica de **todos** los celulares de la solicitud:

```sql
UPDATE SOLI_CELULARES
SET baja_fecha = '19000101'
WHERE soli = @prm_soli
```

3. Después, los celulares del titular se procesan solamente mediante:

```powerscript
idw_cel.GetNextModified(...)
```

4. Si el celular no fue modificado, no se ejecuta `afu_soli_cel` para reactivarlo.

## Alcance

El defecto **no ocurre en cualquier motivo de solicitud**:

- **Afiliación (`soli_moti = 1`)**: afectado.
- **Incorporación (`2`)**: no ejecuta la baja masiva.
- **Modificación de datos personales (`5`)**: no ejecuta la baja masiva.
- **Cambio de plan/tarifa (`6`)**: no ejecuta la baja masiva.
- Otros motivos tampoco pasan por esta combinación que genera el defecto.

## Por qué no se pierden los celulares de familiares

Aunque `afd_soli_cel` también da de baja los celulares de familiares, posteriormente el sistema recorre **todas** las filas de `idw_cel2`:

```powerscript
FOR li = 1 TO idw_cel2.RowCount()
```

Por eso ejecuta `afu_soli_cel` para cada familiar y vuelve a establecer `SOLI_CELULARES.baja_fecha = NULL`, aunque el celular no haya sido modificado.

La asimetría es:

- **Titular:** procesa solamente filas modificadas.
- **Familiares:** procesa todas las filas cargadas.
