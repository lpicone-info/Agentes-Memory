En ambos casos:

- El lugar determinado por la terminal estaba asociado con un círculo.
- El círculo tenía convenio aplicable.
- La autorización manual resultaba aceptada.
- La transacción remota era rechazada erróneamente por falta de convenio.

## Causa técnica

El problema se origina en el orden de ejecución de `pri_auto_remotas`:

1. El procedimiento selecciona inicialmente un lugar, normalmente el de menor código.
2. Busca la categoría de círculo para ese lugar inicial.
3. Si la categoría queda en `NULL`, entra en la lógica agregada por el **RM29405**.
4. Esa lógica reemplaza el lugar inicial por el lugar correspondiente a la terminal recibida.
5. Después de cambiar el lugar, **no vuelve a recuperar el círculo ni la categoría del lugar definitivo**.
6. La búsqueda del convenio se ejecuta sin categoría.
7. Como el convenio pertenece al círculo y no directamente al prestador, no lo encuentra y genera el rechazo.

Flujo defectuoso:

```text
Lugar inicial
→ categoría inicial NULL
→ buscar lugar por terminal
→ cambiar al lugar correcto
→ no recalcular círculo/categoría
→ no encontrar convenio
→ rechazo incorrecto
```

El ajuste del RM29405 resolvió un caso anterior, pero dejó incompleto el escenario inverso: cuando el lugar seleccionado por terminal es justamente el lugar asociado con el círculo.

## Corrección propuesta en el documento

El flujo debería ser:

```text
Determinar prestador
→ obtener lugares vigentes
→ resolver el lugar mediante la terminal
→ dejar definido el lugar final
→ recuperar círculo y categoría del lugar final
→ buscar convenio
→ aceptar o rechazar
```

La búsqueda por terminal no debería depender de:

```sql
@var_cate IS NULL
```

Debería depender de que se haya informado una terminal:

```sql
@prm_nroTerminal IS NOT NULL
```

Una vez seleccionado el lugar definitivo, siempre se debe volver a resolver:

- Relación con círculo.
- Categoría vigente.
- Convenio aplicable.

## 2. Defecto de presentación del número de transacción

La respuesta muestra valores como:

```xml
<NroTransaccion>1.0852878E7</NroTransaccion>
```

El número real es:

```text
10852878
```

### Causa

En Java, el número está representado como `Double`. Al concatenarlo directamente al XML, Java puede serializarlo en notación científica.

### Impacto

La transacción se registra correctamente en la base. El defecto está en la respuesta XML, pero puede afectar:

- Lectura humana.
- Comparaciones automáticas.
- Integraciones que esperan un identificador entero.
- Precisión futura si el número continúa creciendo.

La solución propuesta es tratarlo como `Long` o `BigDecimal`.

# Relación con terminal inexistente

El rechazo `272 - Terminal inexistente` es un camino relacionado que debe incluirse en la regresión, pero **no es la causa del error principal documentado**.

Al reorganizar la selección del lugar se debe asegurar que:

- Una terminal válida determine el lugar correcto.
- Una terminal inexistente genere `272`.
- No se asigne un lugar arbitrario.
- No se conserven lugares dados de baja.
- El rechazo `272` no sea reemplazado posteriormente por otro rechazo.

## Dictamen

El RM30496 corrige principalmente una **inconsistencia de secuencia**:

> Se determina correctamente el lugar por terminal, pero no se recalculan el círculo y la categoría después de cambiar el lugar. Por eso no se encuentra el convenio del círculo y la operación se rechaza incorrectamente.

Adicionalmente, corrige la serialización del número de transacción para evitar notación científica. No realicé modificaciones ni ejecuciones sobre la base durante este análisis.
