assistant: Sí, podés. Para una función escalar como `dbo.afn_soli_deriv_aportes_sueldo`, podés agregar:

```sql

```

o mejor, al rol real de la aplicación:

```sql
GRANT EXECUTE ON dbo.afn_soli_deriv_aportes_sueldo TO nombre_rol_aplicacion
```

Eso también resolvería el error de permisos para usuarios nuevos, siempre que esos usuarios pertenezcan a ese rol.

La diferencia es de arquitectura:

- **Grant sobre la función:** solución directa y mínima. El DataWindow puede seguir con SQL embebido.

Si el problema puntual es solo permisos sobre esa función, el `GRANT EXECUTE` sobre la función alcanza. La opción más prolija es no darlo a cada usuario, sino al rol/perfil que usan los usuarios de la aplicación.

Pero la causa raíz es más general: cualquier proceso que haga join contra `CUENTAS` por `cuit` y espere una sola cuenta puede duplicar resultados si ese CUIT tiene más de una cuenta registrada.

La regla segura sería: cuando `CUENTAS` se use solo para traer datos descriptivos por CUIT, no hacer join directo tipo:

```sql
JOIN CUENTAS c ON c.cuit = x.cuit
```

sino elegir una única cuenta con criterio funcional:

1. activa primero: `baja_fecha IS NULL`
2. si no hay activa, la más reciente por `alta_fecha`
3. desempate determinístico si hiciera falta

Entonces sí: para este Redmine atacaría los dos puntos visibles que explican el caso, pero conviene hacer una búsqueda preventiva de otros joins por `CUENTAS.cuit` en procesos de derivaciones/aportes.
