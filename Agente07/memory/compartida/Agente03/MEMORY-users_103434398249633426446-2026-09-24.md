### [24/09/2026 13:03:41] Agente

Sí, con esa implementación la comparación queda protegida contra coincidencias parciales:

```sql
@var_origenes_ant =
  ';' + ISNULL(NULLIF(LTRIM(RTRIM(lot.afi_origenes)), ''), '') + ';'
```

y la comparación:

```sql
CHARINDEX(';' + LTRIM(RTRIM(ori)) + ';', @var_origenes_ant) > 0
```

Por ejemplo:

- Lista: `;1;11;`
- Origen `1`: encuentra `;1;`
- Origen `11`: encuentra `;11;`
- Origen `2`: no encuentra coincidencia

En ese caso, **no es necesario cambiar a `LIKE`**. De hecho, `LIKE` sería menos conveniente porque los valores `%`, `_` o `[` tienen significado especial como comodines.

La forma recomendada sería:

```sql
CASE
  WHEN tra.ori IS NULL THEN 'X'
  WHEN CHARINDEX(
         ';' + LTRIM(RTRIM(tra.ori)) + ';',
         @var_origenes_ant
       ) > 0 THEN 'B'
  ELSE 'X'
END
```

También debe verificarse un punto funcional importante: la variable contra la que se compara debe contener los **orígenes seleccionados en la búsqueda actual**. Si `lot.afi_origenes` representa los orígenes del lote anterior, no debe usarse para decidir `B` o `X`, porque el requisito indica comparar el origen anterior contra el filtro actual.

Como alternativa aún más robusta, SQL Server permite comparar tokens mediante `STRING_SPLIT`:

```sql
CASE
  WHEN tra.ori IS NULL THEN 'X'
  WHEN EXISTS
       (
         SELECT 1
         FROM STRING_SPLIT(@prm_origenes, ';') AS s
         WHERE LTRIM(RTRIM(s.value)) = LTRIM(RTRIM(tra.ori))
       ) THEN 'B'
  ELSE 'X'
END
```

Conclusión: con delimitadores en ambos extremos y `CHARINDEX(';' + ori + ';', lista)`, el riesgo técnico de prefijos queda eliminado. El hallazgo sobre `CHARINDEX` debe retirarse si esa es efectivamente la lógica desplegada; el hallazgo independiente sobre actualizar `afi_origenes` antes de confirmar resultados continúa vigente.
