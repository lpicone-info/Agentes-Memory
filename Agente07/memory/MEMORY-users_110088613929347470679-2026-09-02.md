Trazabilidad:


Después:


Y al precargar la cabecera:

```text

```

Ese parámetro 19 entra a:

```text

```

El XML sí aporta estos datos:

```text
<EsCentro>N</EsCentro>              -> auto_remotas.es_centro = N
<CuitPrestador>9999999999</...>     -> auto_remotas.cuit_prestad = 9999999999
<CodigoPrestador></...>             -> efe_prestad = NULL
```

Validé en base que el CUIT `9999999999` no existe en `prestadores`. Entonces el flujo queda así:

1. El WS inserta cabecera con `efe_tipo = C` por configuración.
2. Como `CodigoPrestador` viene vacío, `efe_prestad` queda `NULL`.
3. `prs_valida_of_prestador_remoto` intenta resolver prestador por `cuit_prestad = 9999999999`.
4. No encuentra prestador, entonces rechaza por `18 - Prestador inexistente`.
5. No limpia `efe_tipo`, por eso queda `C` en cabecera aunque el prestador no exista.

Conclusión: `efe_tipo=C` es un default/configuración del WS, no un dato derivado del prestador del XML. Para este XML, el dato funcional que manda es el CUIT inexistente, por eso el rechazo correcto es `18`.
