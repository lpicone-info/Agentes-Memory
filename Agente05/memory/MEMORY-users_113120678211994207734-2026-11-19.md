# 3. Inconsistencias dentro de la EF

## 3.1. Campos obligatorios ausentes

La tabla propuesta `FACT_FACTURAS` declara obligatorios:

```text
fecha_radicacion
tipo_factura
```

Pero el ejemplo de factura con un solo afiliado no contiene esos campos.

Debe definirse si:

- son obligatorios;
- son opcionales;
- se calculan;
- o el ejemplo está incompleto.

## 3.2. Autorización obligatoria, pero ausente

El contrato técnico marca `numero_autorizacion` como obligatorio.

Sin embargo, la factura con un afiliado no informa autorización:

- ni en la factura;
- ni en el afiliado;
- ni en los ítems.

Debe definirse si una factura sin autorización:

- se rechaza como `NO_PROCESABLE`;
- se procesa como inconsistencia;
- o puede continuar con `SIN_AUTORIZACION`.

## 3.3. Autorización de factura no definida

La prioridad requerida es:

```text
ítem → afiliado → factura
```

Pero ninguno de los ejemplos contiene un campo explícito de autorización a nivel factura.

Falta definir su nombre y ubicación en el esquema.

## 3.4. Identificación de afiliado insuficiente

El JSON informa tipo y número de documento, pero PRESMED trabaja con:

```text
prepaga + contra + inte
```

Falta definir:

- entidad/prepaga;
- comportamiento cuando el documento aparece en más de un contrato;
- vigencia utilizada;
- tratamiento de afiliados dados de baja;
- criterio para seleccionar programa y plan.

## 3.5. Nomenclador insuficiente

Los servicios informan:

```text
codigo_prestador
codigo_norma
tipo_item
```

Pero PRESMED necesita determinar, según el proceso:

```text
nomen
prestac
tipo de prestación
```

Falta la matriz de homologación para:

- procedimientos;
- medicamentos;
- insumos;
- códigos sin norma;
- códigos de prestador no homologados.

## 3.6. Diseño de intentos y duplicados

La EF propone una restricción única sobre:

```text
FACT_ARCHIVOS_JSON.hash_archivo
```

Pero también exige registrar un nuevo intento para archivos duplicados y reprocesos.

Si el hash es único en la misma tabla, el segundo intento no podrá insertarse.

La solución debería separar conceptualmente:

```text
Archivo lógico
└── Intentos de procesamiento
```

Esto requiere una tabla de intentos o redefinir la restricción.

## 3.7. Restricción de errores incorrecta

La restricción propuesta:

```text
archivo_id + factura_id + item_id
```

impediría registrar más de un error para el mismo ítem, aunque:

- existan varios errores;
- haya múltiples intentos;
- cambie el componente;
- se produzca un error técnico y otro funcional.

Debe incluir un identificador propio y utilizar índices no únicos para búsqueda.

## 3.8. Transacción distribuida no definida

La EF exige que archivo, factura y expediente constituyan una sola transacción, pero también requiere:

- Google Drive;
- servicios;
- motor de reglas;
- persistencia SQL.

No es viable mantener una transacción SQL abierta incluyendo servicios externos. Debe definirse una estrategia de estados, compensación u outbox.
