**Evaluación de la solución del cliente**
La solución propuesta por el cliente es correcta conceptualmente: validar documento-correo antes de generar/enviar el link y devolver respuestas genéricas. Pero es incompleta si se implementa solo en pantalla o JavaScript.

Debe quedar aplicada en servidor:

1. `controlador/cambio_pass.php` no debe confiar en `email` recibido por POST.
2. `Usuario::enviarMailCambioPass('R')` o el SP `aru_cambio_contrasena_gis` debe validar que el documento exista y que el correo destino sea el registrado.
3. La respuesta debe ser genérica tanto para éxito como para rechazo.
4. Corregir generación de URL para usar `/gis/` consistente y preferentemente `https`.
5. El reset no debería enviar `password_old`; para restablecimiento debe viajar nulo/omitido.
6. El token debería tener expiración real validada en servidor y no depender solo del contenido cifrado del link.

**Riesgo**
Crítico: con documento real, un atacante puede forzar envío de link a un correo propio si llama directo al endpoint vulnerable.
