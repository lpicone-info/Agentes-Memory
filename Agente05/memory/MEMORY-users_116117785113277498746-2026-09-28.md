## Solución propuesta

### 1. Mantener la clave primaria actual

```text
PK_AFI_PLANES = (prepaga, contra, vigen_desde)
```

Debe continuar utilizándose para:

- Localizar un registro específico.
- Modificarlo.
- Darlo de baja.
- Relacionarlo con otros procesos administrativos.
- Auditar su historia.

### 2. Utilizar `VIGEN_COBER` solamente para seleccionar la cobertura

```sql
SELECT TOP (1)
       prepaga,
       contra,
       vigen_desde,
       vigen_cober,
       plan_codi
FROM AFI_PLANES
WHERE prepaga = @prepaga
  AND contra = @contra
  AND vigen_cober <= @fecha_evaluacion
ORDER BY vigen_cober DESC,
         vigen_desde DESC
```

El resultado devuelve:

- El programa vigente.
- Su fecha efectiva.
- `VIGEN_DESDE`, necesario para identificar inequívocamente el registro.

### 3. Las actualizaciones deben utilizar la PK recuperada

Una vez seleccionado el registro por cobertura, cualquier modificación debe realizarse mediante:

```sql
WHERE prepaga = @prepaga
  AND contra = @contra
  AND vigen_desde = @vigen_desde_seleccionado
```

Nunca mediante `VIGEN_COBER` solamente.

## Centralizar la selección

Conviene implementar una única función o Stored Procedure, por ejemplo:

```text
prs_afi_plan_vigente
```

Parámetros:

- `@prepaga`.
- `@contra`.
- `@fecha_evaluacion`.

Resultado:

- `plan_codi`.
- `vigen_cober`.
- `vigen_desde`.
- Estado de la determinación.

Todos los procesos de Ambulatorio, Cirugía, Hospitalización, IVR y GIS deberían consumir esta operación, evitando que cada procedimiento implemente una selección diferente.

## Índice recomendado

Para evitar degradación de rendimiento:

```sql
CREATE INDEX IX_AFI_PLANES_COBERTURA
ON AFI_PLANES
(
    prepaga,
    contra,
    vigen_cober DESC
)
INCLUDE
(
    vigen_desde,
```

No reemplaza la PK; solamente optimiza la búsqueda por cobertura efectiva.

Un índice `UNIQUE` sobre `(prepaga, contra, vigen_cober)` solo sería conveniente si se confirma funcionalmente que nunca pueden existir dos versiones administrativas con la misma fecha efectiva.
