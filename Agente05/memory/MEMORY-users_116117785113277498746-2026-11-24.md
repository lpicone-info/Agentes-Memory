# 1. Bloqueos críticos

## 1.1 No está definida la unión entre `FACT_*` y `EXPE_*`

La EF obtiene el detalle desde:

```text
FACT_FACTURAS
→ FACT_FACTURA_AFILIADOS
→ FACT_FACTURA_ITEMS
```

Pero las glosas y la operatoria existente utilizan:

```text
EXPEDIENTES
→ EXPE_ORDENES
→ EXPE_ORDEN_ITEMS
→ EXPE_ERRORES
```

No se explica cómo un registro:

```text
FACT_FACTURA_ITEMS.item_id
```

o:

```text
FACT_FACTURA_ITEMS.numero_item
```

se relaciona inequívocamente con:

```text
EXPE_ORDEN_ITEMS.ofi
EXPE_ORDEN_ITEMS.expe
EXPE_ORDEN_ITEMS.item
EXPE_ORDEN_ITEMS.orden
```

### Impacto

El programador no puede garantizar que una glosa iniciada desde una fila de `FACT_FACTURA_ITEMS` quede asociada al registro correcto de `EXPE_ORDEN_ITEMS`.

### Corrección requerida

Incorporar una relación física o una regla completa:

```text
factura_id
+ factura_afiliado_id
+ item_id
↔
ofi
+ expe
+ item
+ orden
```

Debe indicarse:

- tabla o vista de relación;
- claves;
- cardinalidad;
- comportamiento cuando no existe correspondencia;
- comportamiento cuando existen varias coincidencias.

---

## 1.2 Identificación incompleta de la factura

La EF propone:

```text
NIT del prestador + número de factura
```

y menciona `factura_id` cuando esté disponible.

Esto no resuelve inequívocamente:

- dos radicaciones de la misma factura;
- factura corregida;
- mismo prestador/número en entidades diferentes;
- factura asociada a otro expediente;
- duplicidad histórica.

### Regla recomendada

La consulta debería partir del contexto activo:

```text
expediente_id + factura_id
```

Después debe validar:

```text
prestador_id/NIT + numero_factura
```

Si la combinación no coincide con el expediente desde el cual se abrió la pantalla, debe detenerse la carga y registrar una inconsistencia.

---

## 1.3 Identidad incompleta de autorización

El filtro y la relación funcional utilizan:

```text
numero_autorizacion_item
```

Pero un número de autorización puede no ser globalmente único. PRESMED puede requerir entidad, sucursal y número, o directamente un identificador interno.

### Corrección requerida

Separar:

- identificador técnico de autorización;
- entidad;
- sucursal;
- número visible.

La relación debería utilizar:

```text
autorizacion_id
```

y mostrar:

```text
numero_autorizacion
```

Cuando el número visible se repita, la lista debe diferenciarlos sin mezclar ítems. El filtro no debe agrupar autorizaciones distintas únicamente porque compartan el mismo número textual.

---

## 1.4 Relación autorización–ítem contradictoria

Actualmente aparecen tres fuentes:

```text
FACT_FACTURA_ITEMS.numero_autorizacion_item
FACT_FACTURA_AFILIADOS.numero_autorizacion
FACT_ITEM_AUTORIZACIONES.numero_autorizacion
```

No se define cuál prevalece cuando:

- el ítem y el afiliado informan autorizaciones diferentes;
- existe número en el ítem, pero no relación en `FACT_ITEM_AUTORIZACIONES`;
- una relación tiene `autorizacion_id`, pero el número no coincide;
- el ítem no tiene autorización y el afiliado sí.

### Regla recomendada

Para RM30419, que es una consulta, debería utilizarse como relación definitiva:

```text
FACT_ITEM_AUTORIZACIONES.item_id
+ FACT_ITEM_AUTORIZACIONES.autorizacion_id
```

`numero_autorizacion_item` debería mantenerse como dato recibido y visible, pero no como única clave técnica.

Si no existe relación, el ítem debe mostrarse como inconsistente o “Sin autorización”; no debe heredarse automáticamente una autorización del afiliado sin una regla explícita.

## 1.5 Fuentes económicas sin prioridad única

La EF utiliza simultáneamente:

- `FACT_FACTURAS.valor_total_factura`;
- suma de `FACT_FACTURA_ITEMS.valor_total_item`;
- `EXPEDIENTES.total`;
- `EXPE_CUENTAS_COBRO.total`;
- `EXPE_ORDEN_ITEMS.real_valor`;
- `EXPE_ORDEN_ITEMS.ingre_valor`;
- `EXPE_ORDENES.ingre_orden`;
- `EXPEDIENTES.debito`;
- `EXPE_ERRORES.real_valor`;
- `dbo.afn_glosas`;
- `dbo.prs_detalle_glosas`.

No establece cuál es la fuente canónica de cada cálculo.

### Problemas concretos

- No se define cuándo usar `EXPEDIENTES.total` y cuándo `EXPE_CUENTAS_COBRO.total`.
- La base de autorización puede ser `real_valor`, `ingre_valor` o `ingre_orden`.
- No queda probado que `dbo.afn_glosas` produzca el mismo resultado que la suma mostrada.
- Existe riesgo de contar dos veces una glosa incluida por un procedimiento y sumada nuevamente desde tablas.
- No se define tratamiento de copagos dentro del neto.

### Corrección requerida

Agregar una matriz de precedencia:

| Cálculo | Fuente única | Alternativa | Condición |
|---|---|---|---|
| Valor factura recibido | `FACT_FACTURAS.valor_total_factura` | Ninguna | Dato original |
| Valor ítems | `SUM(FACT_FACTURA_ITEMS.valor_total_item)` | Ninguna | Control de integridad |
| Base liquidable factura | A confirmar | A confirmar | Regla PRESMED |
| Base autorización | A confirmar | A confirmar | Regla PRESMED |
| Glosa general | `EXPEDIENTES.debito` | Ninguna | Vigente |
| Glosas por ítem | A confirmar | Ninguna | Evitar duplicación |
| Neto factura | Fórmula única | `dbo.afn_glosas` si es la fuente oficial | A confirmar |

## 1.6 El origen automático/manual de la glosa no puede identificarse

La EF exige un indicador visual diferencial para glosas automáticas, pero declara que el modelo vigente no posee un discriminador.

### Impacto

La pantalla no puede implementar de forma confiable el indicador solicitado.

### Opciones de cierre

1. Incorporar un campo `origen_glosa`.
2. Crear una relación con la ejecución del Motor de Reglas.
3. Definir una regla técnica inequívoca existente.
4. Eliminar el indicador diferencial y mostrar todas las glosas de la misma forma.

Mientras no se seleccione una alternativa, este requisito no es implementable.

---

## 1.7 “Factura Revisada” no puede recuperarse al reabrir

La EF define el check como transitorio y sin campo independiente. Al mismo tiempo:

- “Salir” guarda las modificaciones;
- la auditoría puede retomarse;
- debe quedar trazabilidad del estado;
- el check es obligatorio para cerrar.

`EXPEDIENTES.audi_fecha` representa finalización, no necesariamente una factura marcada y todavía no cerrada.

### Corrección requerida

Persistir explícitamente:

```text
factura_revisada
factura_revisada_usuario
factura_revisada_fecha
```

o registrar una actividad inequívoca de “FACTURA_REVISADA” que pueda reconstruir el estado.

No debería inferirse el check desde la fecha de cierre porque esa fecha se genera después de validar el control.

---

## 1.8 Transacciones, concurrencia e idempotencia

No se define qué ocurre cuando:

- dos auditores abren la misma factura;
- ambos registran glosas;
- uno envía a Supervisión mientras el otro continúa;
- se presiona dos veces “Envío a Revisión”;
- se produce un error después de guardar glosas, pero antes de cambiar el estado;
- falla una parte del cierre;
- se abandona la sesión.

### Corrección requerida

Definir:

- bloqueo pesimista u optimista;
- versión o fecha de última modificación;
- validación del estado antes de guardar;
- transacción única para glosas + auditoría + cambio de estado;
- rollback;
- idempotencia de los botones;
- mensaje de conflicto;
- prohibición de modificar una factura ya enviada.

---

## 1.9 Continuidad hacia Supervisión incompleta

La EF indica que Supervisión debe consultar:

- las mismas glosas;
- las relaciones con autorización e ítem;
- los valores netos resultantes.

Sin embargo, los valores netos se describen como calculados y sin persistencia independiente.

### Decisión requerida

Definir una de estas alternativas:

1. Persistir un snapshot económico al finalizar Auditoría.
2. Recalcular en Supervisión utilizando exactamente las mismas fuentes y versión de reglas.

Si se recalcula, debe garantizarse que las glosas y bases económicas no cambien retrospectivamente. Para auditoría, recomiendo persistir el resultado de cierre y conservar además la posibilidad de recalcularlo.

# 2. Inconsistencias funcionales

## 2.1 “Factura Revisada” para Envío a Revisión

El flujo narrativo indica que el auditor certifica la revisión completa antes de finalizar. Sin embargo:

- “Cerrar Auditoría” exige el check.
- “Envío a Revisión” solo exige glosas mayores a cero.

Esto permitiría enviar una factura con glosas sin certificar que fue revisada completamente.

### Debe definirse

Recomiendo exigir `Factura Revisada = Sí` para ambas salidas:

```text
Cerrar Auditoría:
Factura Revisada = Sí
AND Total glosas = 0

Envío a Revisión:
Factura Revisada = Sí
AND Total glosas > 0
```

---

## 2.2 Código del prestador inconsistente

El requerimiento contiene referencias incompatibles:

- En algunas partes exige “Código prestador”.
- En la definición formal de la grilla no aparece esa columna.
- La EF muestra “Servicio facturado”, pero no `codigo_prestador`.
- El criterio de aceptación vuelve a mencionar “Código prestador”.
- La lectura del mockup lo ubica dentro de los datos de factura.

Debe aclararse si “Código prestador” significa:

1. código interno del prestador en la cabecera; o
2. `FACT_FACTURA_ITEMS.codigo_prestador`, correspondiente al servicio facturado.

Si corresponde al ítem, debe agregarse como columna visible separada antes de “Servicio facturado”.

---

## 2.3 Fuente del programa del paciente

La EF afirma que el programa es propio del usuario y debe mantenerse igual en todos sus servicios, pero lo recupera desde:

```text
EXPE_ORDENES.plan_codi
```

Esto lo vincula a la orden/autorización, no necesariamente al afiliado de la factura.

RM30414 propone `FACT_FACTURA_AFILIADOS.programa_id`, lo cual sería más consistente con el concepto de programa por usuario.

### Debe elegirse una fuente

- Programa persistido por afiliado en `FACT_FACTURA_AFILIADOS`; o
- programa de la autorización/orden.

También debe definirse qué mostrar cuando un mismo usuario tenga órdenes de programas diferentes.

---

## 2.4 Ítem sin usuario

La EF conserva el registro y genera una novedad, pero deja pendiente:

- si se permite glosarlo;
- si participa en totales;
- si bloquea cierre;
- si puede pasar a Supervisión;
- cómo se presenta en filtros;
- qué mensaje aparece.

### Recomendación

- Mostrar el ítem.
- Incluirlo en los totales estructurales.
- Identificarlo como `USUARIO_NO_ASOCIADO`.
- Impedir finalizar Auditoría hasta resolver o aceptar formalmente la inconsistencia.
- No asignar otro usuario por inferencia.

---

## 2.5 Cantidad nula convertida a uno

El requerimiento dice que una cantidad nula debe tomar valor `1`, pero también exige no modificar los datos originales.

Debe diferenciarse:

```text
cantidad_recibida = NULL
cantidad_utilizada = 1
regla_aplicada = CANTIDAD_POR_DEFECTO
```

No debería sobrescribirse silenciosamente el valor original.

---

## 2.6 Alcance de los filtros sobre totales y glosas

No está completamente definido qué se actualiza al aplicar filtros complementarios.

Debe aclararse:

- Los totales globales de factura no cambian.
- El resumen de autorización corresponde a toda la autorización, no solamente a los ítems visibles por usuario/tipo.
- La grilla sí aplica todos los filtros combinados.
- La lista de glosas debe definirse como global o filtrada.
- “Sin autorización” debe tener su propio resumen de ítems y valores.
- El botón Limpiar debe restablecer todos los filtros.

Actualmente el criterio de aceptación menciona “Limpiar”, pero la botonera de la EF no lo define.

---

## 2.7 Criterios de búsqueda no definidos

Falta precisar:

- combinación mediante `AND` u `OR`;
- búsqueda exacta o parcial;
- sensibilidad a mayúsculas;
- tratamiento de espacios;
- ceros iniciales;
- búsqueda por autorización visible o ID interno;
- comportamiento al pulsar Enter;
- valor inicial al reabrir.

Recomiendo combinar filtros mediante `AND` y preservar todos los identificadores como texto.

---

## 2.8 Orden y duplicidad de `numero_item`

La EF ordena por `numero_item`, pero no define:

- qué ocurre con valores repetidos;
- valores nulos;
- valores alfanuméricos;
- criterio secundario de orden.

Debe utilizarse `item_id` como desempate técnico sin modificar el número visible.

---

## 2.9 Sin paginación y sin límite de volumen

La exigencia de cargar todos los registros en una sola grilla puede degradar la ventana ante facturas extensas.

Debe establecerse:

- volumen máximo esperado;
- tiempo máximo de carga;
- recuperación por bloques o DataWindow virtual;
- indicador de carga;
- comportamiento ante miles de ítems.

Puede mantenerse la experiencia “sin paginación visible” utilizando recuperación técnica incremental.

# 3. Errores y faltantes técnicos

## 3.1 Modelo `FACT_*` todavía se presenta como propuesto

La sección 4.5 solo referencia RM30414. No confirma si las estructuras:

- existen;
- serán creadas;
- son staging;
- son vistas;
- pertenecen a la misma base;
- son accesibles transaccionalmente desde PRESMED.

La EF debe ser autosuficiente o referenciar una definición técnica aprobada y versionada.

---

## 3.2 Integración excluida, pero necesaria como dependencia

El requerimiento excluye correctamente la definición concreta de API o transporte. Sin embargo, el desarrollo de RM30419 necesita, como mínimo, un contrato entregado por Arquitectura con:

- mecanismo;
- autenticación;
- operación de consulta;
- parámetros;
- respuesta;
- errores;
- timeout;
- disponibilidad;
- correlación;
- versión.

No es necesario incluir toda la arquitectura en la EF, pero sí registrar este documento como **dependencia previa al desarrollo**.

---

## 3.3 Trazabilidad de apertura no garantizada

La EF afirma que debe conservarse:

- usuario;
- fecha y hora de apertura;
- resultado de integración.

Pero luego indica que no existe un registro independiente de apertura y que `EXPE_AUDITORIA` se actualiza cuando se registra actividad.

Eso no garantiza la trazabilidad mínima solicitada.

Debe registrarse una actividad explícita de consulta, por ejemplo:

```text
APERTURA_DETALLE_FACTURA
```

con usuario, fecha, expediente, factura y resultado.

---

## 3.4 Estado activo no definido

El acceso requiere expediente y factura “activos”, pero no define:

- estados habilitados;
- tratamiento de `baja_fecha`;
- factura ya auditada;
- factura en Supervisión;
- factura liquidada;
- expediente cerrado;
- expediente abierto por otro auditor.

Debe agregarse una matriz de estados habilitados.

---

## 3.5 Falta una máquina de estados

La EF menciona Auditoría, Revisión y Supervisión, pero no define formalmente:

```text
estado origen
acción
validación
estado destino
campos actualizados
actividad registrada
```

Esta matriz es necesaria para “Envío a Revisión”, “Cerrar Auditoría” y reapertura.

---

## 3.6 Dependencia del requerimiento Registro de Glosas

Está correctamente fuera del alcance definir toda la captura de glosas. Sin embargo, RM30419 necesita un contrato mínimo con ese requerimiento:

- operación invocada;
- datos de contexto enviados;
- resultado devuelto;
- momento de recálculo;
- cancelación;
- modificación;
- eliminación/anulación;
- permisos;
- evento que actualiza la pantalla.

Sin ese contrato, el ícono de glosa y el recálculo inmediato quedan incompletos.

---

## 3.7 Manejo de errores sin resolución operativa

La EF define mensajes, pero no indica:

- quién atiende la novedad;
- cómo se marca como resuelta;
- si se reintenta;
- cuándo vuelve a habilitarse la factura;
- dónde se consulta el error;
- qué identificador se entrega al usuario.

Debe diferenciar error técnico, inconsistencia de datos y restricción funcional.

# 4. Problemas documentales

## 4.1 Mockup contradictorio

La sección se denomina:

```text
Mockup funcional aprobado
```

pero la figura indica:

```text
Mockup pendiente de actualización
```

Debe existir una única condición: aprobado o pendiente. Mientras esté pendiente, la disposición visual no puede considerarse criterio definitivo.

## 4.2 Historial y aprobación

El archivo fue actualizado, pero debe verificarse que:

- historial de revisión refleje la versión actual;
- fecha y descripción del cambio estén actualizadas;
- aprobaciones estén completas;
- lista de distribución esté completa;
- anexos referencien el requerimiento y RM30414;
- aprobación final esté registrada.

Las tablas de aprobación y anexos continúan vacías.

## 4.3 Criterios de aceptación

El requerimiento contiene una lista extensa de aceptación, pero la EF no la incorpora como matriz trazable.

Debe incluir:

| ID | Requisito | Precondición | Acción | Resultado esperado | Evidencia |
|---|---|---|---|---|---|

Casos mínimos:

- factura con un usuario;
- factura multiusuario;
- varias autorizaciones;
- sin autorización;
- sin código normalizado;
- ítem sin usuario;
- autorización repetida;
- diferencia económica;
- glosa automática;
- glosa manual;
- glosa general;
- cambio de filtros;
- reapertura;
- concurrencia;
- doble ejecución;
- cierre sin glosas;
- envío con glosas;
- error de integración;
- continuidad a Supervisión.

## 4.4 Validación repetida

La diferencia entre total de ítems y valor facturado aparece más de una vez en las validaciones. Debe consolidarse en una sola regla con:

- fórmula;
- tolerancia;
- mensaje;
- bloqueo;
- persistencia de la novedad.

# 5. Aspectos correctamente cubiertos

No requieren redefinición sustancial:
