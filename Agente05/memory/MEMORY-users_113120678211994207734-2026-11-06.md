## Paso 5.6 — Solicitar el bloqueo lógico

Inmediatamente después:


Interpretación:

| Resultado | Significado |
|---:|---|
| `0` | Bloqueo obtenido inmediatamente |
| `1` | Bloqueo obtenido después de esperar |
| `-1` | Timeout |
| `-2` | Solicitud cancelada |
| `-3` | Víctima de deadlock |
| `-999` | Error de parámetros o llamada |

Como usamos:

```text

```

la segunda sesión no debería esperar. Recibirá resultado negativo inmediatamente.

# 7. Análisis del riesgo de bloqueo

## ¿Bloqueará todo el aplicativo?

No.

`sp_getapplock` no bloquea tablas completas. Bloquea un recurso lógico reconocido solamente por sesiones que también soliciten ese recurso.

## ¿Bloqueará otras solicitudes?

No.

Cada `soli_auto` genera un recurso diferente.

## ¿Bloqueará la bandeja?

No por el bloqueo lógico.

La bandeja no solicita:

```text
SOLI_AUTO_NOTIF_FINAL|<solicitud>
```

Por tanto, no compite por ese lock.

## ¿Bloqueará la misma solicitud?

Solamente impedirá que dos sesiones generen simultáneamente la notificación final de esa solicitud.

Además, como el timeout es cero, la segunda sesión no queda esperando.

## ¿Puede haber bloqueos normales de SQL?

Sí, durante unos milisegundos o pocos segundos pueden existir locks normales por:

- `INSERT` en `MAIL_ENVIO`.
- `INSERT` en `MAIL_TO`.
- `INSERT` en `MAIL_ATTACH_BINARY`.
- `INSERT` en auditoría.
- Actualización de `SOLICITUDES_AUTO.mail_id_afi_mail`.

Esos locks ya existen en el proceso actual. No son creados específicamente por `sp_getapplock`.

## ¿Puede producir deadlock?

El riesgo es bajo si todos los llamadores usan el mismo orden:

```text
sp_getapplock
Validar duplicados
Insertar mail
Insertar destinatario
Insertar relación
Insertar adjuntos
Actualizar status
Auditar
COMMIT
```

No se debe adquirir primero un lock de tablas y después el `sp_getapplock`, porque invertir el orden entre sesiones sí podría aumentar el riesgo de deadlock.

# 8. Medidas adicionales para reducir impacto

1. Mantener `LockTimeout = 0`.
2. Preparar PDF y API antes del bloqueo.
3. Tener el índice:

```text
SOLICITUDES_AUTO_NOTIFICACIONES
    soli_auto
    proceso_id
    baja_fecha
```

4. Usar el índice existente de auditoría por `soli_auto`. Está definido en [SOLICITUDES_AUTO_AUDITORIA.sql](/home/desarrollo-ia-05/.openclaw/workspace/svn/whiguera-Version84-Modelo2Gis/backend/tables/SOLICITUDES_AUTO_AUDITORIA.sql:14).
5. No mostrar ventanas ni pedir confirmaciones dentro de la transacción.
6. No hacer llamadas HTTP ni subir adjuntos dentro de la transacción.
7. No usar `WAITFOR`.
8. No utilizar un recurso global como:
   ```text
   SOLI_AUTO_NOTIF_FINAL
   ```
   sin el número de solicitud, porque eso serializaría todas las notificaciones.
