# 4. Problemas del modelo de base de datos propuesto

## Restricción por hash contradictoria

Se mantiene:

```text
UQ_FACT_ARCHIVOS_JSON_HASH
```

Pero la EF exige registrar varios intentos del mismo archivo. Un hash único impediría insertar el segundo intento.

## Errores múltiples bloqueados

Se propone:

```text
UQ_FACT_ARCHIVOS_JSON_ERRORES
(archivo_id, factura_id, item_id)
```

Esto impediría registrar dos errores para el mismo ítem, aunque exista `intento_id`.

## No existe una entidad física de intentos

Se utilizan:

```text
intento_numero
intento_id
archivo_origen_id
```

pero no existe una tabla consistente de intentos ni una FK que relacione conciliaciones y errores con un intento real.

## Claves incompatibles con PRESMED

Se proponen identificadores simples:

```text
prestador_id
afiliado_id
expediente_id
autorizacion_id
```

pero el modelo real utiliza claves compuestas. Falta el mapeo físico definitivo.

## Estados inconsistentes

La secuencia utiliza estados que no aparecen en el catálogo:

```text
INICIADO
YA_PROCESADO
PARCIAL_RECUPERABLE
```

El catálogo presenta otros:

```text
RECIBIDO
EN_PROCESO
DUPLICADO
```

## Transacción no viable como está redactada

La V2 mantiene que archivo, factura y expediente son una única transacción y ubica dentro del flujo:

- Google Drive;
- consultas externas;
- motor de reglas;
- SQL.

No debe mantenerse una transacción SQL abierta durante llamadas externas. Falta definir límites transaccionales, estados de recuperación u outbox.
