Walter, el `recalcula = 'S'` lo pone el SP `afs_compro_exportacion`, no PowerBuilder.

Está en `backend/procedures/afs_compro_exportacion.sql`, dentro del bloque BBVA:

- Primero arma `#compro_recalculo` con `recalcula = 'N'` por defecto, líneas 1357-1389.
- Después, si el menor vencimiento es menor que la fecha de débito (`IF @var_min_vto < @fecha_debito`), recalcula el flag en el `UPDATE #compro_recalculo`, líneas 1406-1424.
- Ahí pone:
  - `V` si la fecha de débito cae entre vencimientos (`vto`/`vto2` o `vto2`/`vto3`)
  - `N` si `@fecha_debito <= vto`
  - `S` si `@fecha_debito` es mayor al último vencimiento disponible: `WHEN @fecha_debito > IsNull(Isnull(vto3, vto2), vto) THEN 'S'`
- Luego copia ese valor a `#comprobantes.recalcula`, líneas 1458-1463.
- Finalmente el DataWindow detalle devuelve ese campo, líneas 1730-1746.

En este caso, si todos vienen en `N`, entonces el filtro de PB:

`dw_list_det.SetFilter('recalcula = "S" ')`

deja la DW sin filas. El bug no es que no haya `S`; eso es válido. El bug es que después de usar ese filtro temporal para preguntar por recalculo, si no encuentra filas, no hace `SetFilter('')` + `Filter()` para restaurar `dw_list_det`.

En `wp_export_debitos.srw`, cuando encuentra `recalcula = "S"`:

1. Filtra `dw_list_det` por `recalcula = "S"`.
2. Si hay filas, muestra el mensaje: “Existen comprobantes que vencen antes de la Fecha Débito ingresada. El sistema aplicara los intereses. ¿Confirma que desea continuar?”
3. Si el usuario acepta, habilita exportar.
4. Después limpia el filtro.

O sea: para los `S`, el sistema **pide confirmación**, pero no los bloquea ni los excluye.

La causa del bug sigue siendo que cuando no hay ningún `S`, el filtro queda aplicado y deja `dw_list_det` en 0 filas.
