## Origen histórico del desajuste

El comportamiento se introdujo en la revisión **r78465**, del **17/10/2024**, correspondiente al **RM26403**:

> Portal Prestadores - Autorización de Int. Clínica (02I) no guarda la cantidad correcta.

Ese cambio hizo dos modificaciones relacionadas:

```diff
- SET @dias = 1
+ -- SET @dias = 1
```

y:

```diff
- SELECT ..., 1, ...
+ SELECT ..., @dias, ...
```

La intención fue respetar la cantidad real de días recibida desde el Portal de Prestadores. Sin embargo, el WAR `auto_remotas` continúa enviando el parámetro `@dias` como `NULL`.

Por lo tanto, quedó una incompatibilidad entre ambos circuitos:

| Circuito | Cantidad de días |
|---|---|
| Portal de Prestadores | Puede enviar la cantidad ingresada |
| WAR `auto_remotas` | Envía siempre `NULL` |
| Procedimiento actual | Espera utilizar el valor recibido |
| `AUTO_SALAS` | Exige obligatoriamente un valor no nulo |

## Evidencia del intento en la base

Los dos intentos más recientes quedaron registrados así:

| Transacción | Autorización | Tipo | `AUTO_REMOTAS.dias` | Sala | Estado | Registro en `AUTO_SALAS` |
|---:|---:|---|---:|---:|---|---|
| 1215955 | 868428 | 02I | `NULL` | 1 | Aceptada | No |
| 1215956 | 868429 | 02I | `NULL` | 1 | Aceptada | No |

Ambos corresponden a:

```text
Referencia: 304340504
Prestador: 7456
Lugar: 1
Fecha de internación: 09/10/2026
```

Esto también evidencia un efecto secundario importante: la conexión del WAR trabaja con `autoCommit = true`. La autorización se genera y queda aceptada antes de fallar el alta de `AUTO_SALAS`. Por eso, aunque el servicio responde con error, quedaron autorizaciones creadas parcialmente y los reintentos generaron nuevas autorizaciones.

## Conclusión

El error **no se debe a que `InterSala` sea inválida**: el valor `1` se interpreta y se guarda correctamente.

La causa es:

1. El XML no informa días.
2. El WAR tampoco tiene lógica para obtenerlos del XML y envía `@dias = NULL`.
3. Desde el RM26403, `pri_auto_remotas` dejó de reemplazar ese nulo por `1`.
4. `prs_valida_of_auto_remotas` conserva el nulo.
5. El procedimiento intenta insertarlo en `AUTO_SALAS.dias`, campo obligatorio.

Es, por lo tanto, un desajuste entre el WAR de transacciones remotas y el tratamiento incorporado para respetar los días enviados por otros circuitos.
