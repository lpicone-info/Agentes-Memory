Backend: `pri_transac_webpos_total`, `02A -> pri_transac_remotas`, `02D -> pri_transac_remotas_dif`; esta valida 15 dias y delega a `pri_transac_remotas`. Error 700 = fecha invalida.

Ejemplo prestador `722` tipo C/circulo medico no puede informar por `02A/02D`; usar `02Q` si es cirugia o efector de tipo no C para prestacion comun/odontologica. No cambiar tipo global del prestador salvo decision funcional.
- Query odontologia: para detectar prestadores aptos conviene cruzar `carti_convenios -> prestadores -> convenios -> conve_prestaciones -> odon_prestac -> prestaciones -> planes -> cartillas -> coberturas`, con `baja_fecha IS NULL`, `p.tipo <> 'C'`, opcional `@plan_codi`, mostrando `op.nomen`, `op.prestac`, `pr.exten_deno`, `op.practica`, `op.aplica`, `op.cant_max`. No asumir `nomen=15`; en esta base hay odontologicas en `odon_prestac` incluso con `nomen=10`.
- Caso cirugia portal: auto `1/221`, transaccion `617`, tipo `02Q`, prestacion `020405 - CAUTERIZACION CORNEAL`, sanatorio `47`. Auto aceptada, cantidad autorizada 2, informada 1, saldo 1, nomenclador quirurgico correcto (`nomencladores.carac=4`), efector sanatorio coincide. Rechazo real por afiliado/morosidad/DDJJ: `afi_morosidad_estado` para `prepaga=1`, `contra='216039'`, fecha `20260803`, `tipo='C'`, `condicion='P'`, `cod_interno='P'` devuelve `error=2`, estado `Cantidad de Declaraciones Juradas Insuficientes`; analisis DDJJ: `APORTE INFERIOR AL MINIMO PRESTACIONAL`. Solucion funcional: regularizar contrato/afiliado por DDJJ/aportes o probar con afiliado sin restriccion.
- Bug tecnico detectado: `prs_valida_of_afiliado_remoto` detecta `@r_erro = 2`, pero al actualizar rechazo usa `@error` NULL. Por eso portal muestra rechazado sin mensaje. Fix sugerido: asignar `@error = @r_erro` antes del `UPDATE` final de rechazo en ese SP.
