## Filtros aplicados

Una autorización solamente se devuelve cuando:

```text
AUTORIZACIONES.prepaga = entidad consultada
AUTORIZACIONES.contra = contrato consultado
AUTORIZACIONES.nro_pedido = pedido informado, si se informó
AUTORIZACIONES.baja_fecha IS NULL
AUTORIZACIONES.impre_fecha IS NOT NULL
AUTORIZACIONES.vali_fecha >= fecha actual
AUTORIZACIONES.esta IN ('A', 'R')
```

Por lo tanto, el SP excluye:

- Autorizaciones dadas de baja.
- Autorizaciones todavía no impresas.
- Autorizaciones vencidas.
- Autorizaciones pendientes.
- Autorizaciones con estados diferentes de aceptada o rechazada.

Aunque la traducción contempla “Sin autorización”, “En trámite” y “No requiere autorización”, el origen principal de la consulta es `AUTORIZACIONES`. En consecuencia, un pedido que no tenga ninguna autorización asociada no puede aparecer en el resultado.

## Cardinalidad de la relación

La relación entre una autorización y sus ajustes no está definida como única.

El índice existente es:

```sql
CREATE INDEX ik_ajuste_auto
ON ajustes(ori_sucur, ori_auto)
```

No es un índice `UNIQUE`: [ajustes.sql:32](</home/desarrollo-ia-07/.openclaw/workspace/svn/mpariso-V25.08.001/backend/tables/ajustes.sql:32>).

Por lo tanto:

- Una autorización puede tener más de un ajuste vigente.
- Cada ajuste puede generar una fila diferente para la misma autorización.
- Esta posible duplicación ya existe por el `LEFT JOIN` actual.
- Incorporar `aju` no crea la duplicación, pero permite identificar cuál de los ajustes originó cada fila.

No sería correcto usar `MAX(AJ.aju)` o `TOP 1` sin una definición funcional, porque podría asociarse un ajuste distinto del comprobante informado.
