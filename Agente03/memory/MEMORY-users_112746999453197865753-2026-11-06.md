## 5. Cómo se almacenan las claves

### `zz_usuari`

- `pwd_encript` contiene un **hash SHA-1**.
- No es texto plano ni cifrado reversible.
- SHA-1 es un algoritmo obsoleto y débil para almacenar contraseñas porque no utiliza salt ni un algoritmo adaptativo.
- Los usuarios tipo `S` tienen además su contraseña real administrada por SQL Server.
- La columna heredada `pwd`, utilizada para usuarios web, contiene una sustitución de caracteres reversible implementada por PowerBuilder. No es texto plano, pero tampoco constituye cifrado seguro.

### `zz_usuari_api`

- Tipo `I`: hash SHA-1, no reversible, pero criptográficamente débil.
- Tipo `E`: Base64 almacenado como `VARBINARY`; es completamente reversible y **no debe considerarse cifrado**.

### `conexion.ini`

En modalidad SQL, `username` y `password` se leen directamente del INI. En modalidad AD el código aplica desencriptación a esos datos de conexión.

## Conclusión

- La función masiva sirve para forzar claves individuales, pero **sólo debe aplicarse a usuarios tipo `S`**.
- `zz_usuari_api` requiere administración SQL y coordinación directa con cada integración.
- ADMIN puede funcionar sin `sa` mediante un login técnico con permisos de administración suficientes.
- El almacenamiento actual combina SQL Server, SHA-1, cifrado reversible heredado y Base64; varios mecanismos necesitan revisión de seguridad.

# Especificación: Excluir autorizaciones rechazadas (estado 'R' en cabecera) del cálculo de topes

## 1. Objetivo

Al validar topes sobre la **autorización que se está cargando**, el cálculo que acumula las **autorizaciones históricas** del afiliado **no debe tener en cuenta las autorizaciones cuya cabecera esté en estado 'R' (Rechazada)**.

Una autorización rechazada no genera consumo, por lo tanto no debe sumar al tope ni provocar que una autorización nueva quede bloqueada o advertida por exceso de tope.

## 2. Comportamiento actual vs esperado

| | Comportamiento |
|---|---|
| **Actual** | Al cargar una autorización, el cálculo de topes suma las autorizaciones históricas **incluyendo las que tienen cabecera en estado 'R'**. Una autorización nueva puede quedar bloqueada o advertida por topes que en realidad incluyen consumos rechazados. |
| **Esperado** | El cálculo de topes excluye las autorizaciones históricas con cabecera en estado 'R'. La validación sobre la carga actual se sigue haciendo igual, pero con el acumulado sin las rechazadas. |

## 3. Reglas de negocio

**RN-01:** En el cálculo de topes, las autorizaciones históricas cuya cabecera tenga estado 'R' no se suman al acumulado (ni cantidades, ni importes, ni ningún otro concepto que se use para el tope).
**RN-02:** Las autorizaciones históricas en cualquier otro estado se siguen considerando igual que hoy.
**RN-03:** La validación de topes sobre la autorización que se está cargando se mantiene; solo cambia el acumulado histórico contra el que se compara.
