Marcelo, **SQL Server Service Broker** es el sistema nativo de mensajería y colas del motor SQL Server. Permite desacoplar procesos mediante mensajes persistentes y transaccionales, sin instalar RabbitMQ, Kafka u otro broker externo.

## Versión mínima

- Disponible desde **SQL Server 2005 (9.x)**.
- En **SQL Server 2025**, tiene soporte completo en **Standard y Enterprise**.
- **Express:** sólo puede actuar como cliente; no admite toda la funcionalidad de servidor ni crear endpoints.
- También está disponible en **Azure SQL Managed Instance**.
- No requiere `compatibility level 170`: una base en nivel **100** puede utilizarlo en SQL Server 2025.

## Componentes

| Componente | Función |
|---|---|
| Message Type | Define el tipo y validación del mensaje |
| Contract | Determina qué mensajes puede enviar cada participante |
| Queue | Almacena los mensajes persistentemente |
| Service | Nombre lógico asociado a una cola |
| Conversation/Dialog | Canal ordenado entre dos servicios |
| Activation Procedure | Stored Procedure ejecutado automáticamente al llegar mensajes |
| Route/Endpoint | Comunicación entre instancias diferentes |

El flujo básico es:

`Transacción → SEND → Queue → Activation Procedure → RECEIVE → Proceso`

Los mensajes participan en las transacciones de SQL Server. Esto permite confirmar conjuntamente el cambio de datos y el envío o consumo del mensaje.

## Escenarios apropiados

1. **Procesamiento asincrónico**
   - Generación de archivos.
   - Cálculos pesados.
   - Actualización de información derivada.
   - Procesos posteriores a una operación administrativa.

2. **Desacoplar la aplicación**
   - PowerBuilder registra una operación y devuelve el control.
   - El procesamiento secundario continúa en background.

3. **Integración entre módulos o bases**
   - Una base publica una operación para que otra la procese.
   - Puede funcionar dentro de la misma instancia o entre instancias.

4. **Distribución y regulación de carga**
   - Los mensajes se acumulan en la cola durante picos.
   - SQL Server activa varios lectores según el volumen configurado.

5. **Procesos confiables**
   - Los mensajes no desaparecen si el consumidor está detenido.
   - Dentro de una conversación se mantiene el orden.

6. **Patrón Outbox transaccional**
   - Guardar una operación de negocio y publicar su evento en la misma transacción, evitando inconsistencias entre datos y notificaciones.

## Puesta en marcha

### 1. Verificar el estado

```sql
SELECT
  name,
  is_broker_enabled
FROM sys.databases
WHERE name = N'MiBase'
```

Las bases nuevas tienen Service Broker habilitado por defecto.

### 2. Habilitarlo si fuera necesario

```sql
ALTER DATABASE MiBase
SET ENABLE_BROKER
```

`ENABLE_BROKER` necesita acceso exclusivo a la base y puede quedar esperando mientras existan conexiones activas.

No debe utilizarse `NEW_BROKER` como alternativa rápida: genera un nuevo identificador y elimina las conversaciones existentes.

### 3. Crear los objetos

```sql
CREATE MESSAGE TYPE [//Infomedical/Procesar]
VALIDATION = WELL_FORMED_XML

CREATE CONTRACT [//Infomedical/ContratoProceso]
(
  [//Infomedical/Procesar] SENT BY INITIATOR
)

CREATE QUEUE dbo.ColaProcesos

CREATE SERVICE [//Infomedical/Procesador]
ON QUEUE dbo.ColaProcesos
(
  [//Infomedical/ContratoProceso]
)
```

Después se crea:

- un servicio iniciador;
- un diálogo mediante `BEGIN DIALOG CONVERSATION`;
- el envío mediante `SEND`;
- un Stored Procedure consumidor que utilice `WAITFOR (RECEIVE...)`;
- activación automática sobre la cola.

Para comunicación entre servidores también hacen falta:

- endpoint TCP de Service Broker;
- routes;
- certificados y permisos;
- firewall;
- configuración de seguridad de transporte.

## Operación y monitoreo

Los principales controles son:

```sql
SELECT * FROM sys.transmission_queue

SELECT * FROM sys.conversation_endpoints

SELECT * FROM sys.dm_broker_queue_monitors

SELECT * FROM sys.service_queues
```

Aspectos críticos:

- Finalizar correctamente las conversaciones con `END CONVERSATION`.
- Procesar mensaje y cambios de negocio dentro de la misma transacción.
- Implementar reintentos e idempotencia.
- Controlar mensajes “venenosos”: varios rollbacks consecutivos pueden deshabilitar la cola.
- Monitorear crecimiento de colas, conversaciones sin cerrar y errores de transmisión.
- Definir retención y trazabilidad sin guardar indefinidamente todos los mensajes.

## Cuándo no elegirlo

No es la mejor opción cuando:

- se necesita integración amplia con tecnologías no SQL Server;
- se requiere streaming masivo o ecosistemas Kafka;
- múltiples aplicaciones necesitan consumidores independientes;
- se necesita observabilidad y administración centralizada de mensajería empresarial;
- el equipo no puede asumir monitoreo especializado dentro del motor.

Para procesos internos ligados fuertemente a SQL Server, Service Broker es sólido y transaccional. Para integración corporativa heterogénea, suele ser más mantenible Azure Service Bus, RabbitMQ o Kafka.

## Evaluación para su entorno

Para aplicaciones PowerBuilder, puede resultar útil para descargar procesos pesados sin bloquear la interfaz. PowerBuilder sólo ejecutaría el procedimiento que registra la operación y envía el mensaje; el consumidor quedaría dentro de SQL Server.

Recomendaría comenzar con un caso **local, dentro de una única base e instancia**, antes de incorporar comunicación remota. Esto reduce considerablemente la complejidad de rutas, certificados, endpoints y recuperación.
