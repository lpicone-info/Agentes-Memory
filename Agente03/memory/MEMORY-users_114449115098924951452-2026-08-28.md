### [28/08/2026 12:08:43] Agente

Hugo, lo mas razonable es separar el proceso en dos etapas:

1. La impresion/generacion deja los PDFs en disco y registra una cola pendiente.
2. Otro proceso independiente toma esa cola y sube los PDFs a la API.

Modelo recomendado:

- Crear una tabla tipo `compro_pdf_upload_queue`.
- Al generar cada PDF, insertar un registro con `ente`, `tipo`, `nro`, `path_pdf`, `estado`, `intentos`, `fecha_alta`.
- Estados posibles: `PENDIENTE`, `SUBIENDO`, `SUBIDO`, `ERROR`.
- Un proceso batch/worker toma pendientes y llama a `of_sube_adjunto_masivo`.
- Si sube bien, actualiza `archivo_pdf_api` con el resultado.
- Si falla, guarda error y reintenta luego.

Punto importante: la generacion de comprobantes no deberia depender de que la API responda en ese momento. Solo deberia garantizar que el PDF fue generado correctamente y que quedo encolado para subir.

Para evitar inconsistencias, usaria:

- `lote_impresion_id` para agrupar la corrida.
- Reintentos controlados.
- Idempotencia por comprobante, para que subir dos veces el mismo PDF no duplique adjuntos.
- Una pantalla o consulta de pendientes/error para monitoreo.
- Un job cada X minutos o un proceso residente que procese la cola.

El cambio minimo seria no tocar todavia la generacion PDF, sino reemplazar la llamada directa a `of_api_sube_compro_pdf()` por un registro en cola. Despues se implementa el worker que reutilice la logica actual de subida.
