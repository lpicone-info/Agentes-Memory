---

### [21/09/2026 16:33:15] Agente

Marcelo, le ponen `EXECUTE AS` a un stored procedure para que el SP se ejecute con la identidad de otro usuario/principal de SQL Server, no con el usuario que lo invoca.

Motivos habituales:

1. **Resolver permisos indirectos**
   El usuario no tiene permisos directos sobre tablas, vistas u otros SP, pero sí puede ejecutar el procedimiento. El SP corre “como” otro usuario con más permisos.

2. **Encapsular seguridad**
   Se evita dar permisos amplios al usuario final. Solo se le da permiso de `EXECUTE` sobre el SP.

3. **Acceder a objetos de otro esquema o base**
   Si el SP consulta objetos fuera del ownership chain normal, `EXECUTE AS` puede usarse para que tenga permisos suficientes.

4. **Compatibilidad con lógica legacy**
   A veces se agregó para que el mismo SP funcione desde aplicaciones con usuarios distintos sin replicar permisos.

En tu error puntual, SQL Server está diciendo que intenta ejecutar el SP como el principal `dbo`, pero ese principal **no existe como usuario válido en esa base**, **no puede ser impersonado**, o **el usuario actual no tiene permiso para impersonarlo**.

Revisión concreta:

```sql
SELECT name, type_desc, sid
FROM sys.database_principals
WHERE name = 'dbo';
```

Y revisar el SP:

```sql
SELECT sm.execute_as_principal_id, dp.name
FROM sys.sql_modules sm
LEFT JOIN sys.database_principals dp
  ON sm.execute_as_principal_id = dp.principal_id
WHERE OBJECT_NAME(sm.object_id) = 'nombre_del_sp';
```

La causa más común en migraciones/restores es que quedó mal asociado el owner de la base o el `dbo`. En ese caso suele revisarse el owner de la DB y el mapeo de usuarios.

### [21/09/2026 16:51:12] Agente

Marcelo, sí: la causa más común es un **restore/migración mal cerrado**.

En SQL Server, `dbo` dentro de la base no es “un usuario común”: representa al **owner de la base**. El problema aparece cuando el `sid` interno de `dbo` queda apuntando a un login que en esa instancia **no existe**, o no coincide con el owner que SQL Server cree que tiene la DB.

Causas habituales:

1. **Restore desde otra instancia**
   La base venía de otro SQL Server donde el owner tenía otro SID. Al restaurarla en esta instancia, ese login no existe. Queda `dbo.sid` apuntando a un SID huérfano.

2. **Login owner eliminado o recreado**
   Si el login que era owner fue borrado y creado de nuevo con el mismo nombre, para SQL Server no es el mismo: cambia el SID.

3. **Restore sin reasignar owner**
   Después del restore no se ejecutó:

   ```sql
   ALTER AUTHORIZATION ON DATABASE::[Base] TO [sa]
   ```

   o al login dueño definido por estándar.

4. **Cambio parcial de owner**
   A veces se corrige `sys.databases.owner_sid`, pero la base queda internamente con `dbo` mal asociado, o viceversa. Eso deja inconsistencias raras como la que vimos.

5. **Uso viejo de `sp_changedbowner` o scripts legacy**
   Puede dejar escenarios confusos si se usó mezclado con restores, usuarios existentes o owners previos.

En tu caso, la evidencia fuerte es esta:

```text
PensandoSalud_Prod:
db_owner_login = sa
dbo.sid = d52b...
SUSER_SNAME(dbo.sid) = NULL
```

Eso indica que `dbo` quedó asociado a un SID que no resuelve a ningún login actual.

No necesariamente alguien “rompió” el SP. El `WITH EXECUTE AS SELF` solo hizo visible el problema, porque al ejecutar necesitó impersonar `dbo` y SQL Server no pudo resolverlo.

### [21/09/2026 16:59:26] Agente

Marcelo, podés correr esto en el server:

```sql
CREATE TABLE #dbo_owner_check
(
  database_name sysname,
  db_owner_login sysname NULL,
  db_owner_sid varbinary(85) NULL,
  dbo_mapped_login sysname NULL,
  dbo_sid varbinary(85) NULL,
  estado varchar(100)
)

EXEC sp_MSforeachdb '
IF ''?'' NOT IN (''master'', ''model'', ''msdb'', ''tempdb'')
BEGIN
  INSERT INTO #dbo_owner_check
  SELECT
    database_name = ''?'',
    db_owner_login = SUSER_SNAME(d.owner_sid),
    db_owner_sid = d.owner_sid,
    dbo_mapped_login = SUSER_SNAME(dp.sid),
    dbo_sid = dp.sid,
    estado =
      CASE
        WHEN dp.sid IS NULL THEN ''SIN_USUARIO_DBO''
        WHEN SUSER_SNAME(dp.sid) IS NULL THEN ''DBO_SID_HUERFANO''
        WHEN d.owner_sid <> dp.sid THEN ''OWNER_DBO_SID_DISTINTO''
        ELSE ''OK''
      END
  FROM sys.databases d
  LEFT JOIN [?].sys.database_principals dp
    ON dp.name = ''dbo''
  WHERE d.name = ''?''
END
'

SELECT *
FROM #dbo_owner_check
WHERE estado <> 'OK'
ORDER BY database_name

DROP TABLE #dbo_owner_check
```

Te va a devolver solo las bases problemáticas.

Interpretación rápida:

- `DBO_SID_HUERFANO`: caso como `PensandoSalud_Prod`, `dbo` apunta a un SID que no existe como login.
- `OWNER_DBO_SID_DISTINTO`: el owner de la base y el `dbo` no están alineados.
- `SIN_USUARIO_DBO`: anomalía más rara, falta el principal `dbo`.

La corrección típica para cada base afectada sería:

```sql
ALTER AUTHORIZATION ON DATABASE::[NombreBase] TO [sa]
```
