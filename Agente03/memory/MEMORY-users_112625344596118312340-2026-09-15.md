Dentro del `FOR`, el flujo sería conceptualmente:

```powerscript
FOR ...
    afi_impre_creden(...)
    lds_creden_impre.Retrieve()
NEXT

lds_creden_impre.Retrieve()
```

**¿Por qué está dentro del bucle?**

Probablemente fue colocado para que, después de insertar cada afiliado, el DataStore se actualice y el programa pueda disponer inmediatamente de los datos calculados por `afs_datos_creden` para esa iteración: plan, credencial, datos del afiliado, mail, condición fiscal, etc.

Pero hay un problema importante: cada `Retrieve()` no trae sólo el último registro. Como `afs_datos_creden` filtra por:

```sql
WHERE icpt.sp_id = @@spid
```

en cada iteración vuelve a procesar todos los registros acumulados de esa sesión.

Ejemplo con 3 afiliados:

```text
Iteración 1: Retrieve de 1 registro
Iteración 2: Retrieve de 2 registros
Iteración 3: Retrieve de 3 registros
Final:       Retrieve de 3 registros
```

Con 50 afiliados, el SP puede procesar aproximadamente:

```text
1 + 2 + 3 + ... + 50 + 50 = 1.325 filas lógicas
```

en lugar de procesar las 50 una sola vez. Además, cada fila vuelve a pasar por los `JOIN`, subconsultas `MAX(...)`, validaciones de vigencia y actualizaciones de `#temp`.

**¿Y por qué hay otro `Retrieve()` afuera?**

Puede tener dos motivos:

1. **Motivo funcional:** asegurar que el DataStore quede actualizado con el conjunto completo antes de continuar con la impresión o el envío.
2. **Motivo histórico:** puede ser una llamada redundante que quedó luego de modificar el flujo y conservar el `Retrieve` final por seguridad.

### [15/09/2026 10:45:59] Agente

Sí, existe la posibilidad de unificarlos. Pero hay dos alternativas distintas y conviene separar sus impactos.

**Alternativa 1: unificar para procesar un afiliado por llamada**

`afs_datos_creden` podría recibir los mismos parámetros de `afi_impre_creden`:

```sql
@prm_contra char(15),
@prm_inte char(2),
@prm_nombre varchar(100),
@prm_ape varchar(100),
@prm_val_hasta smalldatetime,
@prm_plan_codi char(10),
@prm_ingre_fecha smalldatetime,
@prm_naci_fecha smalldatetime,
@prm_docu_nro int,
@prm_val_desde smalldatetime,
@prm_prepaga smallint,
@prm_os_deno varchar(100),
@prm_docu_tipo char(2),
@prm_cuenta_tipo char(1) = NULL,
@prm_mail varchar(100) = NULL
```

Internamente, el SP podría formar una fila en una tabla variable o una expresión derivada y ejecutar la lógica actual sobre esa fila, sin:

```sql
INSERT INTO impre_creden_provi_tmp
```

ni:

```sql
WHERE icpt.sp_id = @@spid
```

El flujo quedaría conceptualmente:

```powerscript
FOR ...
    lds_creden_impre.Retrieve(parametros_del_afiliado)
NEXT
```

Esto elimina la tabla intermedia y el crecimiento `1, 2, 3`. Pero cada llamada seguiría ejecutando toda la lógica de `afs_datos_creden`, incluyendo sus subconsultas, `JOIN` y actualizaciones temporales. Si son muchos afiliados, seguiría existiendo un costo por cada llamada.

**Alternativa 2: unificar y procesar todo el lote de una sola vez**

Esta sería la opción con mejor rendimiento:

```powerscript
FOR ...
    afi_impre_creden(...)
NEXT

lds_creden_impre.Retrieve()
```

En este caso se mantiene una tabla de entrada, pero se ejecuta `afs_datos_creden` una sola vez para todos los afiliados. También se podría reemplazar `sp_id` por otro identificador de lote, aunque eso no resolvería el problema principal si se mantiene un `Retrieve()` dentro del bucle.

**Mi recomendación**

Para este caso no recomendaría que `afs_datos_creden` reciba un afiliado por vez, porque trasladaría el problema desde:

```text
INSERT + Retrieve
```

a:

```text
llamada completa a afs_datos_creden por afiliado
```

La solución más eficiente sería:

1. Mantener temporalmente `afi_impre_creden` para cargar los registros.
2. Eliminar el `Retrieve()` que está dentro del `FOR`.
3. Ejecutar un solo `Retrieve()` al finalizar el bucle.
4. En una segunda etapa, reemplazar `sp_id` por un identificador de lote más seguro o utilizar una tabla temporal real por sesión.
5. Optimizar internamente `afs_datos_creden`.

La unificación completa es posible, pero exige modificar:

- la firma de `afs_datos_creden`;
- el objeto DataWindow o DataStore;
- las llamadas PowerBuilder;
- la lógica que espera los datos dentro del `FOR`;
- las pruebas de impresión y envío de mails.

Además, algunos resultados actuales se calculan sobre el conjunto completo de filas cargadas. Por eso no alcanza con copiar el `INSERT` dentro de `afs_datos_creden`; primero hay que confirmar si PowerBuilder necesita los datos de cada afiliado inmediatamente o si puede esperar hasta el final.

**Conclusión:** sí, se puede eliminar `afi_impre_creden` y `sp_id`, pero el cambio de mayor beneficio inmediato sigue siendo dejar un único `Retrieve()` fuera del bucle. La unificación puede hacerse después como una refactorización controlada.
